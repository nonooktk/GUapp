## 0. 前提

P1 では事前レビュー（実装前レビュー記録 20260917、Wave 1・2 の事前レビュー）で設計の論理矛盾 21 件を潰したが、実装で さらに 5 件が見つかった。いずれも「論理」ではなく「ライブラリ・OS・DB の挙動」に起因し、机上では拾いにくい種類だった。本書はその 5 件を「同じ失敗を生む構造」に戻し、机上で確かめられる問いと、動かして確かめる手順の 2 段にした。

## 1. 観点（P1 の発見 5 件）

| # | P1 での発見 | 構造（なぜ起きた） | チェック項目（問い） | 確かめ方 | P2 で効く箇所 |
| --- | --- | --- | --- | --- | --- |
| 1 | 設計書 5.2「P1 は 13 表」が実際は 12 表 | 列挙と集計が別々に手書きされ、片方だけ直った。人は列挙を数え直さない | 文書内の「N 件」「N 表」「N 本」は、対応する列挙・表の行数と一致するか | `grep -oE "[0-9]+ (表|件|本|画面)"` で数字を全部抜き、列挙を数えて突き合わせる。ID 体系（DS-TBL 等）は連番と件数を照合 | 追補で増える表（sessions・stripe_events・chat_sessions・chat_messages・login_attempts）、API 本数、画面数、Must 18 件の充足数 |
| 2 | 同一カートへの同時確定で InnoDB デッドロック（INSERT orders の FK 共有ロック × UPDATE carts） | 事前レビューは UPDATE の順序だけ見て、INSERT が親行に共有ロックを取ることを考慮しなかった。DB の暗黙ロックは設計図に描かれない | 1 トランザクション内で触る行を、INSERT の FK 参照先を含めて列挙したか。同じトランザクション 2 本が同時に走ったときのロック取得順を表にしたか | 処理仕様ごとに「ロック表」（文・対象表・ロック種別・順序）を書く。同時実行テストは「同じ入力 × 2」と「同じ親 × 異なる子」の両方を含める。デッドロック時の再試行方針を先に決める | Stripe Webhook（stripe_events INSERT × orders UPDATE の同時到着）、会員登録（members INSERT × sessions INSERT）、チャット往復上限（chat_sessions UPDATE × chat_messages INSERT） |
| 3 | asyncmy が MySQL 8.4 の認証（caching_sha2_password）で `cryptography` を要求 | ドライランは「パッケージが解決できる」だけを確かめ、接続して初めて要る依存は見えない | 外部サービスとの接続に、実接続まで表れない依存・設定（認証方式・TLS・証明書・拡張）はないか | 版の調査に「hello world で実接続」を含める。Azure MySQL の `ssl=true`・CA 証明書、Stripe SDK の署名検証、ACS Email の接続、Anthropic SDK を最小コードで 1 回叩いてから設計を確定 | Azure Database for MySQL（SSL 必須）、Stripe、Azure Communication Services Email、Claude API |
| 4 | Windows に tz データベースが無く `ZoneInfo("Asia/Tokyo")` が失敗 | 開発 OS（Windows）と本番 OS（App Service Linux）の差。設計は Linux 前提 | 時刻・ロケール・パス区切り・改行・大文字小文字・子プロセス管理で、開発 OS と本番 OS の挙動差はないか | 差が出る領域ごとに「両 OS で動く方法」を設計書 8 章に明記（`tzdata` を依存に固定、`pathlib`、`.gitattributes`）。CI は Linux なので Windows 固有は ローカルでしか出ない前提で、README の再現手順を Windows で通す | 期限切れバッチ（APScheduler・`GET_LOCK`）、ログのエンコーディング（cp932 と Application Insights）、gunicorn（Windows では動かない。ローカルは uvicorn） |
| 5 | Python の `\d` が全角数字に一致し、郵便番号の検証を素通りする | 設計書の正規表現を、実装言語での意味の差を考えずに写した。日本語入力では全角が普通に来る | 正規表現・比較・正規化を実装言語の意味で読んだか。全角・半角・かな・大文字小文字・前後空白・ゼロ幅文字に対し、期待どおりに拒否／正規化するか | 入力形式表に「正規化の順序」（除去 → 変換 → 検査）と「全角は拒否か変換か」を明記。UT-VAL に全角数字・全角ハイフン・前後空白・絵文字を含める。TypeScript 側（BFF・フォーム）でも同じ表を使う | 会員登録のメール・パスワード、管理画面の検索、チャット本文のマスク（全角の電話番号を見逃すとマスク漏れ） |
