# ADR-0001 P2 を 4 回に分ける判断

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認 |
| 日付 | 2026-09-24 |
| 決定者 | 統括（Oya） |

## 背景

P1 は 2026-09-24 に完了し、PR #14 でマージ待ちの状態にある（`引継ぎメモ_20260924.md`）。P2 の出口条件は「Azure 上で Must 18 件と AI アシスタント（F-029）が動く」ことで、必達期限は 2026-10-31 である（`実装フェーズ計画.md` 2 章）。

P2 の残りは P1 のおよそ 3 倍の量にあたり、詳細設計もまだ作成していない。加えて、講義側の進捗報告が 9/30 にある。この 3 点（分量・未設計・締切）から、P2 を 1 回の V 字で回すのは難しいと判断した。

## 決定

P2 を次の **4 回**に分け、各回で「追補設計とテスト項目 → 実装 → 検収 → PR」という V 字を小さく回す。

| 回 | 内容（機能 ID） | 目安 |
| --- | --- | --- |
| P2-a | 商品検索 F-003、FAQ・静的ページ F-028、コンテンツ・お知らせ F-030、講義の MySQL への接続切り替え | 9/30 |
| P2-b | 会員登録・認証 F-024、注文履歴 F-017、店舗受け取り F-013／F-014（REQ-FR-501・508）、再入荷通知の申込 F-007（REQ-FR-205）、サイズ感の集計 F-005（REQ-FR-208） | 10/10 |
| P2-c | 管理画面（商品・在庫 F-031、注文 F-033、設定の画面 F-032）と管理認証 F-035、Stripe テストモード接続 IF-01、メール実送信 IF-02 | 10/20 |
| P2-d | AI アシスタント F-029（IF-03）、Azure デプロイ、P2 の検収 | 10/31 |

## 判断基準と理由

次の **4 つの基準**で各回への配置を決めた。

- **基準 1 依存関係**: 先に作らないと後が作れないものを前に置く。
- **基準 2 触るデータの塊（手戻り防止）**: 同じテーブル・同じ処理を変える機能を同じ回に集め、マイグレーションと注文確定処理（DS-PRC-014）の変更を 1 回にまとめる。
- **基準 3 優先度と外部依存**: Must を先、Should を後。外部サービスの品質や可用性に左右されるものは最後に置く。
- **基準 4 締切への成果の出し方**: 直近の締切（9/30 の講義報告）に確実に動くものを出すため、依存がなく小さく、既に基本設計がある機能を先頭の回に置く。

各回がどの基準でそこに置かれたかを次の表で対応づける。

| 回 | 適用した基準 | 対応づけの理由 |
| --- | --- | --- |
| P2-a | 基準 4 | 9/30 の講義報告に確実に動くものを出すため、依存がなく小さく、設計書に基本設計が既にある 3 件（DS-API-004〜006・DS-TBL-22 contents）を先頭に置いた。講義の指示（Step3-1,2 で使った MySQL にスキーマを新規追加して使う）も今週の課題なので P2-a に入れた |
| P2-b | 基準 1・基準 2 | 会員認証 F-024 → 注文履歴 F-017（会員の注文を出すため）という依存があるため、認証を先に P2-b に置いた。会員セッションの仕組み（`sessions` テーブル、DS-TBL-03）は管理認証 F-035（P2-c）が `subject_type` で分けて再利用する設計のため、認証を先に固める P2-b が P2-c より前に来る また、店舗受け取り・再入荷通知の申込・サイズ感の集計は、会員と注文の前後で `orders`・`reviews`・`restock_notifications` を触る「顧客側の購入前後」の塊として同じ回に集めた（基準 2）。 |
| P2-c | 基準 1・基準 2 | 会員セッションの仕組み（P2-b）を前提に管理認証 F-035 を置いた（基準 1）。また、注文の状態遷移（管理の状況更新 F-033 と Stripe の決済待ち→受付済・期限切れ）を触るため、管理と Stripe テストモード接続 IF-01 を同じ回にまとめた（基準 2） |
| P2-d | 基準 3 | Must を優先し、Should を後にする方針に加え、外部サービス（Claude API）の応答品質・可用性に左右される AI アシスタント F-029 を最後に置いた（要件定義書 A-03 で Should 判定にした理由と同じ） |

基準 2 の補足として、P2-b は `members`・`sessions`・`orders`（受け取り方法・受け取りコード）・`reviews`・`restock_notifications` を足す「顧客側の購入前後」をまとめた回であり、P2-c は注文の状態遷移を触る「管理と Stripe」をまとめた回である。この 2 つを分けることで、同じテーブル・同じ処理への変更が P2 内で 2 か所に分散することを避けた。

## 検討した代替案

| 案 | 内容 | 不採用の理由 |
| --- | --- | --- |
| 案 A | P2 全体の追補設計を最初にまとめて書く | DB 設計の手戻りは最も少ないが、9/30 の講義報告までに実装の成果が出ない。今回は不採用。代わりに、各回の頭で次の回以降に影響するテーブル変更だけは先に洗い出す（P2-b の追補設計で P2-c のテーブルも確認する）運用で代替する |
| 案 B | Must を全部終えてから Stripe・メール・Azure に着手する | 外部接続のリスクが最後に集中するため不採用 |
| 案 C | 機能ごとに 1 PR で細かく刻む | 注文確定処理を何度も変えることになり回帰リスクが増えるため不採用 |

## 影響とリスク

- Azure へのデプロイが P2-d と最後に来る。本番 OS 差（`P2_事前レビュー観点_v1.md` #4・#8）で詰まると 10/31 に響く。緩和策として、P2-a で講義の Azure MySQL に接続し DB 側の差を先に潰す。また、App Service へのデプロイ手順の試行を P2-c の終わりに前倒しできるかどうかを、P2-c の追補設計で検討する
- P2 の残りが見込みより大きい場合、どの機能から削るかの順番は未決である。これは本 ADR では決めず、別の ADR で決める
