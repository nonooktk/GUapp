# ADR-0006 P2 の残りの進め方と削る順番

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認 |
| 日付 | 2026-10-20 |
| 決定者 | 統括（Oya） |

## 背景

P2 の必達期限は 2026-10-31 で、今日（2026-10-20）から数えて残りは 11 日（10/21〜10/31）である。ADR-0001 は P2 を 4 回に分け、P2-b を 10/10、P2-c を 10/20、P2-d を 10/31 の目安としていた。実際には P2-a が 2026-09-25 に完了し（PR #22〜#25）、P2-b は追補設計の最初の版（`GU_ECsite_設計仕様書_P2追補b_draft-v1.md`）を書いた段階で、実装は始まっていない。P2-c・P2-d も未着手である。

状況は次のとおり。

- 2026-10-10 に配備先を `app-tech0-gen12-01-fe` / `-be`（F1 無料プラン）へ移した（ADR-0005）。2026-10-19 のセキュリティ点検の指摘は PR #39 で対応した。
- 講義の Week9（ログ・アラート）と Week10（閉域化）の対応が並行して要る。閉域化は、F1 では VNet 統合と Private Endpoint が使えないため、統括に確認中である。
- Lv3 の新機能 F-029（AI アシスタント）は、外部 LLM の応答品質と可用性が未確認で、早めに触る必要がある（要件定義書 A-03）。
- IF-03 の外部 API は、ADR-0001 と本編の設計仕様書が Claude API を前提にしている。しかし、オーナーが用意できるキーは OpenAI のものである。
- P2-b だけで会員認証・注文履歴・店舗受け取り・再入荷通知・サイズ感の集計があり、ADR-0001 の見積もりどおりの直列の進め方では 10/31 に収まらない。

## 決定

1. **日程**。次の表で進める。

   | 日付 | 内容 |
   | --- | --- |
   | 10/21〜10/22 | P2-b の追補設計とテスト設計の確定（draft-v1 を 10/20 に作成済み） |
   | 10/23〜10/25 | P2-b の実装（レーン分けは設計仕様書 P2 追補b の 11 章） |
   | 10/26 | P2-b の検収 |
   | 10/26〜10/29 | P2-c（管理画面 F-031・F-033・F-032、管理認証 F-035、メールの実送信 IF-02） |
   | 10/30 | P2-c の検収と、F-029 の組み込み |
   | 10/31 | P2 全体の検収（Must 18 件の確認、未実装の記録） |

2. **承認は「実装し切ってから最後にまとめて」とする**。ADR-0001 は各回で「追補設計とテスト項目 → 実装 → 検収 → PR」と進める方針だった。今回は、各回の設計・実装の途中で承認を取らない。統括が内容を見る関門は、10/26（P2-b の検収）、10/30（P2-c の検収）、10/31（P2 全体の検収）の 3 回とする。実装担当が迷わないよう、追補設計は迷う点を「決定」として書き切る（DS-DEC に理由つきで残す）。
3. **F-029 は P2-b と並行して、別ブランチ・別の作業ディレクトリで進める**。F-029 は会員・注文のデータに触らないため、P2-b と作業が衝突しない。ただし、次の共有点はマージ順で調整する。P2-b を先にマージし、F-029 側が取り込み直してからマージする。
   - Alembic の head：両方が `ad00074244c2` から分岐するため、F-029 側が `down_revision` を P2-b の最後のリビジョンへ付け替える（設計仕様書 P2 追補b の DS-DEC-83）。CI に「head が 1 本」の検査を足す。
   - `apps/api/app/main.py`（ルーターの登録）、`core/config.py`（環境変数）、`pyproject.toml`・`uv.lock`（依存）、`.env.example`、`apps/api/openapi.json` は両方が変えるため、後からマージする側が衝突を解消する。
   - F-029 の表（`chat_sessions`）の `member_id` は、P2-b を先にマージするので `members` を参照できる。参照するか NULL のまま運用するかは F-029 の追補設計で決める。
4. **IF-03 の外部 API は OpenAI（GPT）に変更する**（Claude API から）。理由は、オーナーが用意できるキーが OpenAI だからである。
   - 要求・要件との関係：要求仕様書（REQ-FR-901・902・905）と要件定義書（IF-03、A-03、6 章のチャット制約・LLM への送信）は「LLM API」と書き、提供元を指定していない。したがって、OpenAI の API は要件上の「外部の LLM」として扱え、要求・要件の改訂は要らない。商品 ID の照合、個人情報のマスキング、往復数の上限といった制約は提供元に関係なく維持する。
   - 設計・計画の文書で Claude を前提にしている箇所（F-029 の追補設計が改訂する）：設計仕様書 本編の 1 章（構成図の「Claude API」）、2 章（LLM の行。`anthropic`、モデルの想定）、3.3.3（シーケンス図）、7.6、8.1・8.2（環境変数 `ANTHROPIC_API_KEY`）、ADR-0001（P2-d の行と基準 3 の「Claude API」）、`P2_事前レビュー観点_v1.md` の観点 3（Anthropic SDK）。これらの記述は、ADR の履歴としては当時の前提の記録であり、本 ADR では書き換えない。
   - 環境変数名は `OPENAI_API_KEY` を想定する。モデル名・SDK の版・料金の上限は F-029 の追補設計で決める。キーはソースにも `.env.example` の値にも書かない。
5. **IF-01 Stripe テストモードは P3 へ送る**。購入の流れは、P1 の決済スタブで閉じている。
   - P2 の間は、公開環境でもスタブの決済のまま動かす（画面は「テスト決済」）。REQ-CO-06（カード情報を自サイトで保持しない）は、スタブがカード情報を扱わないので満たす。
   - 設計仕様書 本編の DS-DEC-26 の「P2 以降はスタブ OFF」「決済待ちの期限切れ（30 分）の実装」と、DS-DEC-28 の定期ジョブ（決済待ちの期限切れ用）は、P2 では実装しない。`stripe_events` 表も P2 では作らない。
   - ADR-0001 の P2-c の行から IF-01 を外す。実装フェーズ計画 4 章の「IF-01 は P2 でテストモード接続」は、本編と追補を統合する版で改訂する。
6. **遅れたときに削る順番**を次のとおり決める。各回の検収の時点で未完了のものがあれば、上から削る。

   | 順 | 削るもの | 関連する要求（優先度） | 削ったときの扱い |
   | --- | --- | --- | --- |
   | ① | IF-02 メールの実送信（P2-c） | IF-02。REQ-FR-504・802・803 のメール部分（いずれも Must の要求） | 外部 IF であり、Must の機能ではない。実送信の代わりに、開発はファイル出力、本番はログのスタブで動かす。このとき、確認メール・メール確認・パスワード再設定は、本番では完了できない（スタブはリンクを残さない）。検収記録に「メールは実送信せず（スタブ）」と書き、公開環境の確認が未実施であることを明記する |
   | ② | F-005 のサイズ感の集計 | REQ-FR-208（Should）。F-005 は Must | Must の機能 F-005 の一部を削る。検収記録に未実装と明記する |
   | ③ | F-007 の再入荷通知 | REQ-FR-205（Could）。F-007 は Must（在庫切れの表示 REQ-FR-204 は P1 で実装済み） | Must の機能 F-007 の一部を削る。検収記録に未実装と明記する |
   | ④ | F-032 の設定の管理画面 | REQ-FR-1102（Must） | Must の一部を削る。税率・送料などは seed と DB の直接更新で運用する（データは P1 から実装済み）。検収記録に未実装と明記する |

   ①は Must の機能ではないため、削っても Must 18 件の充足数は変わらない。②〜④は Must の機能の一部を削るため、検収記録に未実装と書く。この表の 4 つ以外を削る場合は、統括の追加の承認を取る。

## 判断基準と理由

- **必達期限（10/31）と Must 18 件の充足**：残り 11 日で直列に進める余裕がない。承認の関門を 3 回にまとめ、設計と実装の間の待ち時間をなくす。
- **触るデータの分離**：F-029 は会員・注文・商品のデータに触らない（読み取りで商品と FAQ を使うのみ）ため、P2-b と並行できる。マイグレーションの head などの共有点だけをマージ順で調整する。
- **不確実なものを早く確かめる**：外部 LLM の応答品質は ADR-0001 の時点では最後に置く理由だった。期限が迫った今は、不確実なものを後ろに置くほど、問題が見つかったときの余地が無くなる。並行して早めに実機で確かめる。
- **キーの入手性**：IF-03 は、使えるキーがある提供元を選ぶ。要求・要件が提供元を指定していないので、設計の差し替えで済む。
- **削る順番の根拠**：①は仕組み（トークンの作成と検証、メールの文面、API）を P2-b で作り終えており、アダプタを差し替えるだけの部分なので、削っても作った機能を失わない（意見）。②〜④は、①を削っても足りないときの順で、要求の優先度が低い（Should、Could）ものから先に置いた。④は Must の要求 REQ-FR-1102 だが、データは seed と DB の更新で代替できるため最後にした。

## 検討した代替案

| 案 | 内容 | 不採用の理由 |
| --- | --- | --- |
| 案 A | ADR-0001 の P2-b → P2-c → P2-d の直列を維持する | F-029 の統合と Azure の確認が 10/30〜10/31 に集中し、問題が見つかったときの余地がない |
| 案 B | F-029 を P2 から外す | Lv3 の課題要件（新機能）を満たせない |
| 案 C | 削る順番を決めずに進める | 遅れたときの判断が遅れ、検収の直前に議論になる |
| 案 D | Stripe を P2-c に残す | Webhook の署名検証と公開 URL を使う確認が要り、日程に収まらない。購入の流れはスタブで閉じているので、価値の損失が小さい |
| 案 E | 設計の承認を各回に残す | 11 日に 3 回の設計承認の待ちが入り、実装時間が足りない |

## 影響とリスク

- 承認が最後にまとまるため、設計の誤りの発見が遅れる。緩和策は、P2 事前レビュー観点の 8 問を追補ごとに記入すること、API・DB・画面の契約を追補設計の章で固定すること、同時実行などの結合テストを設計に含めること。P2-b の検収（10/26）で大きな差し戻しが出ると P2-c 以降が遅れる。この場合は、上の削る順番を使う。
- F-029 と P2-b の並行で、Alembic の head や共有ファイルの衝突が起きうる。決定 3 のマージ順で扱う。
- ①（IF-02 の実送信）を削ると、REQ-FR-802・803（Must）の検収は「ローカルのみ」になる。決定 6 のとおり検収記録に明記する。
- IF-01 を P3 に送ったため、DS-DEC-26・28 の P2 の範囲が変わる（決定 5）。監査ログの 90 日削除ジョブは、定期ジョブが P2 に無いままだと未実装になる。P2-c の設計で、実装するか未実装と明記するかを決める。
- OpenAI への変更で、応答品質・可用性・料金は実測前である。キーは秘匿値であり、コミットしない。キーを渡す先の利用上限（月額）を OpenAI 側で設定しておくことを推奨する（意見）。
- 閉域化（Week10）が P2-d のデプロイに影響する場合は、別の ADR で扱う（現時点は統括に確認中）。
