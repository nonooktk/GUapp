# ADR-0003 検索 API のレート制限の見送り

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認（ADR-0004 で再判断・見送り維持。2026-09-25） |
| 日付 | 2026-09-24 |
| 決定者 | 統括（Oya） |

## 背景

P2-a で F-003 商品検索（`GET /api/v1/search`、DS-API-004）を設計するにあたり、他の公開 API との整合を確認した。

- ゲスト注文照会（DS-API-023、`POST /api/v1/orders/{order_number}/lookup`）には**レート制限（100 件/時/IP）**が本編で設計済みで、`app/core/rate_limit.py` の `SlidingWindowRateLimiter`（プロセス内メモリのスライディングウィンドウ）として実装済み（本編 7.5・9.4、テスト設計書 IT-023-02）。個人情報（注文内容）への総当たりアクセスを防ぐ目的
- 一方、検索 API（DS-API-004）は**個人情報を含まない公開商品情報の読み取り**であり、本編・P2 追補a のどちらにもレート制限の設計が無い
- P2 追補a の事前レビュー（コーディネーターによる差し戻し）で、この非対称性が「本編との差分・矛盾」として指摘された（検索 API への大量呼び出し＝スクレイピング対策が未検討のまま）

検討した論点:

1. 検索 API は個人情報アクセスではないため、本編 6 章の非機能要件「不正検知（100 件/時/ID 超で遮断）」の対象（個人データ API）には該当しない
2. とはいえ、大量呼び出しによるサーバー負荷（DB への LIKE 検索クエリの連打）は、公開情報かどうかに関わらず起こり得るリスクである
3. P2-a の時点では GUapp はまだ Azure（講義サーバー）に公開されておらず、ローカル環境・限定的な検証環境での利用に留まる。実害が発生する状況ではない
4. レート制限を入れる場合、置き場所（BFF／FastAPI／CDN・WAF 相当）の選定、ローカルテストへの影響（IT の同時実行テストとの整合）など、検討すべき項目が増え、P2-a のスコープ（9/30 Week7 デプロイに向けた最小構成）を圧迫する

## 決定

**P2-a では検索 API（DS-API-004・004a）にレート制限を実装しない。** 設計仕様書追補（P2追補a）7 章にも「P2-a では設計しない」と明記済みのまま維持する。

意思決定のタイミングは、**Azure で GUapp を公開する P2-d（Week7 デプロイ前後を想定）の着手前**とする。そのタイミングで、次を判断する。

- 検索 API にレート制限が必要か（実際に外部から到達可能になるため、P2-a 時点とはリスクの前提が変わる）
- 必要な場合、どの層に置くか（BFF の Route Handler・FastAPI のミドルウェア・Azure App Service のアクセス制限・将来的な CDN/WAF 導入のいずれか）
- 制限値（件数／時間窓）をゲスト照会の 100 件/時/IP に揃えるか、公開商品検索としてもっと緩くするか

## 判断基準と理由

- **個人情報の有無**: DS-API-023 は注文内容という個人情報を扱うため総当たり対策が必須だが、DS-API-004 は公開商品情報のみで、本編 6 章の不正検知（個人データ API 対象）の対象外である
- **到達可能性と実害の対応**: P2-a の時点では Azure に公開されておらず、実際に外部から大量アクセスを受ける状況にない。実害が発生しうる段階（P2-d の Azure 公開）まで判断を遅らせても安全側に倒せる
- **スコープの最小化**: P2-a は 9/30 の講義報告に向けた最小構成を優先する回（ADR-0001 の判断基準 4）であり、置き場所の設計まで含むレート制限の追加はこの回の目的に合わない
- **やり直しのコストの低さ**: レート制限は後から追加してもデータ構造・API 契約に影響しない（追加のミドルウェア／依存関数を挟むだけ）ため、今回見送っても手戻りが小さい

## 検討した代替案

| 案 | 内容 | 不採用の理由 |
| --- | --- | --- |
| 案 A（採用） | P2-a では実装せず、P2-d 着手前に要否を再判断する | 上記の理由により、現時点でのリスクとスコープのバランスが最も良いと判断した |
| 案 B | P2-a で既存のスライディングウィンドウ制限器（`app/core/rate_limit.py`、DS-API-023 で使用）を流用して入れる | 実装コスト自体は小さいが、(1) DS-API-004 は個人情報アクセスではなく本編の非機能要件の対象外であり適用の必然性が薄い、(2) プロセス内メモリ実装のため P2-c 以降の gunicorn 複数ワーカー構成では効果が薄く、共有ストア（MySQL 表や Redis）への置き換えが別途必要になる、(3) 同時実行を検証する IT（本編 1.4 の偽陽性防止条件）に新たな考慮が要る、という理由で、Azure 公開前に本格設計する方が手戻りが少ないと判断し不採用とした |
| 案 C | 検索 API を含む全公開 API に一律のレート制限を先に入れる | 検索以外の閲覧系 API（DS-API-001〜003）まで対象が広がり、P2-a のスコープを大きく超えるため不採用 |

## 影響とリスク

- P2-a 実装から P2-d 着手までの間、検索 API に大量呼び出し対策が無い状態が続く。ただしこの間は Azure に公開されておらず、実害は限定的と判断している
- P2-d 着手前にこの ADR を再訪することを**忘れると**、レート制限が無いまま本番公開される恐れがある
- 案 B（`rate_limit.py` の流用）を後日採用する場合も、プロセス内メモリの限界（複数ワーカーでは制限が守れない）を踏まえた設計が必要になる

## 変更履歴

- 2026-09-25: レビュー期間限定で Azure App Service に公開するにあたり（ADR-0004）、サイト全体に HTTP Basic 認証をかける方針にしたため、この ADR が想定していた「再判断のタイミング」（Azure 公開の P2-d 着手前）で見送りを維持することを決定した。Basic 認証を知らない第三者は検索 API を含む `/api/*` に到達できないため、本 ADR が懸念する大量呼び出しのリスクは「Basic 認証あり」の前提では発生しない。詳細は `docs/00_計画/ADR/ADR-0004_レビュー用のAppService公開.md` を参照。**この判断は Basic 認証がかかっている間に限る。** Basic 認証を外す一般公開に切り替える場合は、本 ADR を改めて再訪すること
