# ADR-0004 レビュー用の App Service 公開

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認 |
| 日付 | 2026-09-25 |
| 決定者 | 統括（Oya） |

## 背景

Tech0 講義のレビュー期間中、運営のレビュワーに GUapp を実際に触ってもらう必要がある。統括が 2026-09-25 に次を決定済みである。

- サブスクリプション `9b680e6d-e5a6-4381-aad5-a30afcbc8459`（Microsoft Azure スポンサー プラン、テナント `admintech0jp`）のリソースグループ `rg-001-gen12`（受講生で共用。既存の `TV_MVP`・`POS` のリソースと名前が衝突しないよう命名する）、リージョンは東日本 `japaneast`
- 設計どおり App Service。Linux の App Service プラン B1 を 1 つに、web（Next.js）と api（FastAPI）の 2 つの App Service を同居させる（設計仕様書本編 8.1 で既に決定済みの構成をそのまま使う）
- DB は講義の MySQL `gen12-mysql-pos`（ADR-0002 のスキーマ `guapp_nonooktk`）を使い、ファイアウォールには App Service の送信 IP だけを追加する

本 ADR は、この決定を実施するにあたっての **入口保護の方式** と、それに伴う **ADR-0003（検索 API のレート制限見送り）の再判断** を記録する。ADR-0003 は「Azure で公開する P2-d 着手前に要否を再判断する」としており、本件がその再判断の機会にあたる。

## 決定

1. **サイト全体に HTTP Basic 認証をかける。** 対象は全ページと BFF の `/api/*`（`_next/static`・`_next/image`・favicon 等の静的アセットは対象外。理由は「判断基準と理由」参照）。ID・パスワードは統括が Slack でレビュワーにだけ個別に伝える
2. **Basic 認証の導入により、ADR-0003 の検索 API レート制限は今回の公開でも実装しない。** 理由は「判断基準と理由」参照。ADR-0003 の状態を「承認（P2-d 前に再判断）」から「承認（本 ADR で見送りを維持）」に更新する
3. **全ページ上部に「講義レビュー用のデモとして、YYYY/MM/DD まで期間限定で公開しています」の帯を常時表示する。** 終了日は App Service の環境変数（`DEMO_PUBLIC_UNTIL`）で管理し、コード変更・再デプロイなしで延長できるようにする。終了日を過ぎても自動停止はせず、停止は統括が手動で行う
4. **デプロイは最初は Azure CLI による手動デプロイとする。** 手順は `scripts/azure-deploy/` にスクリプトとして残す。GitHub Actions による自動デプロイは講義 Week7 以降に別途決定する

## 判断基準と理由

- **目的に対する最小構成**: 目的は「レビュー期間中だけ、限定した相手に触ってもらう」ことであり、一般公開ではない。Basic 認証はこの目的に対して実装コストが最小で、かつ検索 API・注文照会 API を含むサイト全体を一括で保護できる
- **ADR-0003 との関係**: ADR-0003 は検索 API への「大量呼び出し」（スクレイピング・DB 負荷）を懸念していた。Basic 認証を通過できるのはレビュワーだけであり、認証情報を知らない第三者は検索 API（含む `/api/*` 全体）に到達できない。したがって、ADR-0003 が懸念する状況（不特定多数からの大量呼び出し）は本公開では発生し得ず、レート制限を追加する必要性が無い。**この判断は「レビュー期間・Basic 認証あり」という前提に限定される。** Basic 認証を外す、または ID・パスワードが漏えいした場合はこの前提が崩れるため、ADR-0003 を改めて再訪すること
- **相手の候補を絞れない**: レビュワーが Tech0 のテナントアカウントを持つかどうか、固定 IP から接続するかどうかは統括側で把握できない。したがって Entra ID ログインや IP 制限は使えない
- **既存要件との整合**: 講義演習用のデモという位置づけ自体は変わらないため、DS-DEC-47（個人情報対策）・ADR-0002（講義サーバーに本物の個人情報を入れない）の方針をそのまま継続する。Basic 認証はこれらの上乗せであり、置き換えではない
- **期間限定の周知**: レビュワーが「いつまで見られるか」を認識できないと問い合わせ対応コストが増える。帯を全ページ常時表示にすることで、画面を見れば期間が分かるようにする。終了日をコードでなく環境変数にするのは、レビュー期間が延びた場合に再デプロイなしで対応するため
- **デプロイ方式**: 初回は手順の検証を兼ねるため、GitHub Actions より先に手動デプロイで動作確認する。自動化は Week7 の演習範囲であり、今回のスコープ外

## 検討した代替案

| 案 | 内容 | 不採用の理由 |
| --- | --- | --- |
| 案 A（採用） | サイト全体に HTTP Basic 認証 | 上記のとおり、実装コストが最小でスコープ全体を保護できる |
| 案 B | Container Apps の実行環境に相乗り | 要件定義書のインフラ選定で Container Apps は不採用（本編 8 章・実績調査 8 節「Container Apps は SSR アプリのホスティングに適する一方、バックグラウンドタスクがあると App Service が安定」）と経緯が既にある。今回だけ別基盤を使うと、Week7 以降の本デプロイ（App Service 前提）と構成が二重管理になるため不採用 |
| 案 C | Entra ID（Microsoft Entra ID）ログイン | レビュワーが `admintech0jp` テナントのアカウントを持つかどうか統括側で把握できていない。持たない場合はゲストアカウント発行等の追加調整が要り、レビュー期間に間に合わせるのが難しいため不採用 |
| 案 D | Azure App Service のアクセス制限（IP 制限） | レビュワーの接続元 IP が事前に分からない（複数人・複数拠点からのアクセスが想定される）。IP が変わるたびに統括が Azure 側の設定を更新する運用は現実的でないため不採用 |
| 案 E | Basic 認証なしで公開し、ADR-0003 のレート制限を実装する | 検索 API 以外（注文照会・カート・チェックアウト等)には元々レート制限が無く、Basic 認証と異なりサイト全体は保護できない。検索 API だけ守っても一般公開である以上、他の API への不正アクセス・スクレイピングは防げない。実装量も Basic 認証よりかかるため不採用 |

## 影響とリスク

- **共用 MySQL への接続**: `gen12-mysql-pos` は受講生で共用のため、ファイアウォールへの追加は App Service の送信 IP に限定し、他の受講生の規則には触れない（`scripts/azure-deploy/03-db-firewall.sh` の規則名 `guapp-appsvc-<連番>` で区別する）。共用サーバーへの負荷は B1・単一 uvicorn プロセス・`DB_POOL_SIZE=5`/`DB_MAX_OVERFLOW=5`（DS-DEC-46 の推奨値）を踏襲する限り小さいと見込む
- **費用**: App Service Plan B1（Linux）1 プランに web・api の 2 サイトを同居させる。2026-09-25 時点で Azure Retail Prices API（`https://prices.azure.com/api/retail/prices`、認証不要の公開 API）で確認した japaneast の B1（Linux）単価は **USD 0.019/時間**。730 時間/月換算で概算 **USD 13.87/月**（為替換算・実際の請求通貨はサブスクリプションの契約により異なるため参考値。日本円での実額は Azure ポータルの請求情報で確認すること）。DB は既存の講義サーバーに相乗りするため追加課金は無い想定
- **公開期間後の停止忘れ**: 終了日を過ぎても自動停止はしないため、統括が手動で `scripts/azure-deploy/90-stop.sh` を実行し忘れると課金が継続する。README に「終了日を過ぎたら 90-stop.sh を実行する」ことを明記し、統括の運用チェック項目とする
- **Basic 認証情報の漏えい**: ID・パスワードが漏えいすると、ADR-0003 で見送ったレート制限が無い状態でサイト全体が実質公開状態になる。漏えいに気づいた場合は `scripts/azure-deploy/02-settings.sh` を再実行して認証情報を再生成し、レビュワーに再周知する運用とする
- **検索 API のレート制限を今後入れる場合**: 一般公開（Basic 認証を外す運用）に切り替える判断が別途生じた場合は、本 ADR ではなく ADR-0003 を再度参照し、レート制限の要否を判断し直すこと

## 停止手順（概要）

1. `scripts/azure-deploy/90-stop.sh` を実行し、web・api の 2 つの App Service を停止する（削除はしない。再開はポータルまたは `az webapp start` で可能）
2. レビュー完全終了後、リソースが不要と判断できた時点で `scripts/azure-deploy/99-delete.sh` を実行する（実行前に確認プロンプトあり）。同スクリプトは DB ファイアウォールの `guapp-appsvc-*` 規則も削除する
3. 停止・削除いずれも、事前に統括の承認を得てから実行する（本タスクの禁止事項どおり、本タスク自体では Azure 上の操作は行わない）
