## 1. 判定の方法

各 UT について次の 3 問を順に立て、最初に No になった問いで分類した。

1. 期待結果を設計書の記述だけから手計算・手導出できるか（できなければ **A: 矛盾** か **C: 未定義**）
2. 記載されたテストレベル（pytest／Vitest）でその期待結果を観測できるか（できなければ **B: レベル不一致**）
3. 設計書の他の箇所と食い違わないか（食い違えば **A: 矛盾**）

3 問とも Yes なら「実装可」。判定は 1 件ずつ行い、まとめて判定しなかった。

## 3. 決定と理由

| # | 決定 | 理由 | 採らなかった案 |
| --- | --- | --- | --- |
| A1 | tax_rate は文字列 `"0.10"` で保存し、Decimal／基点整数（10 = 10%）で `合計×10 // 110` と整数演算 | float を排除し DS-DEC-31 と整合。期待値 411・592 はそのまま成立 | DB 列を DECIMAL に変える（system_settings は JSON value なので列型では縛れない） |
| A2 | エラー応答を判定順序（認証→形→存在→業務規則→DB 状態→回数→その他）で 1 つに決める規則に差し替え、DS-DEC-32 とする | P2 以降の認証・管理 API でも同じ規則で追補でき、Pydantic 既定の 422 との混同を防ぐ | 422 を使わず業務上限も 400 にする（「入力を変えれば通る」と「常に不正」の区別が消え、画面側の文言が出し分けられない） |
| A3 | 送料無料の閾値は小計に対して判定。ワイヤー例を 3,980／550／4,530／内税 411 に統一 | AT-08 と UT-021-01 が既に小計基準・この金額で書かれていた | 合計基準（送料を含めた金額で送料を判定する循環になる） |
| B1 | UT-WEB-06 を CI ジョブへ移管 | 観測できる場所に置く。設計書 7.2 の検証欄も元から「CI」 | Vitest でモジュールグラフを静的解析（過剰） |
| B2 | UT-WEB-07 は「表示内容が選択に追従」のみ。幅は AT／ST | jsdom の限界。Playwright 導入は P2 で採否判断（テスト設計書 8 章） | P1 で Playwright 導入（期限に対して重い） |
| B3 | UT-014-03/04 は SQLite インメモリで影響行数のみ検証 | 条件付き UPDATE は SQLite でも同じ意味。MySQL 固有挙動は IT-014-04 が担保 | UT を廃止して IT に統合（UT の高速な回帰検知を失う） |
| C1 | 郵便番号 `^\d{7}$`（ハイフン除去後）、電話 `^\d{10,11}$`（同）、メール EmailStr | 日本の郵便番号・電話番号の桁数。ハイフン除去で入力の揺れを吸収 | ハイフン付きのみ許可（スマホの数字キーボードで入れづらい） |
| C2 | ship_name 50、ship_address 200、ship_phone 11、guest_email 254 | メール 254 は RFC 5321 の上限。住所 200 は都道府県〜建物名の結合を想定 | — |
| C3 | 列挙コード pending_payment／accepted／preparing／shipped／delivered／pickup_expired／cancelled／payment_failed | 要件定義書 5.5 の 8 値と 1 対 1。英語小文字スネークで DB・API・画面を統一 | 数値コード（可読性が落ちる） |
| 補足 | 注文番号は UNIQUE 衝突時に 1 回だけ再生成 | 衝突確率は低いが 0 ではない。無限リトライは不要 | — |

## 4. 学び

- 期待結果を設計書から手で導く作業そのものがレビューになる。導けない箇所は「テストの書き方の問題」ではなく「設計書の穴」だった（6 件中 6 件）。
- テスト設計書は「観測できる場所」を意識して書く。jsdom にはレイアウトもビルドも無い。
- 「金額は整数」のような原則は、設定値の表現（JSON の 0.10）まで追わないと破れる。原則を書いたら、その原則に触れる全データを列挙して確認する。
