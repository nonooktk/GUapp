## 1. 結論

実装は 4 フェーズに分け、第 1 フェーズ（P1）を「ゲストが商品を選び、カートに入れ、注文を確定するまで」の最小構成とする。実装対象は機能 8 件と付随する 2 件の部分機能に絞るが、DB と API の基本設計は Must 18 件すべてを対象に先行して固める。理由は手戻りの回避にある。注文テーブルの会員 NULL や確定時単価のように、後のフェーズで追加すると既存テーブルの変更を伴う項目が要件定義書 5.5 に複数あるためだ。

フェーズを切っても開発モデルは V 字のままである。各フェーズの中で要求・要件・設計とそれぞれに対応するテストを対にして回し、フェーズをまたぐ追跡は要求 ID（REQ-xx）と機能 ID（F-xxx）で保つ。いわゆる反復型の V 字であり、フェーズは V を回す単位にすぎない。

Lv3 の課題要件である新機能は、要件定義書 v1.3 で AI アシスタント（F-029）と定めた。全画面右下に常駐するチャットが FAQ に答え、会話で商品を探して該当商品へ誘導する。優先度は Should のままだが、演習の課題要件として第 2 フェーズ（P2）で実装する。

この計画で決めたいのは、機能範囲と割り切り（2 章・3 章）、そしてフェーズごとの文書とテストの単位（5 章）である。未決の論点は 7 章にまとめた。

## 2. フェーズの分け方

要件定義書は機能 39 件を Must 18・Should 17・Could 4 に分けている。演習の合格ラインは Must 18 件が Azure 上で動作することなので（要件定義書 1 章）、Must の完遂を P2 の出口に置き、その手前に購買導線だけを通す P1 を設ける。P2 には Lv3 新機能の F-029 を加える。残りの Should と Could はそれぞれ P3・P4 とし、講義の Week7 デプロイ以降に余力があれば着手する。

| フェーズ | ゴール | 出口条件 |
| --- | --- | --- |
| P1 購買最小構成 | ゲストが SCR-001〜006 を通して注文を確定できる | ローカル環境で US-01（ゲスト購入）の受け入れテストに合格し、単体・結合テストが緑。画面幅 375px で導線が通る。README の手順だけで別 PC に環境を再現できる |
| P2 Must 完遂＋新機能 | Must 18 件と AI アシスタント（F-029）が動く | Azure 上で Must 18 件が動作し、7 章の受け入れ基準と 6 章の非機能基準（性能・セキュリティ・レスポンシブ）を満たす（Week7） |
| P3 Should | 返品・店舗受取・クーポン等の業務フローが閉じる | 着手した Should 機能の受け入れテストに合格 |
| P4 Could | レコメンド・再購入・ID 基盤 | 同上。未実装の Could は未実装と明記して申し送る |

## 3. P1 の範囲と割り切り

含める機能は次の 8 件である。F-001 商品カタログ表示、F-004 共通ナビゲーション、F-005 商品詳細表示、F-009 カート管理、F-013 注文手続き、F-014 注文確定処理、F-025 ゲスト購入、F-036 画面共通の状態表示。画面は SCR-001 ホームから SCR-006 注文確認・完了までの 6 枚で、要件定義書 5.3 の購入導線そのものにあたる。

このほかに、P2 送りの機能から 2 件を部分的に P1 へ戻す。F-007 のうち「在庫切れの明示」は P1 に入れる。在庫 0 の商品をカートに入れられると、注文確定時の在庫引当失敗（要件定義書 5.3 の異常系）が常態化するためだ。再入荷通知の申込は P2 のままとする。F-032 のうち税率・送料のデータ（システム設定テーブルと seed）も P1 に入れる。SCR-005 と SCR-006 の金額表示に必要だからで、管理画面から変更する機能は P2 とする。

割り切りも明記しておく。受け取り方法は配送のみとし、店舗受け取りの選択肢は P2 で足す。このため F-013 は P1／P2 の分割扱いとする（REQ-FR-501 の充足は P2）。支払い方法はクレジットカードのみとし、決済代行 IF-01 はアダプタ層の背後にスタブを置く。スタブと P2 のテストモード実装は同じアダプタ IF を満たすため、差し替えで済む。メール送信 IF-02 はログ出力のスタブとする。会員認証 F-024 は P2 とし、P1 はゲスト購入だけで導線を閉じる。F-005 のサイズ感集計（REQ-FR-208）はレビューデータに依存するため P2 とし、レビュー投稿 F-020 が P3 のあいだは seed のレビューで集計を出す。ゲスト購入には氏名・住所・メールの入力があるため、P1 のテストデータはダミーに限定する。

一方、設計で落とせない項目もある。注文確定の二重引当禁止と冪等キー（F-014、要件定義書 5.3 の二重送信防止）はトランザクション設計に直結するので P1 の詳細設計と単体テストに含める。金額計算をバックエンドで行いフロント値と照合する方針（設計仕様書雛形 7 章）も F-014 の設計に含める。画面幅 375px からのレスポンシブ（要件定義書 6 章）は後付けが難しいため、P1 の画面設計の前提とする。

## 5. フェーズごとの文書とテストの単位

設計仕様書は P1 を本編とし、P2 以降は差分だけを書く追補版にする。本編は設計仕様書雛形の 9 章構成に従い、基本設計（システム構成・画面・API・DB・外部 IF）は Must 18 件を対象に書き、F-029 は構成図・API 1 本・テーブル 1 つの概要レベルに留める。詳細設計（クラス・シーケンス・処理仕様）は P1 の機能に絞る。F-029 の詳細は P2 の追補で書く。提出時は本編と追補を結合した 1 冊にする。基本設計が全体を覆っていれば、講義側が 1 冊として評価しても範囲不足にはならないと考える。

テスト設計書も同じ単位で作る。V 字の左右対応は次の 4 レベルとし、1 冊の中で章を分けて末尾にトレーサビリティ表（REQ → F → 設計 ID → テスト ID）を置く。

| 左側（入力） | 右側（テスト） | ID | 粒度 | 作成時期 |
| --- | --- | --- | --- | --- |
| 要求仕様書 REQ-xx | 受け入れテスト | AT-xxx | ユーザーストーリー・業務フロー単位 | 設計仕様書の後（9/16 目安） |
| 要件定義書 F-xxx・非機能 | システムテスト | ST-xxx | 機能単位と非機能（性能・セキュリティ） | 同上 |
| 基本設計（API・画面・DB） | 結合テスト | IT-xxx | BFF・FastAPI・DB の主要経路。外部 IF はスタブ | 同上（P1 分） |
| 詳細設計（クラス・関数） | 単体テスト | UT-xxx | pytest・jest | P1 実装と同時 |

各テスト項目は正常値・異常値・境界値の 3 区分で書く。テスト設計書の完了条件は要件定義書 7 章のとおり、Must 18 件すべてに受け入れ基準が 1 件以上つくことである。

## 6. スケジュールと開発プロセス

守るべき期限は 2 つある。設計仕様書の提出が 9/9、実装とテストの完了が 10 月末である。README の講義スケジュール（Week4 テスト設計 9/9、Week5 コーディング 9/16、Week7 デプロイ 9/30）は進め方の目安として扱い、個人課題として次の順で進める。設計仕様書 P1 本編を 9/9 までに書き上げ、テスト設計書 P1 を 9/16 目安で続ける。環境構築は設計と並走させ、P1 の実装とテストを 9 月中に通す。P2 の追補設計・実装・Azure デプロイを 10 月に行い、10/24 までにデプロイを終えて残りをバッファに充てる。

開発プロセスは段階的に重くする。P1 はローカル環境・ゲスト購入・決済スタブ・ダミーデータに閉じているため、計画承認と証拠つきの完了報告だけを必須にした軽量プロセスで進める。P2 で会員認証と AI アシスタントの外部 API を加える時点、および Week7 の公開時点で、セキュリティレビューと公開リポジトリの点検を追加する。講義の Week8 セキュリティチェックがこの点検に相当する。

## 7. リスクと未決の論点

リスクのうち重いのは期限・DB の手戻り・決済スタブの不整合である。期限は 9/9 まで 3 日しかない。そのため P1 の設計仕様書は no_ai を壁打ちで作り、ai 版を経ずに with_ai 相当の 1 本にまとめることに決めた（2026-09-06 統括承認）。テスト設計書も同じ方式とする。DB の手戻りは 1 章の先行設計で対処する。決済スタブと本物の IF-01 の不整合は、P1 の設計で代行トークン方式のアダプタ IF を先に決め、スタブをその実装として書くことで避ける。

AI アシスタントには固有のリスクがある。応答品質と外部 API の可用性が演習の期間内に確かめきれないことで、要件定義書 A-03 が Should 判定にした理由でもある。対処として、FAQ 静的ページ（F-028、Must）だけで問い合わせ業務が成立する構成を崩さず、LLM が商品名や価格を創作しないよう商品 ID の照合を FastAPI 側に置く（要件定義書 6 章のチャット制約）。

未決の論点は次のとおり。docx の生成環境は現在の PC に無く、python-docx で再構築するか Markdown 正本を別 PC で docx 化するかは未定で、内容を先に固めてから決めればよいと考える。コードの置き場は GUapp リポジトリ配下に `apps/` を切る案に傾いている。docs とコードのトレースを 1 リポジトリで保て、他 PC への引き継ぎが README の前提と揃うためだ。作業用の clone は toolmaker の `apps/GUapp/` に置いた。ただし GUapp は public リポジトリなので、push の前にリポジトリの公開設定と秘匿情報の点検を行う。
