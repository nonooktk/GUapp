### G-01 【High】レート制限と本文サイズ制限が無く、共用プランを使い切れる（F-04）

- 事実: `GET /api/cart` を Cookie 無しで 300 回（20 並列）送ったところ、300 件すべてが 200 を返し、1.2 秒で終わった。毎回、カートが 1 行作られた。`/api/search` に 300 回送った場合も、すべて 200 だった。2 MB の JSON を `POST /api/cart/items` に送ると、201 で受理された。回数制限がかかっているのは注文照会だけである。これらのリクエストは公開環境には送っていない。
- 影響: 公開 URL を知っていれば誰でも、F1 の共用プランを短時間で使い切らせられる。プランを共用する他の受講生 4 人のアプリも止まる。講義で共用する MySQL のカート行も増え続ける。
- 対応: **今回の PR（PR-B）** で、S1（BFF の回数制限。`/api/*` は 120 回/分、それ以外の動的リクエストは 600 回/分）、S2（本文 8192 バイトの上限。超えたら 413 を返す）、S3（GET /cart でカートを作らない）を入れる。

### G-02 【中】Next.js 16.3.5 に既知の脆弱性（E-01）

- 事実: `pnpm audit --prod` は critical 1・high 3・moderate 4・low 1 の計 9 件。next 本体の 7 件（RCE は `next/og` の `ImageResponse` 限定、SSRF は `images.remotePatterns` 設定時のみ、ほかにキャッシュ汚染・情報露出など。修正は 16.3.6〜16.3.8）と、推移的依存の sharp・source-map-js の high。該当する機能は現構成で使っておらず（コード上の使用箇所 0 件）、実影響は小さいと判断した。`pip-audit` は 0 件。CI の `deps-audit` は `continue-on-error: true` で PR を止めない。
- 影響: 現構成では悪用条件を満たさない。OGP 画像や `next/image` の導入など、機能を足した時点で条件がそろう。
- 対応: **今回の PR（PR-B）**。S11（`next` と `eslint-config-next` を 16.3.8 以上へ更新）、S12（CI の `deps-audit` を critical で失敗させる）。sharp・source-map-js の high が残る場合は、Next の更新または `pnpm.overrides` で解消を試し、残れば理由を記録する。

### G-03 【中】本番に `TRUSTED_PROXY_HOPS` が入っておらず、注文照会の制限が全員で 1 つの枠になる

- 事実: BFF のコードは修正済みで、手元では `X-Forwarded-For`・`X-Client-IP`・`X-Real-IP` を毎回変えて照会しても、100 回目で 429 になる。公開 web のアプリ設定は、名前の一覧（値は見ていない）に `TRUSTED_PROXY_HOPS` が無く、設計仕様書 8.2 の「App Service 配下は 1」が反映されていない。未設定のときは、送信元に接続元の `127.0.0.1` が使われる。手元では、照会が 429 になった後、別のクライアントからの正しい照会も 429 になった。
- 影響: 公開環境では、誰か 1 人が 1 時間に 100 回照会を送るだけで、全員が 1 時間、注文照会を使えなくなる。
- 対応: **PR-A（#38）**で対応する。値は 1 とし、配備時にアプリ設定へ投入して反映する。反映後に、公開環境で 1 回照会し、App Service が付ける `X-Client-IP` が使われることを確認する。

### G-04 【中】カートの成功応答の本文に `cart_token` が入る（A-07）

- 事実: `GET /api/cart` の本文の `cart_token` が Cookie の値と一致する。本文から取った値だけを別クライアントの Cookie に入れると、他人のカートの明細が取れ、`POST /api/cart/items` も通った。
- 影響: XSS が 1 つ成立すると、HttpOnly で守っているはずのカート識別子を JS が読める。カートは匿名で個人情報が無く、注文後の照会にはメールが要るため、被害は他人のカートの閲覧・編集に限られる（意見: 現状は中〜低。CSP が無い点と重なる）。
- 対応: **今回の PR（PR-B）**。S4（BFF のカート応答の本文から `cart_token` を除く。Set-Cookie は従来どおり）。

### G-05 【中】セキュリティヘッダ・CSP・HSTS が無い（D-01〜D-03、C-02）

- 事実: 公開 web・手元とも、CSP・X-Frame-Options・X-Content-Type-Options・Referrer-Policy・Permissions-Policy・Strict-Transport-Security が 0 件。api も同様。HTTP→HTTPS は 301、TLS は 1.2 以上で、これは OK。
- 影響: クリックジャッキング、MIME スニッフィング、XSS 発生時の被害拡大を防ぐ層が無い。HSTS が無いので、初回 HTTP アクセスの傍受を防げない。
- 対応: **今回の PR（PR-B）**。S5（web は `next.config.ts` の `headers()`、api はミドルウェアでヘッダを付ける）。CSP の `script-src` は付けない。nonce 方式の本格的な CSP は後日。

### G-06 【中】拒否・失敗のログとアラートが無い（F-05）

- 事実: BFF の 403（`verifyCsrf`）と 400、api の 401（内部トークン不一致）と 429 は、ログが一切出ない。公開側は `httpLoggingEnabled=false` で、Application Insights の設定もない。上限への到達も、不正なトークンの連発も検知できない。
- 影響: 攻撃や誤設定が起きても気づけない（G-01 の消費攻撃も、後から把握できない）。
- 対応: **今回の PR（PR-B）**で S9 に対応する。拒否したときに 1 行の構造化ログを出し、IP は丸め、本文・Cookie・トークン・個人情報は出さない。**アラートは未対応**。検知の仕組み（Application Insights の接続とアラート規則）は今回の範囲に含めておらず、当面はログを手動で確認する。

### G-07 【低】api の URL がインターネットから直接届く（D-12）

- 事実: 外部からの通信が公開 api に直接届く。`/api/v1/health` 以外は、トークンがなければ 401 になり、誤ったトークンや空のトークンでも同じく 401 になる。トークンは 256bit のランダムな値である。web も api も、IP 制限は「Allow all」だけになっている。
- 影響: 内部トークンが漏れた場合、BFF の CSRF・入力の絞り込み・回数制限をすべて回避して api を直接呼び出せる。今のところ、トークンが漏れる経路は見つかっていない（バンドルに 0 件、履歴に 0 件、ログはマスクされている）。
- 対応: **Week10 の閉域化**。App Service のアクセス制限で、api への許可を web の送信元だけに絞る（設計仕様書 DS-DEC-21、DS-DEC-27）。

### G-08 【低】数量が極端に大きいと 500（F-03）

- 事実: `POST /api/cart/items` に `quantity` として 999999999999 を送ると、固定文言の 500 が返る。カートの状態は変わらず、内部情報も漏れない。PATCH は上限判定が先に行われ、422 が返る。`1e300` は 400 になる。
- 影響: 応答自体は正常に返るが、500 は不要なアラートやログの汚染を招く。また、外部から DB の例外パスを叩ける。
- 対応: **今回の PR（PR-B）**。S7 として、BFF は `quantity` を 1〜99、`variant_id` と `item_id` を 1 以上 2^53-1 以下に制限し、api は `quantity` に `ge=1, le=99`、`variant_id` に `ge=1, le=9223372036854775807` を指定する。範囲外の値は 400 になる。

### G-09 【低】製品名の露出と開発時のメソッド挙動（D-04、A-05）

- 事実: web には `X-Powered-By: Next.js` が、api には `Server: uvicorn` が付く（バージョン番号は出ていない）。手元の `next dev` では TRACE に対して 500 が返る。公開している web・api の ARRAffinity Cookie は SameSite=None で、Azure が付与している（`clientAffinityEnabled=true`）。
- 影響: どちらのヘッダも、攻撃者に製品名を教える程度である。F1 は 1 インスタンスなので、ARR affinity は不要である。
- 対応: **今回の PR（PR-B）と PR-A**で行う。web の `X-Powered-By` は、S5 の `poweredByHeader: false` で外す（PR-B）。api の `Server` ヘッダは、PR-A の起動コマンドに `--no-server-header` を指定して外す。ARR affinity は、配備時に `clientAffinityEnabled` を false にして止める。

### G-10 【低】アプリ設定が平文で、マネージド ID・Key Vault が無い（E-02）

- 事実: web・api とも Key Vault 参照が 0 件で、マネージド ID も無い。api の `DATABASE_URL`（DB パスワードを含む）と、両者の `INTERNAL_TOKEN` が App Settings に平文で入っている。リポジトリ（履歴を含む）には混入していない。
- 影響: Azure サブスクリプションの閲覧権限がある人は、値が読める。講義環境では許容範囲と考える（意見）。
- 対応: **本番運用時に対応**。本番運用に進める場合は、Key Vault 参照に切り替える。それまでは、サブスクリプションの共有範囲を README に明記する。

### G-11 【低】共用 MySQL のファイアウォールと公開設定（Z-01）

- 事実: 講義共用の `gen12-mysql-pos` は public アクセスが有効で、規則 62 件のうち `0.0.0.0` が 1 件（全 Azure サービスの許可）。自分の側の規則 31 件は個別 IP。`require_secure_transport=ON`、TLS 1.2 以上。
- 影響: 他テナントの Azure リソースからも DB のポートに届く。ただし認証情報は別途必要。
- 対応: **講義運営へ依頼**。サーバーの管理者の設定で、自分では変更できない。自分の側では、DB ユーザーの権限を自分のアプリ用の 1 ユーザーだけに限っているか確認する（15 分）。

### G-12 【低】CSRF 対策の弱い点（C-03）

- 事実: Double Submit Cookie に署名が無い。攻撃者が Cookie を差し込める前提（サブドメインや同一ホストの別アプリ）では、両方に同じ値を入れて通せる（手元で再現した）。`Origin` と `Sec-Fetch-Site` の検証は無く、`Origin` が `evil.example` でもトークンが正しければ通った。`GET /api/cart` は Cookie を発行し、DB に書き込む。
- 影響: SameSite=Lax と Secure（本番）により、通常の別サイトからの攻撃は成立しない。ゲスト購入のみのため、影響はカート操作と注文確定に限られる。
- 対応: **今回の PR（PR-B）** で、S6（`verifyCsrf` に Origin の確認を足す）と S3（GET が DB に書かないようにする）を実施する。

### G-13 【低】注文メールがファイルに個人情報を平文で保存する（M-01 の別件）

- 事実: `OutboxMailAdapter` が `.mail-outbox/<注文番号>.txt` に、氏名・住所・電話・メールを平文で書く（手元に 4 ファイル）。公開側でも同じアダプタなら、App Service のローカルディスクに残る。`.gitignore` 済みで、リポジトリには入らない。
- 影響: 個人情報を扱う本番では不適切。デモはダミー値が前提（フォームの初期値で誘導）。
- 対応: **今回の PR（PR-B）**。S10（`APP_ENV=production` のときは、ファイルに書かず、ログに注文番号だけを出す）。

### G-14 【低】api 側の回数制限は `X-Forwarded-For` の先頭を信用する

- 事実: `client_ip` は `X-Forwarded-For` の先頭の要素をそのまま採用する。BFF が検証済みの IP を付与するため、BFF 経由では偽装できない（手元で確認済み）。api を直接呼ぶには内部トークンが必要なので、この挙動は現状では悪用できない。
- 影響: 影響が出るのは、G-07 と組み合わさる場合（トークンが漏えいした時）だけ。
- 対応: **今回の PR（PR-B）** で、S8（`X-Forwarded-For` の末尾の要素を使う）として対応する。

### G-15 【低】未認証で内部状態が分かるヘルス応答

- 事実: 公開 api の `/api/v1/health` は、トークンなしで `{"status":"ok","db":"ok"}` を返す。公開 web の `/api/health` は、`upstream` の内訳も返す。
- 影響: DB の稼働状態が外部から分かる。この情報の機密性は低い。
- 対応: **対応しない**。死活監視のために、意図的に公開している。必要になれば、web の `/api/health` から `upstream` の内訳を除く（任意）。
