- 事実: 一番重い指摘は G-16。ログインのロックは、リクエストを並列で送るとすり抜けられる。会員のログインでは、12 本を同時に送ると 12 本とも照合まで進んだ。会員と管理画面の両方が対象である（並列の実測は会員のみ。管理はコードで同じ作りであることを確認）。原因は処理の順序にある。「数える→照合→記録」の順で動くため、数える時点では、同時に走っている他のリクエストの失敗がまだ記録されていない。

## 1. 点検の範囲と方法

手元の環境（web は `next dev`、api、Docker の MySQL）には、能動テストとして、改ざん・注入・総当たり・並列送信などを試すリクエストを送った。一方、公開環境の web と api は、受動確認と少量のリクエストによる確認にとどめた。大量送信、注入、改ざんは行っていない。

公開環境では、アカウントの作成、実在するアカウントでのログイン、ロックの試行、そのほか状態を変える操作は行っていない。ロックの試験は手元の環境だけで行った（本人の指示による）。公開環境で状態が変わったのは、存在しない ID でログインに失敗した記録が 3 行（会員 2・管理 1）と、チャット 5 回分の会話の記録だけである。

3 担当とも、コード・設定・DB の変更や git 操作はしていない。`.env*` は開いておらず、本番 DB の中身も読んでいない。

### G-16 【中】ログインのロックが並列送信ですり抜けられる（B-04、F-04）

- 事実: 直列で送ると、誤ったパスワードの 5 回目まで 401 で、6 回目は正しいパスワードでも 403 `account_locked` になる（会員の seed 会員と、管理の `demo-staff` で確認）。
- 事実: 並列で送ると、ロックが効かない。新しい seed 会員に、誤ったパスワードを変えて 12 本同時に `POST /api/auth/login` を送ったところ、12 本とも 401 `invalid_credentials` だった。直後に正しいパスワードで 1 本送ると 403 になった（失敗が 12 件記録されたため）。
- 事実: 原因は `apps/api/app/services/auth.py` の `login` の処理順である。失敗件数を数え（IP 30 件・メール 5 件）、argon2 の照合を待ち、失敗したあとで初めて `_record_failure` が行を書く。argon2 の計算は同時 2 本に絞られているため、待たされる間に後続のリクエストがすべて「件数 0」を読んで通過する。
- 事実: 管理ログインも、`admin_auth.login` が同じ「数える→照合→記録」の順であることを、判定者（Claude Opus）がコードで確認した。並列の実測は会員側のみである。
- 事実: 公開環境では、argon2 が 1 回およそ 1 秒かかる（存在しない会員への 401 が 990〜1035ms）。並列送信は公開環境では試していない。
- 影響: 意見: 「15 分に 5 回」の上限が、1 回のバーストの中では効かない。IP 単位の上限も同じ仕組みなので、同様に超えられる。BFF の全体制限（120 回/分/IP）と argon2 のコストは残る。パスワードの決まりが薄いこと（G-17）と合わさると、よくあるパスワードの推測が現実的になる、と思う。悪用に資格情報は要らない（会員は対象のメールアドレスが分かればよい）。
- 重大度: 中。設計上の主要な防御（DS-DEC-70）が無効になる。Blocker にしないのは、禁止語・argon2id・全体制限が残るため。
- 対応: **PR-C**（6dd2c46）で対応した。会員・管理で共通の `claim_login_attempt`・`withdraw_login_attempt` を使う。
  - 照合の前に、その試行を失敗として `login_attempts` に記録して COMMIT する。そのあとで、自分の行を除いて失敗数を数える。
  - 上限以上なら、照合せずに拒否し、先に記録した行を取り消す（ロック期間は延びない）。
  - 成功したら、失敗行を消して成功を記録する。
  - 閾値、窓、応答は変えていない。
- 意見: 副作用がある。同じアカウントに 6 本以上を同時に送ると、互いの行を数え合って、1 本も照合に進まないことがある（手元の 12 本同時の試験では、3 回とも 0 本だった）。巻き込まれた正規の 1 本も 403 になるが、行は取り消されるのでロックは残らず、再試行で通る。上限ちょうど（5 本）の同時送信は全部が照合に進み、次の 1 本がロックされることを、テストで固定した（IT-032-17・IT-050-13）。

### G-17 【低】弱いパスワードで登録できる（B-05）

- 事実: 8 文字の `password2` で登録でき、ログインもできた（202／200）。禁止語は 20 語で固定。構成ルールは置かず、同一文字の繰り返しとメールとの同一だけを追加で拒否する（`apps/api/app/services/password_policy.py`）。`password!`・`11111112`・`qwertyuiop` なども通る作りである。
- 影響: よくあるパスワードが通る。ログインのロックは 5 回/15 分なので、G-16 と合わせて評価した。意見: 長さ 8 文字以上・argon2id・ロックがあり、NIST SP 800-63B の考え方（構成ルールなし）を意図して選んでいるため、低とした。ただし NIST は、漏えいしたパスワードのリストとの照合も求めており、20 語では足りない、と思う。
- 対応: **PR-C**（8b635a8）で対応した。禁止語を 20 語から 236 語に広げた。あわせて、次のものも 422 `weak_password` にする（登録と再設定の確定の両方）。禁止語の前後に数字・記号を足したもの、leet 表記（`p@ssw0rd` など）、連番・繰り返し・キーボード配列、メールの `@` より前（4 文字以上）を含むもの。対象外は、禁止語の前に文字を足したもの（`mypassword`）、連番の折り返し、5 文字以上の単位の繰り返しである。判定の位置と応答コードは変えていない。

### G-18 【低】本番の管理者 ID が既定値で、5 回の失敗で締め出せる（B-07、B-04）

- 事実: 点検時点の本番の管理者 ID は、配備スクリプトの既定値 `demo-staff` だった（本番 DB は読んでいない）。この ID はコードと設計書に書かれている。`/admin/login` は公開されている。
- 事実: ロックは ID 単位で、IP は問わない。直近 15 分に失敗が 5 件あると、正しいパスワードでも 403 `account_locked` になる。手元で再現した。ロック中は失敗を記録しないため、期限は最初の失敗から約 15 分で、切れたら同じ 5 回でまた閉められる。管理者が自分で解除する手段、通知、アラートは無い（`staff.locked_until` は予約のまま未使用）。
- 事実: パスワードは 20 文字のランダムな値（約 119 bit）で、ロックと IP 制限（10 回/15 分）もある。
- 意見: パスワードの推測は現実的でない。
- 影響: 攻撃者は、15 分ごとに 5 回のリクエストで、管理者の商品・在庫・注文の対応を止められる。ログイン済みのセッションには影響しない。データの漏えいと改ざんには至らず、EC の購入も止まらない。
- 重大度: 低。意見: 影響が管理作業の一時停止にとどまり、管理者は 1 人でログインの頻度も低い。ただし、ID を推測不要にしているのは既定値なので、直すコストは低い。
- 対応: 2026-10-22 に、本番の管理者 ID を `staff-` で始まるランダムな値に変更した（`demo-staff` は 0 件。新しい ID は手元の git 管理外のファイルにだけ置き、本書には書かない）。パスワードは変えていない。あわせて、デプロイスクリプトを変更した（**PR-C**、3445eea）。`02-settings.sh` は、`.env.admin` に `SEED_STAFF_LOGIN_ID`（`staff-` ＋小文字英数字 10 文字）が無ければ作り、`06-migrate-seed.sh` がそれを seed に渡す。締め出しの根本は、Week10 の閉域化で `/admin` を絞ることで対応する。

### G-19 【低】拒否ログに、狙われたアカウントが分からない（F-05）

- 事実: `apps/api/app/core/reject_log.py` の `log_rejection` が出す項目は、event・path・method・status・code・IP だけである。会員のログインの失敗とロック、管理ログインの失敗・ロック・429 も同じ形で、どのアカウントが狙われたかを、ログから特定できない。DB の `login_attempts.identifier`（SHA-256）には残るが、DB を見る運用が前提になる。
- 事実: 補足として、会員の登録の成功と再設定の受付は、ログにも監査ログにも出ない（登録 `member.register` と再設定の確定 `member.password_reset` は監査ログにある）。
- 影響: ログだけでは、特定のアカウントの締め出し（G-18）と、手当たり次第の試行を区別できず、事後の調査に DB が要る。意見: 情報の流出ではなく調査のしやすさの問題なので、低とした。個人情報を出さない設計意図は妥当で、ハッシュなら両立できる。
- 対応: **PR-C**（5ed2502）で、拒否ログに `subject`（正規化した識別子の SHA-256 の先頭 12 桁）を付けた。対象は、会員・管理のログインの 401・403・429 と、再設定の要求のメール単位の 429 である。メール・ID・パスワード・トークンそのものは出さない。アラートは、前回の G-06 のとおり別対応である。

### G-20 【低】AI の出力ガードが、canary を変形した出力と数字なしの約束を通す（L-01a、L-01c）

- 事実: `apps/api/app/services/chat_guard.py` の `contains_canary` は、NFKC 後に大文字小文字を無視した部分一致だけを見る。ガード関数に直接渡したところ、次の出力が通過した。1) canary を 1 文字ずつ空白で区切ったもの。2) `-` を長音（`ー`）や非改行ハイフン（U+2011）に替えたもの。3) 逆順にしたもの。4) 途中に `…` を挟んだもの。5) システムプロンプトの本文（R1〜R12 の文章）をそのまま書いた `clarify`。
- 事実: `faq`・`clarify` の message に、「今なら全品送料無料」「クーポンコード WELCOME で割引」「全品半額セール中」のような、数字を含まない約束文があっても通る。金額と数字の照合（`numbers_not_in_sources`、`find_foreign_amounts`）にかからないため。
- 事実: 実機の LLM（手元 28 回・公開環境 5 回）は、同種の依頼にすべて従わなかった。実害は再現していない。
- 影響: LLM がインジェクションに従った場合、システムプロンプトの本文や、サイトの約束ではない割引・送料無料の案内が、利用者の画面に出うる。システムプロンプトに秘密の値は無く（canary は漏えいを見つけるための合言葉）、機密性への影響は小さい。誤った約束は、トラブルや景品表示の面で信頼を下げうる。ただし、他の利用者には見えず、依頼した本人の画面にだけ出る。意見: 実機で再現しないこと、他の利用者に波及しないこと、プロンプトに秘密が無いことから、低とした。将来、プロンプトに内部 URL など運用上の秘密を入れるなら、重大度は上がる。
- 対応: **PR-C**（96afb85）で対応した。canary の検知は、NFKC・小文字化のあと、空白・記号・長音を除いた文字列とその逆順にも当てる。約束の語（送料無料・クーポン・割引・半額・セールなど）が応答にあり、LLM に渡した資料（FAQ・特商法・商品一覧・文脈の商品）に無いときは、安全な文に置き換える。FAQ の「4,990円以上で送料無料です」は通る。利用者の質問は資料に含めない。システムプロンプトの本文そのものを書いた出力の検査は、今回は足していない。

### G-21 【低】AI に送る前の個人情報のマスクに漏れがある（L-01e）

- 事実: `chat_guard.mask_pii` は正規表現で、次の形を取りこぼした（ガード関数に直接渡した結果）。県名なしの住所（`渋谷区神南1丁目2番3号`）、`taro (at) example (dot) com` のように崩したメール、漢数字の電話番号（`零九零 一二三四 五六七八`）、`佐藤花子といいます`、姓名の間に空白がある氏名（`山田 太郎 です`）、マイナンバーに似た 12 桁。`東京都渋谷区神南1-2-3` は `[住所]-3` となり、末尾の断片が残る。通ったものは、DB（`body_masked`）と OpenAI の両方に渡る。
- 影響: 入力欄の注意書き（氏名・住所・電話番号などは入力しない）を無視して個人情報を書くと、一部が OpenAI（`store=False`、`safety_identifier` はハッシュ）と DB に残る。保存は匿名の会話で、会員・注文とは結びつかない。意見: 設計判断 DS-DEC-99 が「最小の形」と明記していること、注意書きがあること、紐づく会員がいないことから、低とした。
- 対応: **PR-C**（96afb85）で、マスクを足した。県名なしの住所（番地の末尾の断片は残さない）、`(at)`・` at `・`(dot)` で崩したメール、漢数字・全角の電話番号、「〇〇といいます」「山田 太郎 です」の氏名、12 桁の番号（`[番号]`）である。限界は、漢数字の番地と「1条西2丁目」型の住所が未対応なことである。「といいます」の氏名は、前の語を巻き込むことがある。

### G-22 【低】AI のガードが発動しても、ログに出ない（F-05）

- 事実: ログに出るのは、canary の漏えい（`chat_canary_leak`）と、`chat_reply` の `dropped_ids`（`recommend` で捨てた商品 ID の件数）だけである。金額照合による定型文への置き換え、`product_info` の定型文化、FAQ の数字の不一致による `out_of_scope`、HTML・URL の除去、PII のマスクの発動は、記録されない。`chat_reply` の intent が `out_of_scope` でも、LLM が断ったのか、コードが置き換えたのかを区別できない。
- 事実: 補足として、`clarify` が定型の聞き返し（`NO_PRODUCTS_MESSAGE`）になった例が 2 件あった。LLM が `items` を空で返したのか、ガードが商品を捨てたのかは、このログの不足のために区別できなかった。
- 影響: インジェクションの試行や LLM の暴走が起きても、運用者は件数や傾向を知れない（canary の漏えいだけは分かる）。意見: 攻撃自体は止められており、検知が遅れるだけなので、低とした。
- 対応: **PR-C**（96afb85）で対応した。ガードが動いたとき、種類と件数だけを 1 行のログ（event は `chat_guard`）に出す。種類は `html_url`・`pii_output`・`pii_input`・`canary`・`amount`・`promise`・`product_info`・`faq_number`。本文は出さない。出力側のガードが動いたときは WARNING、質問のマスクだけなら INFO である。

### G-23 【低】AI の 1 日 300 回の枠を、複数の IP で使い切れる（L-01g）

- 事実: 日次の上限は全利用者の合計（DB の `role=user` の行数）で、IP の上限は 30 回/時である。1 つの IP でも約 10 時間、使う IP を増やすほど短い時間で、300 回に届く。届くと全利用者に 503 `chat_daily_limit` が返り、`/api/chat/status` も `available: false` になる。試験はしていない（コードと設計からの判定）。
- 影響: 費用は守られる（設計書の試算で最大約 54 円/日）が、AI アシスタントがその日は使えなくなる。サイト本体の購入には影響しない。
- 対応: **対応しない**。費用を守る設計を優先し、枠の枯渇による停止は許容する（本人の承認済み）。担当が挙げた代案は、1 IP あたりの日次回数（例: 50 回/日）を別に数えることである。

## 4. 指摘にしないもの

次の 8 点は、確認したが指摘には含めなかった。見送った根拠を後から追えるように、ここに記録しておく。

- AI アシスタントには 1 回の相談あたり 10 往復の上限があるが、Cookie を削除するか reset を呼べば新しい相談になり、往復数は 0 から数え直しになる。設計書にも「新しい相談で往復数は 0 に戻る」とあり、これは設計どおりの動作である。実際に歯止めになっているのは、IP ごとに 1 時間 30 回、全体で 1 日 300 回までという制限である。意見: 設計仕様書 P2 追補 d の 4.4 と DS-DEC-96 に「往復数は会話の長さの目安」と書くと、設計書と実装が合う、と思う。
- 会話ログの 90 日削除は手動の SQL で行っていて、削除ジョブはコードにない。設計（8.5、DS-DEC-100）で「P2 では削除ジョブを作らず、手動の SQL で消す」と決めており、既知の割り切りである。保存している内容はマスク済みで、会員や注文とは結びつかない。
- 管理画面は公開サイトと同じオリジンにあり、CSP に `script-src` がない（既知の G-05）。`asid` には `Path=/admin` を指定しているが、同じオリジンの JS から `/admin/api/*` へ fetch すれば、この Cookie はそのまま送られる。公開側に XSS が 1 件でも出ると、ログイン中の管理者の権限で更新を実行されうる。現状は、React の既定のエスケープと、`dangerouslySetInnerHTML` の使用が 0 件であることで XSS を防いでいる。意見: 管理画面だけ別のホスト名にする案は大がかりなので、まず CSP の導入を優先する。
- ゲスト用の注文照会では、注文番号と注文時のメールアドレスが一致すれば、ログインなしで氏名・住所・電話番号を閲覧できる。会員の注文も同様である。注文番号は 32^8 通りの乱数で、照会には 1 IP あたり 1 時間 100 回の回数制限がある。本人の判断により、今のままとする。
- 他人のメールアドレスで 5 回ログインに失敗すると、その会員を 15 分間ロックできる。これはロックの仕組みの性質で、設計の想定内である。
- BFF は `Content-Type` に関係なく本文を JSON として読むため、`text/plain` の本文も受け付ける。ただし、CSRF トークンの確認（独自ヘッダ）は必須で、Origin の検査と SameSite の設定も加わる。実害は確認していない。
- Dependabot の #5（Mako 1.4.1、GHSA-5639-2j2p-m4mx）は、このアプリには影響しない。脆弱性が起きるのは Windows だけで、公開環境は Linux で動いている。Mako は alembic の推移的依存で、利用者が入力するテンプレート名もない。それでも、PR-C で 1.4.3 に更新した（757cb62。修正版は 1.4.2 以上）。
- 会員の同時セッション 10 件の上限は、並列でログインすると超えることがある（9 件ある状態で 3 本同時にログインすると、12 件になる）。会員の行のロックで直列にしていないためで、G-16 より前からある問題である。管理者側は `staff` の `FOR UPDATE` で直列にしている。今回は直さず、次の対応候補とする。
