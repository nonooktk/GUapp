0. この手引きの使い方

コードレビュー当日に、VS Code を見ながら説明するための手引きです。レビュワーが機能を 1 つ指定したら、その機能の章を開き、書いてある順に IDE でコードをたどります。各章の停留所には path:行 が出ているので、そのまま ⌘P に貼って開けます。

この章の数字と状態は 2026-10-03 時点です。基準にしたコミットは、ページ上部の「対象コミット」です。

レビューの進め方と、この手引きの章の並び

レビューは次の ①〜⑥ の順に進みます。各章（1〜10 章）の小見出しも、同じ順に並んでいます。

順レビューでやること各章の小見出し
①レビュワーが機能を 1 つ指定するこの章の「機能 × テストの早見表」と「指定のされ方の言い換え表」で章を選ぶ。各章の冒頭は「指定のされ方と 30 秒版」
②指定された機能を Frontend のコードから説明し、リクエスト先のバックエンドを示すまで② 画面からバックエンドへ
③対象のエンドポイントが、バックエンドでどう処理するか③ バックエンドの処理（エラーの分岐つき）
④response として戻ってきたところから、Frontend に表示されるまで④ 応答から表示まで
⑤対象の機能について、テストの仕様を 1 つ選び、そのテストコードが何を確認しているか⑤ テスト 1 本の説明
⑥テストの条件がテスト仕様書どおりか、レビュワーと突き合わせる⑥ 仕様書との突き合わせ。最後に「詰まりそうな質問」

当日は次の順に動きます。

  1. 指定を聞く。
  2. この章の早見表か言い換え表で、章を開く。
  3. 章の冒頭の「30 秒版」を言う。
  4. 順路（②③④）を IDE でたどる。停留所の「コピー」で path:行 を取り、⌘P に貼る。
  5. テスト 1 本（⑤）を説明する。
  6. 突き合わせ表（⑥）をレビュワーと見て、判定が緑（一致）でない行は、事実だけを言う。

詰まりそうな質問

1〜2分CSRF はどう防いでいますか

Double Submit Cookie という方式です。csrf_token の Cookie と、X-CSRF-Token ヘッダーの値が一致するときだけ、BFF が通します。他のサイトから送られたリクエストは、Cookie は付いても、ヘッダーに同じ値を載せられません。判定は isCsrfValid（定数時間の比較）で、テストは csrf-validation.test.ts と bff.cart-route.test.ts です。

追撃: cart_token は HttpOnly なのに、csrf_token は JavaScript で読めるのはなぜですか

csrf_token は、JavaScript が読んでヘッダーに載せる必要があるためです。cart_token は、BFF が Cookie からヘッダーに載せ替えるので、JavaScript に読ませる必要がありません。

1〜2分同じ商品を同時に 2 回押したらどうなりますか

追加は INSERT … ON DUPLICATE KEY UPDATE の 1 文で、(cart_id, variant_id) の UNIQUE 制約もあるので、行は 1 つで数量が 2 になります。確認は IT-011-01（asyncio.gather で同時に 2 回送る）です。画面側も、処理中はボタンを無効にします。ただし IT-011-01 は CI ではスキップされます。

1〜2分在庫が 1 しかないのに、2 点をカートに入れられるのはなぜですか

設計仕様書 DS-PRC-011 で、数量が在庫を超えていても追加は許すと決めています。在庫の確定は、注文確定時の引当で行うためです。カートの応答は明細ごとに stock_statusを返します。1 つでも insufficient があると「レジへ進む」を無効にします。確認は IT-011-02 の別関数 test_it_011_02_quantity_over_stock_is_allowed_with_insufficient です。

1〜2分他の人のカートの商品を、消したり変えたりできませんか

できません。リポジトリの get_item が、明細の ID に加えて自分のカートの ID も条件にして探すので、他人の item_id を送っても見つからず、404 not_found になります。他人のものと存在しないものは区別しません。BFF は [id] を正の整数に限っています。確認は IT-012-01 ですが、結合テストは CI でスキップされます。この点は先に伝えておいたほうがよいです。

Cookie の cart_token（43 文字の乱数）です。BFF が X-Cart-Token ヘッダーに載せ替えて FastAPI に渡し、FastAPI がトークンからカートを特定します。3 章の順路 B に発行の流れがあります。

1〜2分送料無料の閾値は、どこで決まっていますか。画面と API で食い違いませんか

system_settings の free_shipping_threshold で決まり、金額の判定は API の calc_shipping_fee が行います。画面は、API の応答の閾値と送料をそのまま表示するだけで、計算はしません。cart/page.tsx の予備値 4,990 円は、公開設定の取得に失敗したときの表示だけに使います（既知の弱点 C5）。

0〜1分なぜ prepare を別の API にしているのですか

詰まりそうな質問

1〜2分他人の注文番号を総当たりで試されたら、どうなりますか

当てるには、注文番号とメールアドレスの両方が必要です。注文番号の後ろの 8 文字は 32 種類から選ぶので、約 1.1 兆通り（32 の 8 乗）あります。番号が無い場合もメールが違う場合も、同じ 404 を返すので、注文があるかどうかも分かりません。1 つの IP からの照会は、1 時間に 100 回までです（404 になった呼び出しも数えます）。

追撃: その制限は、公開環境でも掛かっていますか

掛かり方に穴が 2 つあります。1 つ目は、公開環境では IP の設定漏れで、利用者全員が 1 つの枠を共有する見込みであることです（コード解説書 9 章 A1。直す予定ですが、まだ直していません）。2 つ目は、ワーカーごとに数えるので、最大 200 回まで通ることです（同 B1。設計書 9.4 に既知として書いてあり、P2 で対応します）。

1〜2分レート制限の IP は、どう決めていますか

IP を決めるのは BFF の resolveClientIp で、FastAPI にはその値を X-Forwarded-For に載せて渡します。利用者が付けたヘッダーは使いません。信頼するプロキシの段数（TRUSTED_PROXY_HOPS）が 0 のときは接続元だけを使い、1 以上のときは App Service が付ける X-Client-IP を使います。それが無ければ、X-Forwarded-For を右から数えた位置の値です。FastAPI は、受け取った値の先頭を IP として数えます。

ST 実施記録の 2026-09-24 の指摘で、問題が見つかりました。利用者の X-Forwarded-For をそのまま転送していたため、ヘッダーを付けるだけで制限を逃れられたのです。これは PR #27 で今の形に直しました。公開環境で段数の設定が抜けている点は、上の A1 のとおりです。

0〜1分完了画面をリロードしたり、別のタブで開いたりしたらどうなりますか

同じタブでリロードしたときは、sessionStorage の guapp.lastOrder が残っているので、同じ注文がまた表示されます。タブを閉じたあとや、別のタブで URL を開いたときは、保存した注文が無いので、照会フォームが出ます（注文番号は URL から入り、メールアドレスは自分で入力します）。URL の注文番号が保存済みの注文の番号と違うときも、保存済みの注文は見せず、照会フォームを出します。別タブから照会する流れは、手動テストの ST-F025-01 で確認しました（2026-09-18）。
