1. V字モデルとは何か

ソフトウェアを作る手順を「左側で決めて、右側で確かめる」の V 字に並べた考え方です。左に降りるほど話が細かくなり（何がしたいか → どう作るか）、右に登るほど確認の範囲が広くなります（部品が動くか → 全体で目的が達成できるか）。

肝心なのは左右が同じ高さで対になっていることです。設計書の 1 行に対してテストの 1 行があり、要求の 1 行に対して受け入れテストの 1 行がある。だから「何を確かめれば完成と言えるか」が作り始める前に決まります。

たとえるなら

家を建てるとき、「南向きのリビングが欲しい」（要求）→「窓は 2 間幅」（要件）→「サッシの型番と取付図」（設計）と細かくしていき、完成後は「サッシが図面どおり付いたか」→「窓が 2 間幅か」→「リビングは南向きで明るいか」と逆順に確かめます。V 字はこれをソフトウェアでやる形式です。

2. この演習で作っているもの

題材は GU の EC サイトです。講義の前提として、画面は Next.js、裏側の処理は FastAPI、データベースは Azure 上の MySQL と決まっています。要件定義では機能を 39 件に分け、必須（Must）18 件・推奨（Should）17 件・任意（Could）4 件に優先度を付けました。

全部を一度に作ると、途中で設計が変わったときに手戻りが大きくなります。そこで実装を 4 つのフェーズに分け、最初の P1 は「会員登録なしで商品を選び、カートに入れ、注文を確定するまで」の一本道だけを通すことにしました。今回の 2 冊はこの P1 を対象に書かれています。

フェーズゴールP1 に含めた機能（8 件＋部分 2 件）
P1 購買最小構成ゲストが 6 画面を通って注文を確定できる。ローカル PC で動く商品一覧・共通メニュー・商品詳細・カート・注文手続き・注文確定・ゲスト購入・画面共通の状態表示。加えて「在庫切れの明示」と「税率・送料のデータ」
P2 Must 完遂＋新機能必須 18 件と Lv3 新機能の AI アシスタントが Azure 上で動く—
P3 / P4推奨・任意機能（返品、クーポン、レコメンドなど）—
なぜ一本道から

P1 の途中で「注文テーブルに会員の列がない」「注文時の単価を保存していない」と気づくと、テーブルの作り直しになります。そのため設計仕様書は、実装は P1 に絞りつつ、DB と API の土台だけは必須 18 件すべてを見据えて先に固める二層構造にしています。

3. 設計仕様書の各章の意図

設計仕様書は 10 章あります。それぞれが「誰の、どんな疑問に答える章か」で読むと構造がつかめます。

1 章 システム構成 — 「部品はどう並んでいるか」

ブラウザ、Next.js、FastAPI、MySQL、外部サービス（決済の Stripe、メール、Claude API）の配置図です。重要な決定は 1 つで、ブラウザは Next.js にしか話しかけられないようにしたことです。FastAPI と DB は Next.js の後ろに隠れます。

たとえるなら

レストランの「ホール（Next.js）」「厨房（FastAPI）」「倉庫（MySQL）」です。お客様はホール係にだけ注文し、厨房や倉庫には直接入れません。文書ではホール係を BFF（Backend for Frontend）と呼んでいます。

2 章 技術スタック — 「何を使って作るか」

言語・フレームワーク・DB の版を表にしています。版を書くのは、半年後に別の人が同じ環境を再現できるようにするためです。「MySQL 8.0 は 2026 年 4 月にサポートが終わるので 8.4 にする」のように、選んだ理由も添えています。

3 章 UML — 「動きを絵で共有する」

4 種類の図が入っています。文章だと読み手ごとに解釈がぶれる「誰が何をするか」「処理はどの順で、どこで分岐するか」を、決まった記法の図で固定するのが目的です。

ユースケース図

登場人物（ゲスト・会員・運用担当・サポート担当）と、それぞれができること。P1 はゲストの購買だけを太枠で示す。

アクティビティ図

購入の流れを分岐付きで描いたフローチャート。「在庫がない」「決済が失敗」「同じ注文が 2 回来た」の 3 つの分岐が入っている。

シーケンス図

注文確定ボタンを押した瞬間から完了画面までに、ブラウザ・Next.js・FastAPI・DB・決済がどの順で会話するかを時間軸で描いた図。

クラス図

データの種類（商品・カート・注文・注文明細…）とその関係。「注文 1 件に明細が複数」のような 1 対多を線で表す。

4 章 API 設計 — 「厨房への注文票の書式」

API は、ホール係（Next.js）が厨房（FastAPI）に出す注文票の書式です。「商品一覧を出して」「カートにこれを追加」「注文を確定」など、P1 では 11 種類。それぞれに DS-API-001 のような番号が付いています。

4.4 の「処理仕様」は、注文確定（DS-PRC-014-1）のように失敗すると実害が出る処理の手順書です。4.5 は、失敗したときに何番のエラーをどう返すかの規則で、今回の改訂で「判定の順序」を明記しました（7 章で解説）。

5 章 DB 設計 — 「倉庫の棚割り」

データを入れる表（テーブル）を 26 個定義し、P1 ではそのうち 13 個を作ります。1 つの表は Excel のシート 1 枚のようなもので、列（項目）と制約（同じ値を 2 つ入れられない、など）を決めます。

なぜ「注文時の単価」を別に保存するのか

商品の値段は後で変わります。注文明細に「その時の単価」をコピーして持たないと、値下げした翌日に過去の注文金額まで変わってしまう。これは要求仕様（REQ-FR-505）から一直線につながっている設計です。

6 章 画面設計 — 「6 枚の画面の骨組み」

ホーム → 商品一覧 → 商品詳細 → カート → 注文手続き → 注文確認・完了 の 6 画面を、文字で描いたワイヤーフレームで示しています。スマホ幅（375px）でも操作できることを前提にし、商品詳細ではスクロール中も「カートに入れる」が押せる固定バーを置きます。

7 章 セキュリティ設計 — 「盗まれない・壊されない仕組み」

講義の必須項目 6 つ（BFF、CORS、Swagger 非表示、型定義、金額はサーバーで計算、DB ファイアウォール）を「設計」と「どう検証するか」の 2 列で表にしています。検証列があるのは、セキュリティは「やったつもり」になりやすいからです。

8 章 インフラ・デプロイ — 「どこで動かすか」

Azure のどのサービスを使うか、環境変数（秘密の鍵や接続先）をどこに置くか、ローカル PC ではどう起動するかの手順です。P1 はローカル環境のみで、Azure への配置は Week7 の話です。

9 章 設計判断 — 「なぜそう決めたか」の台帳

DS-DEC-01 から 32 まで、決めたこと・理由・採らなかった代替案を並べています。後で「なぜこうなっている？」と聞かれたときに、当時の判断を再現できるための章です。設計書で最も価値が長持ちする部分といえます。

10 章 トレーサビリティ表 — 「要求からテストまでの糸」

要求 ID → 機能 ID → 設計 ID → テスト ID を 1 行に並べた表です。ある要求がどの設計で実現され、どのテストで確かめられるかを追えます。逆に、どの要求にもつながらない設計は「余計な作り込み」として見つかります。

4. 設計の要所 3 つ

設計仕様書の中で、EC サイトとして「ここが崩れるとお金と信用に直結する」箇所を 3 つ取り上げます。

4.1 注文確定の 8 手順（DS-PRC-014-1）

  1. 冪等キーで注文を仮登録確認画面を開いた時点で発行した「この注文専用の合言葉」を注文表に書き込む。同じ合言葉が既にあれば、その注文を返して終わる（ボタン 2 度押し対策）。
  2. カートを「注文済み」に切り替える切り替えに失敗したら、別のタブで先に注文されている。409 エラー。
  3. 在庫を 1 明細ずつ引き当てる「在庫が数量以上あるときだけ減らす」という条件付き更新。1 つでも失敗したら全部取り消して在庫切れを返す。
  4. 金額をサーバーで再計算し、画面の金額と照合1 円でも違えば取り消し。ブラウザ側の金額はいくらでも書き換えられるので、信用しない。
  5. 決済を呼ぶP1 は本物の決済ではなく「スタブ」（常に OK を返す代役。テスト用に NG にも切り替え可）。
  6. OK なら確定を書き込む注文を「受付済」に、支払い記録・明細（注文時の単価と商品名）・監査ログを保存して確定。NG なら「決済失敗」を残してから在庫とカートを元に戻す。
  7. 確認メールを送るP1 はログ出力のみ。メールが失敗しても注文は成立させ、失敗は監査ログに残す。
  8. 注文番号を発行するGU-260917-7K3M9Q2X の形式。見間違えやすい I・O・0・1 は使わない。万一同じ番号が出たら 1 回だけ作り直す。

4.2 二重注文を防ぐ 4 層（DS-DEC-07）

「同じ注文が 2 件できる」事故を、1 つの仕掛けではなく 4 つの層で防ぎます。1 層目だけでは、まったく同時に届いた 2 リクエストや、2 つのタブから別々に確定した場合を防げないためです。

層仕掛け防げる事故フェーズ
1冪等キーを注文表で「重複禁止」にする同じ画面でボタンを何度も押す・通信の再送P1
2注文作成と同時にカートを「注文済み」に切り替える2 つのタブから別々に確定するP1
3注文 1 件に決済セッション 1 つ決済画面の二重生成P2
4決済会社からの通知 ID を重複禁止にする同じ通知が 2 回届いて 2 回処理されるP2

4.3 金額の計算規則（DS-PRC-021・DS-DEC-31）

金額は必ず整数の円で計算し、小数（浮動小数点）を使いません。コンピュータの小数は 0.1 を正確に表せず、積み上げると 1 円ずれるためです。商品価格は税込で持ち、「うち消費税」は表示用に逆算します。

小計 ＝ 単価 × 数量 の合計 …… 1,990 × 2 ＝ 3,980
送料 ＝ 小計が 4,990 以上なら 0、未満なら 550 …… 550
合計 ＝ 小計 ＋ 送料 …… 4,530
うち消費税 ＝ 合計 × 10 ÷ 110 を円未満切り捨て …… 4,530 × 10 ÷ 110 ＝ 411.8 → 411

税率は設定表に文字列 "0.10" で保存し、計算時は「10（%）」の整数に直してから 合計 × 10 ÷ 110 と割り算します。これで小数を一度も使わずに済みます。

5. テスト設計書の各章の意図

テスト設計書は「V 字の右側」を 1 冊にまとめたものです。各テストには設計側の ID が必ず書いてあり、何を確かめるテストなのかが設計書から逆引きできます。

0〜1 章 位置づけと方針 — 「4 段の高さと合格ライン」

レベル確かめることやり方件数
AT 受け入れ利用者の目的が達成できるか。「会員登録なしで買えた」人がブラウザで操作。PC 幅と 375px の 2 回8
ST システム機能ごと・非機能（レイアウト、セキュリティ）画面操作と HTTP クライアント。一部自動化39
IT 結合FastAPI と MySQL を本当につないだときの挙動。同時実行や異常系pytest から実 DB へ。全件自動31
UT 単体関数・部品 1 つが仕様どおりかpytest（API）・Vitest（画面）。全件自動、CI で毎回実行22

合格ラインは、AT-01（ゲスト購入）に合格し、IT・UT が全件緑、375px 幅で一本道が通ることです。自動テストは 1 件でも失敗すると main ブランチへの取り込みを止めます。

2〜5 章 テスト項目 — 「1 行 1 テスト、区分付き」

すべての行に「正常・異常・境界」の区分があります。素人目には「動くかどうか」が全部に見えますが、テスト設計では 3 つを意図的に分けます。

正常 仕様どおりの入力で期待どおりになる

いちばん基本。ここが通らなければ何も始まらない。

異常 仕様外の入力・状態で、設計した戻し方になる

「エラーにならない」ではなく「設計どおりのエラーになる」を確かめる。

境界 上限・下限の前後で挙動が切り替わる

バグは境目に集まる。「10 は通って 11 は弾く」を両側で確かめる。

6 章 テストデータ — 「わざと壊れた商品を用意する」

普通の商品 30 点に加え、テストのために「在庫 0 のサイズ」「在庫 1 のサイズ」「非公開の商品」「全サイズ在庫 0 の商品」を初期データに混ぜます。異常系や競合のテストは、こういう意図的なデータがないと再現できません。

7〜10 章 実施計画・申し送り・トレーサビリティ

いつ・どのレベルを実施するか、P2 に持ち越すテスト、講義の観点との対応表、そして設計書 10 章と同じトレーサビリティ表（今度はテスト ID が埋まった版）です。

6. テストの実例で見る「正常・異常・境界」

4 レベルから 1 件ずつ、読み方の例を挙げます。

読み方のコツ

テストの行を見たら、「対象」列の DS 番号で設計書を引き、その設計が守ろうとしている要求まで戻ってみてください。要求 → 設計 → テストの 3 点が 1 本の線になっていれば、そのテストは「意味のあるテスト」です。線がつながらないテストは、設計書かテスト設計書のどちらかに穴があります。

7. 実装直前に直した 6 点

2026-09-17 に、実装に入る前の点検で単体テスト 23 件を設計書と突き合わせました。その結果、文書どうしの矛盾 3 件と、テストでは確かめられない書き方 3 件が見つかり、設計仕様書を draft-v3、テスト設計書を draft-v2 に改訂しました。着手前に見つかれば直すのは文章だけで済みます。実装後なら、コードとテストと文書の 3 か所を直すことになります。

#見つかったこと直し方
A1「小数を使わない」と決めたのに、税率が 0.10 という小数で書かれていた税率は文字列で保存し、計算は「10%」の整数で 合計 × 10 ÷ 110 とする
A2「上限超過は 422 エラー」と書いてあるのに、エラー一覧に 422 がなかった。入力ミスの 400 との使い分けも不明確エラーの判定順序（認証 → 形 → 存在 → 業務規則 → DB の状態 → 回数 → その他）を定め、P2 以降の API にも使える規則として 4.5 を書き直した（DS-DEC-32）
A3画面の見本が「小計 5,970 円・送料 550 円」だった。5,970 円は送料無料ラインの 4,990 円以上なので、自分の規則と矛盾見本を「小計 3,980・送料 550・合計 4,530」に統一し、送料無料の判定は「小計」に対して行うと明記
B1「秘密の部品を画面側から読み込むとビルドが失敗する」は単体テストでは確かめられないCI（自動ビルド）のチェック項目へ移した
B2「375px 幅で固定バーが出る」は単体テストの環境に画面サイズの概念がなく確認不能単体テストは「選んだ色・サイズが固定バーに反映される」だけを見る。幅の確認は人が行う受け入れテストへ
C1〜3郵便番号・電話番号の形式、住所などの文字数上限、注文状態の英語コードが未定義正規表現・文字数・8 つの英語コードを設計書に追記

A2 で決めたエラーの判定順序

エラーの番号は「何が悪かったか」を機械にも人にも伝える言語です。同じ状況で 400 と 422 が混ざると、画面側の処理もテストも書けなくなります。そこで上から順に問いかけ、最初に当たった番号を返すと決めました。

正当な呼び出し元か 401/403→ 形は正しいか 400→ 対象は存在するか 404→ 業務の規則内か 422→ 今の DB 状態と両立するか 409→ 回数上限内か 429→ それ以外 500

覚え方は 2 つです。400 と 422：どんな状況でも常に不正（数量にマイナス）なら 400、形は正しいがこの店の規則で受けられない（数量 11 個）なら 422。422 と 409：DB を見ずに判定できれば 422、在庫のように今の状態次第なら 409。409 は時間が経てば成功しうるエラー、422 は入力を変えないと成功しないエラー、と言い換えられます。

8. 用語集

BFF（Backend for Frontend）
ブラウザからの窓口になるサーバー。ここでは Next.js が担い、裏の FastAPI をブラウザから隠す。
API
プログラム同士が話すための決まった書式。「商品一覧をください」「カートに追加」といった要求 1 つ 1 つに URL と形式がある。
冪等（べきとう）キー
同じ操作を何度繰り返しても結果が 1 回分になるようにするための合言葉。注文確定に必ず付ける。
スタブ
まだ本物をつなげない外部サービス（決済・メール）の代役。決まった返事を返すだけの簡易版。
条件付き UPDATE
「在庫が 2 個以上あるときだけ 2 個減らす」のように、条件を満たすときだけ書き換える DB 命令。同時アクセスでも在庫がマイナスにならない。
トランザクション
複数の DB 操作を「全部成功か、全部取り消し」のひとまとまりにする仕組み。注文確定の途中で失敗したら途中結果を残さない。
マイグレーション（Alembic）
テーブルの追加・変更の履歴を残し、別の PC でも同じ DB 構造を再現できるようにする道具。
seed
動作確認用の初期データ。商品 30 点や、テスト用の在庫 0 商品など。
CORS
ブラウザが「別のサイトからの呼び出し」を許すかどうかの規則。FastAPI は Next.js からの呼び出しだけを許す。
CSRF
利用者になりすまして勝手に操作させる攻撃。状態を変える操作には毎回トークン（合言葉）を要求して防ぐ。
Pydantic
FastAPI で入力の形（型・桁数・必須）を宣言的に検査する仕組み。SQL インジェクション対策の第一線。
CI（GitHub Actions）
コードを保存するたびに自動でテストとビルドを走らせる仕組み。人が忘れても毎回確かめる。
pytest / Vitest
自動テストの道具。pytest は Python（FastAPI 側）、Vitest は TypeScript（Next.js 側）。
P1〜P4
実装のフェーズ。P1 はゲスト購買の一本道、P2 で必須機能と AI アシスタント、P3・P4 で推奨・任意機能。
