0〜1分Q1 どんなアプリで、どこまでできていますか

返し方の骨子: GU の EC サイトを題材にした講義演習のデモで、ゲストが商品を探し、カートに入れ、注文を確定するところまでできています。要件の Must 18 件のうち、完了が 8、一部が 5、未着手が 5 です。会員登録と管理画面はまだ作っていません。自動テストは 528 件（api 300 のうち unit 200・integration 100、web 228）です。api の結合テスト 100 件は、いまは環境変数の漏れで CI ではスキップされていて、ローカルでは全件緑です（第 9 章の D3）。詳しい状況は第 8 章にあります。

根拠の場所: build_protected_router（API の一覧）、HomePage（入口の画面）。

追撃: 残りの 10 件を 10/31 までに終える根拠は何ですか（🟡 準備が要る）

返し: P2 を 4 回に分け、各回の頭で追補設計とテスト項目を先に作ってから実装する運用にしました（ADR-0001）。P2-b が 10/10、P2-c が 10/20、P2-d が 10/31 です。実績としては、実装プランを作った 9/17 から検収完了の 9/24 まで約 1 週間で、受け入れテスト 8 件とシステムテスト 40 件に合格しました。main への実装のマージは 9/18（PR #4〜#10）で、残りは検収と修正です。P2-a は 9/24 の設計から 9/25 の実装 3 PR まで進めました。

準備: ADR-0001 は、P2 の残りを P1 のおよそ 3 倍の量と見ている。P1 の約 1 週間を基準にすると約 3 週間分になり、9/29 から 10/31 までの約 4.5 週間に収まる、という計算になる（これは私の推測で、見積りとして文書には無い）。P2 の量が想定を超えたときに削る順番は未決で、ADR-0001 は別の ADR で決めるとしている。この点も聞かれたら「未決」と答える。

1〜2分Q2 構成はどうなっていますか。なぜ BFF を挟むのですか

返し方の骨子: ブラウザは Next.js の Route Handler（/api/*）だけを呼びます。FastAPI の URL と内部トークンをブラウザに出さないためです。FastAPI は X-Internal-Token が無いと 401 を返し、CORS の許可オリジンは BFF の 1 つだけです。認証 Cookie の検証や CSRF の検証も BFF に集めています。

根拠の場所: apiFetch、verify_internal_token、install_cors、build_protected_router、設計書 4.1。

追撃: Azure の api は公開されています。直接叩かれたらどうなりますか（🟡 準備が要る）

返し: api の App Service にはアクセス制限を設定していません。デプロイのスクリプトにその設定が無く、README にも api の health を直接 curl する手順があります。防御は内部トークンだけです。トークンは openssl rand -hex 32 で作った推測されない乱数で（02-settings.sh L72）、比較は一定時間で行い、期待値が未設定なら全リクエストを拒否します。/api/v1/health だけは死活監視のため対象外です。Swagger は本番で無効にしてあります。Week10 の閉域化で、VNet 統合とアクセス制限を入れる予定です。設計書は api にアクセス制限を掛けて web の送信 IP だけを許可する方針ですが、いまの公開環境では未設定です（第 9 章の D4）。ただし Azure 上の実際の設定は、CLI を使わない方針のため私は確認しておらず、スクリプトから読み取った範囲の話です。

準備: 設計書は、本編 1 章の表と DS-DEC-27 で「App Service のアクセス制限で BFF の送信 IP のみ許可」と書いている。スクリプトにはこの設定が無いので、設計と現状が食い違っている。聞かれる前に自分から「設計では入れる前提だが、公開環境ではまだ入れていない」と言えるようにする。api の URL に内部トークン無しで API を呼び、401 が返ることを 1 回見せられるとよい（私は未実行）。

2〜3分Q3 AI が書いたコードを、理解して説明できますか

返し方の骨子: コードのコメントに設計 ID（たとえば注文確定の手順番号）が付いていて、そこから設計書へたどれます。方式の判断、たとえば在庫を条件付き UPDATE にすることや、二重注文を複数の層で防ぐことは自分で決め、理由と代替案を DS-DEC と ADR に記録しました。

根拠の場所: orders.py の冒頭、設計書の DS-DEC の表、ADR の一覧。

追撃: _confirm の手順 3（金額照合）と手順 4（在庫確保）を入れ替えると、何が困りますか（🔴 今のままだと詰まる）

返し: 設計書 4.4 の手順 3 に理由が書いてあります。引当より前に照合するのは、金額が合わないときに在庫の行ロックを握らないため、です（draft-v3 までは引当が先で、結果は同じ）。設計書 L397-398。入れ替えても正しさは崩れません。どちらの失敗も同じトランザクションで ROLLBACK するので、在庫の戻し漏れは起きないからです。困るのはロックの時間です。

ここから先は、コードを読んだ上での私の推論である。順序を逆にすると、金額が合わない注文も、先に variants の行ロックを取ってから ROLLBACK することになる。同じ商品を同時に買う別の注文は、その間待たされる。金額不一致は価格改定の直後や改ざんで起きる経路で、その注文にロックを取らせなければ、同時購入への影響を小さくできる。もう一つの違いは、金額も在庫も不一致のときに返るエラーである。今は price_changed で、入れ替えると out_of_stock になる。テスト用の遅延フック（_maybe_test_delay）も、この 2 つの手順の間に置いてある。

準備: 設計書の 1 文を言えるようにしておく。設計書 3.2 の図（L154-157）と 3.3.1 の図（L193-195）、テスト設計書の ST-F014-02・03 の手順番号は、引当が先の旧順序のまま残っている。図を見せたときに食い違いを突かれたら、4.4 の文章とコードが新しい順序で、図は更新漏れだと答える。

3〜4分Q4 どこから読めばいいですか

返し方の骨子: 第 2 章のルートに沿って、注文確定を画面から DB まで縦に 1 本読むのがよいです。入口は確認画面の OrderConfirm、そこから BFF、FastAPI のルーター、サービス、リポジトリの順に下ります。

根拠の場所: OrderConfirm → createOrder → POST /api/orders → proxyOrderRequest → router.create_order → service.create_order → _confirm → reserve_stock。

追撃: _confirm が 110 行あります。なぜ分割しないのですか（🟢 事実で返せる）

返し: トランザクションの境界を 1 つの関数で見せるためです。分割すると commit と rollback の場所が散り、どこまでが 1 つのトランザクションかが読み取りにくくなります。コメントの番号（1〜6）を設計書 DS-PRC-014-1 の手順番号に対応させてあるので、設計書と並べて上から順に追えます。ただし、この関数に決済 NG の 2 段コミット（第 9 章の B2）もあり、大きさが弱点になっていることは第 9 章の C1 に挙げてあります。

準備: 不要。

4〜5分Q5 在庫の取り合いは、どう防いでいますか

返し方の骨子: 在庫の引当を条件付き UPDATE の 1 文にしています。UPDATE variants SET stock = stock - :q WHERE id = :id AND stock >= :q の形で、影響した行数が 0 なら在庫不足です。確認と減算が 1 文で原子的に行われ、同じ行を同時に狙った注文は DB の行ロックで順番に処理されるため、一方だけが成功します。最後の砦として、DB 側にも stock >= 0 の CHECK 制約を置いています。

根拠の場所: reserve_stock、_reserve_all、テスト IT-014-04（最後の 1 点を 2 つのカートが取り合う）。

追撃: 3 点のうち 2 点目だけ在庫切れなら、1 点目の引当は戻りますか（🟢 事実で返せる）

返し: 戻ります。_reserve_all は variant_id の昇順に全行を試し、0 行だった ID を集めて 409 out_of_stock を上げます。呼び出し元の _create_order がそれを受けて session.rollback() するので、注文の INSERT、カートの ordered 化、1 点目の引当が同じトランザクションの中で、まとめて取り消されます。昇順に引き当てるのは、複数のカートが同じ商品群を逆順に取り合うデッドロックを避けるためです（設計書 4.4 手順 4）。

準備: 不要。結合テスト IT-014-07（reserve_failure_rolls_back）が、先に引当した分も戻ることを確かめている。

5〜6分Q6 二重注文は、どう防いでいますか

返し方の骨子: コードに実在する 4 層で防いでいます。①画面の二重送信防止（確定ボタンを押すと処理中は無効にし、連続クリックでも送信は 1 回）。②冪等キー（orders.idempotency_key の UNIQUE 制約で、同じキーの注文は 2 件作れず、重複時は既存の注文を返す）。③カートの状態（注文と同じトランザクションで、カートを active から ordered へ条件付きで更新する。0 行なら 409）。④注文番号の UNIQUE 制約（衝突したら 1 回だけ再生成し、2 回目も衝突したら 500）。①は使い勝手のための層で、防御の本体は②と③です（設計書 4.4 の DS-PRC-036）。

設計書との違い: 設計書 7.4（DS-DEC-07）の 4 層は「冪等キー・カート状態・Stripe Session・event_id」で、後ろの 2 つは P2 の内容である（設計書 7.4）。P1 のコードで動いているのは、そのうち冪等キーとカート状態の 2 つに、画面の二重送信防止と注文番号の一意制約を加えた 4 層である。

根拠の場所: OrderConfirm の inflight、insert_pending_order（冪等キーと注文番号の衝突の処理）、mark_cart_ordered、_existing_order_result、テスト IT-014-02（同じキーで 20 並列 → 1 件）と IT-014-03（同じカートに 2 つのキー）。この 2 つは結合テストで、CI ではいまスキップされている（第 9 章の D3）。

追撃: 別タブで確認画面を開き直すと冪等キーが変わります。二重に注文できませんか（🟢 事実で返せる）

返し: できません。キーは prepare のときに FastAPI が発行し（new_idempotency_key）、web は sessionStorage に置きます（saveCheckoutSession）。sessionStorage はタブ単位なので、別タブでは別のキーになり、②の冪等キーでは防げません。防ぐのは③のカート状態です。1 件目がカートを ordered にすると、2 件目の条件付き UPDATE は 0 行になり、ROLLBACK して 409 already_ordered を返します（L198-200。1 件目の完了後に来たときは L351-355 で先に 409）。ほぼ同時に来たときは、注文の INSERT で InnoDB のデッドロック（1213）が起きることがあり、片方が 1 回だけやり直して、同じ 409 に着地します。

準備: 不要。層の呼び方は、コードの 4 層と設計書 7.4 の 4 層で違うことを一言添える。

6〜7分Q7 SQL インジェクション・CORS・Swagger は、どうなっていますか

返し方の骨子: SQL は SQLAlchemy のバインド変数で組み、入力は Pydantic で型を検証しています。LIKE のワイルドカードは autoescape に任せています。CORS は許可オリジンを 1 つに絞り、未設定や * のときは CORS 自体を付けません。Swagger は APP_ENV=production のとき無効で、テストで確かめています。

根拠の場所: reserve_stock、build_match_condition、install_cors、Swagger の無効化、docs 無効のテスト。文字列で SQL を組む箇所は seed だけで、既知の表名に限っています。

追撃: CSP が無いなら、XSS で CSRF トークン（HttpOnly でない Cookie）を読まれませんか（🟡 準備が要る）

返し: 読めます。csrf_token は JS が読んでヘッダに載せる作りなので、HttpOnly を付けていません（buildCsrfTokenCookie）。ただし、同じオリジンで XSS が成立すれば、どの CSRF 対策も破られます。攻撃のコードが正規のページとして、正規のリクエストを送れるからです。本筋は XSS を入れないことです。React の既定のエスケープだけで描画し、dangerouslySetInnerHTML は使っていません（コンテンツのページにその旨のコメントがある）。コンテンツの本文はプレーンテキストだけです（DS-DEC-38）。カートのトークンの Cookie は HttpOnly です（buildSetCookie の既定）。CSP は Week8 で入れます。

準備: セキュリティヘッダーは、どの設定ファイルにも無い（第 9 章の B4）。CSP 以外の 3 種を先に入れるかどうかを決めておくと、この追撃への返しが「入れました」に変わる。

7〜8分Q8 テストと CI は、どうなっていますか

返し方の骨子: 自動テストは 528 件です（api 300 のうち unit 200・integration 100、web 228）。CI は api-test、web-test、deps-audit の 3 ジョブに、別ワークフローの gitleaks が加わります。api-test は MySQL 8.4 のサービスを立ててマイグレーションを流しますが、結合テスト 100 件は環境変数の漏れで、CI ではスキップされています（CI の結果は 200 passed, 100 skipped）。ローカルでは全件緑です。当日までに直す予定です（第 9 章の D3）。web-test は Vitest のあと、server-only の違反でビルドが失敗することと、ビルド成果物に内部トークンが無いことを検査します。

根拠の場所: api-test、conftest.py の ENV_KEY、web-test、secrets-scan.yml。

追撃: カバレッジは何％ですか（🔴 今のままだと詰まる）

返し: 未計測です。pytest-cov も vitest の coverage も設定していません。テストは設計書のテスト ID（UT・IT・ST・AT）から逆算して書いていて、網羅は要件からテストへの対応表で見ています（設計書の 10 章トレーサビリティ表）。

準備: 未計測の理由を問われたときの補足として、計測は依存の追加になるため承認待ちにしてある（第 9 章の D2）。1 回だけ計測して数字を持っておくと、答えが「未計測」から「〇％で、未達は〇〇」に変わる。

8〜9分Q9 ブランチ戦略は、どうなっていますか

返し方の骨子: main へは PR 経由だけで入れます。作業ブランチは feat/・fix/・docs/ の接頭辞で切り、PR は #1 から #30 まで出しました。P1 実装プランでは squash merge を方針にしています。Dependabot が週次で、npm・uv・GitHub Actions の更新 PR を出します。

根拠の場所: 実装プランのブランチ方針、dependabot.yml、PR テンプレート。

追撃: main は保護していますか。CI が落ちてもマージできませんか（🔴 今のままだと詰まる）

返し: 事実として、必須のステータスチェックは gitleaks だけです。api-test と web-test が落ちても、今はマージできます。一方で、PR 必須、ブランチの削除禁止、強制 push 禁止は入っています（gh api repos/nonooktk/GUapp/rulesets の読み取りで確認）。承認 0 人は個人開発として妥当だと考えています。必須チェックに api-test と web-test を足す予定です。

準備: P1 実装プランは「main は CI 緑のみマージ」と書いているが、実際の設定は gitleaks だけで、文書と設定が食い違っている。必須チェックに足すと、この追撃は「保護している」と答えられる（第 9 章の D1）。足す名前は api-test (pytest) と web-test (vitest + build)。

9〜10分Q10 決済やメールは、どうなっていますか

返し方の骨子: どちらも P1 ではスタブです。アダプタ（Protocol）の後ろに置いてあり、注文確定のサービスは中身を知らずに呼びます。決済スタブは環境変数で ok か ng を固定して返し、未設定なら ok です。メールは送信せずに、ファイルへ書き出します。P2-c で、Stripe テストモードと Azure Communication Services のメールに替える予定です。

根拠の場所: StubPaymentAdapter、OutboxMailAdapter、PAYMENT_STUB_RESULT、テスト IT-014-06（決済 NG で在庫とカートが戻る）。

追撃: Stripe は Webhook で後から結果が届きます。今の authorize() で足りますか（🟢 事実で返せる）

返し: 足りません。authorize は同期で ok か ng を返す形なので、P2-c で「Checkout Session を作る」と「Webhook で確定する」の 2 段に変えます。準備として済んでいるのは、注文の stripe_session_id 列（UNIQUE）と expires_at 列、pending_payment の状態、PaymentProvider の stripe です（models/order.py L87-88）。stripe_events 表（event_id の UNIQUE）、Webhook の受け口、決済待ちの期限切れ処理は、まだありません。

準備: 不要。詳しい流れは第 8 章 8.3にある。

突っ込みQ11 レート制限は、複数ワーカーで効きますか

返し方の骨子: 効きません。制限器がワーカーごとのメモリなので、api が 2 ワーカーの Azure では、同じ IP でも 1 時間に最大 200 回まで通ります。設計書 9.4 で既知の点で、P2 で共有ストアに置き換えます。また、公開環境では送信元 IP の判定に使う設定が漏れていて、全員が同じ枠になっています。これは自分で見つけていて、当日までに直す予定です（第 9 章の A1）。

根拠の場所: SlidingWindowRateLimiter、config.sh L51（--workers 2）、設計書 9.4。

追撃: 今すぐ MySQL の表で数えればよいのでは（🟡 準備が要る）

返し: 優先度の判断です。前例として ADR-0003 があります。検索 API のレート制限を後回しにしたときの代替案 B は、既存の制限器の流用でしたが、プロセス内メモリのため共有ストアへの置き換えが別に要る、という理由で不採用にしました。今回も同じ考え方です。公開は 10/09 までのデモで（config.sh L48）、入口は HTTP Basic 認証で守っています（ADR-0004）。加えて、講義共用の MySQL は接続の上限が 171 で（P2 追補a の 9.2 #4）、api は 2 ワーカーで最大 20 接続（プール 5、オーバーフロー 5）を使っています。リクエストごとの書き込みをこの共用サーバーに足すことは、避けたい負担です。

準備: ADR-0003 の見送りの理由と、ADR-0004 の「Basic 認証がかかっている間に限る」という前提を、開いて示せるようにしておく（ADR-0003）。ADR-0003 の代替案 B とここでの提案（表で数える）は完全には同じではなく、前例として使えるのは「置き場所の設計を含むため後回しにした」という判断の型までである。共用 MySQL の負担についての最後の一文は、私の意見である。

突っ込みQ12 自分で分かっている弱点は、何ですか

返し方の骨子: 自分から出します。第 9 章に 16 件の一覧があります。優先して直すのは 4 つで、公開環境でレート制限が全員共通の枠になっていること（A1）、結合テスト 100 件が CI でスキップされていること（D3）、main の必須チェックにテストが入っていないこと（D1）、lint を CI で回していないこと（C4）です。設計で受け入れているものとして、決済 NG の 2 段コミット（B2）、レート制限のワーカーごとの集計（B1）、決済とメールのスタブ（B5）があります。

根拠の場所: 第 9 章の一覧、決済 NG の 2 段。

追撃: 決済 NG のあとに在庫が戻らなかったら、どう気づきますか（🔴 今のままだと詰まる）

返し: 事実として、検知する仕組みは今はありません。決済 NG のときは、1 段目で監査ログに order.payment_failed が残ります（AUDIT_PAYMENT_FAILED）。ただし、この記録は 1 段目のコミットで書かれるため、2 段目が走ったかどうかは監査ログでは分かりません。2 段目が走ったかは、カートの状態で見分けます。payment_failed の注文なのに、カートが ordered のままなら戻し損ねです。これを探す SQL を第 9 章の 9.6に書きました。回収は P2 の決済待ちの期限切れ処理で行い、アラートは Week9 で入れる予定です。

準備: 9.6 の SQL は SQLite で構文と結果を確かめただけで、MySQL の実データでは試していない。ローカルの MySQL に決済 NG の注文を作って、1 回実行しておく。その実行を済ませれば、この追撃は 🟡 に下がる。監査ログ側から決済 NG の注文番号を拾うなら、SELECT target_id FROM audit_logs WHERE action = 'order.payment_failed' で取り、orders と carts に突き合わせる。

11.1 なぜこの形か（5 項目）

質問の奥にある「なぜそう作ったか」に答えるための整理である。設計書の DS-DEC に根拠があるものは番号を添えた。無いものは、無いと書いた。

判断選んだ形と理由別の案と、選ばなかった理由根拠
BFF を挟む ブラウザに FastAPI の URL と内部トークンを渡さないため。認証 Cookie と CSRF の検証、応答の整形を 1 か所に集められる。Stripe の Webhook も BFF で受けて FastAPI に転送するので、閉域化しても届く。 ブラウザから FastAPI を直接呼ぶ案。FastAPI の URL と CORS を公開側に出すことになる。DS-DEC-06 の次善策の欄は空で、比較の記録は無い（意見: 上の理由が主な違いだと思う）。 DS-DEC-05・06・13。apiFetch、verify_internal_token
_confirm を 1 関数にする commit と rollback の場所を 1 か所で読めるようにするため。コメントの番号を DS-PRC-014-1 の手順番号に対応させ、設計書と並べて追える。 手順ごとの関数に分ける案。commit と rollback が複数の関数に散る。分割の是非は、弱点として第 9 章の C1 に置いた。 DS-DEC 番号なし（実装上の判断）。_confirm、設計書 4.4
在庫は条件付き UPDATE 確認と減算が 1 文で原子的になり、影響行数で成否が分かる。設計書の理由は「ロック不要で一方だけ成功」。 悲観ロック（SELECT … FOR UPDATE）。先に行を読んでロックし、在庫を確認してから更新する 2 手になり、ロックの保持が長くなる。ただし複数明細で行を取り合うときの順序管理（variant_id 昇順）は、どちらの方式でも要る。悲観ロックを退けた意味ではなく、DS-DEC-08 の次善策として残してある。ロックの保持時間の違いは一般論で、設計書の記載は「ロック不要で一方だけ成功」だけである。 DS-DEC-08。reserve_stock、variants の CHECK（stock >= 0）
冪等キーを prepare で発行する 確認画面を出した時点でキーが決まり、同じ画面からの再送（連打・通信のやり直し）が同じキーになる。そのため、再送には既存の注文を返せる。キーはサーバー（FastAPI）が乱数で作る。 確定の送信時にクライアントが作る案は、設計書に比較の記録が無い。設計書の DS-DEC-07 が明記するのは「冪等キー単体では同時到着と 2 タブを防げない」ことで、層 2 を足した理由になっている。キーを prepare で出す理由の文章は設計書に無く、上の説明は図（3.3.1）と実装からの推論である。 DS-DEC-07。new_idempotency_key、prepare
匿名カートを乱数のトークンで識別する ゲストでも DB にカートを持て、将来の会員カートとのマージや変動通知を実装しやすい。トークンは 32 バイト乱数の base64url で、FastAPI が発行し、Cookie には HttpOnly で 90 日置く。トークンを知らない人は他人のカートに届かない。 localStorage にカートを置く案（DS-DEC-10 の次善策）。サーバーがカートの内容を知れないので、マージや通知に向かない（この説明は意見。設計書の理由は「マージ・変動通知が実装しやすい」）。 DS-DEC-09・10・12。new_cart_token、resolve_cart、buildCartTokenCookie
