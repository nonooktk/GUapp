8.3 スタブの所在と、Stripe に替えるときの設計

決済とメールは、P1 では本物に接続せず、アダプタの後ろにスタブを置いている。アダプタは Protocol（型だけの取り決め）で、注文確定のサービスは中身を知らずに呼ぶ。テストでは Depends の差し替えで決済 NG を注入できる。

決済は PaymentAdapter と StubPaymentAdapter である。環境変数 PAYMENT_STUB_RESULT が ok か ng ならその値を、未設定なら ok を返す。メールは OutboxMailAdapter で、送信せずに apps/api/.mail-outbox/<注文番号>.txt へ本文を書き出す。本文は render_order_confirmation が作り、宛先・氏名・住所・電話をそのまま含む。このディレクトリは gitignore 済みだが、平文であることは第 9 章の B5 に挙げてある。

Stripe に替えるときの流れは、設計仕様書の 3.3.2（DS-PRC-014-2）に書いてある。P1 との違いは、決済の結果が同期では返らず、Webhook で後から届く点だけである。

  1. 注文の作成と在庫の引当までは P1 と同じ。注文は pending_payment のまま残す。
  2. 決済アダプタが Checkout Session（metadata に注文番号、期限 30 分）を作り、その URL を返す。ブラウザは Stripe の決済ページへ移る。
  3. 支払いが済むと、Stripe が BFF の /api/webhooks/stripe に生ボディと署名を送る。BFF は生ボディを変えずに FastAPI の /api/v1/internal/stripe-events へ転送する。
  4. FastAPI が署名を検証し、stripe_events に event_id（UNIQUE）を INSERT する。重複なら 200 を返して何もしない。新規なら注文を accepted に更新し、payments に記録する。
  5. Webhook が届かない場合の保険として、完了画面が GET /api/v1/checkout/sessions/{id} で Session の状態を照会し、支払い済みなら受付済にする。

モデルには、この流れの準備が一部だけ入っている。

項目状態場所
orders.stripe_session_id（UNIQUE・NULL 可）と expires_atありmodels/order.py L87-88
注文状態 pending_payment と、決済元 stripeありOrderStatus、PaymentProvider
stripe_events 表（event_id の UNIQUE。DS-TBL-17）無いmodels にも migration にも未作成
決済アダプタの形要変更authorize は同期で ok／ng を返す形。上の流れは「Session を作る」と「結果を確定する」の 2 段になる
決済待ちの期限切れ処理（30 分、5 分ごとの実行。DS-DEC-26・28）無い設計のみ。P2 で実装する

意見: 「差し替え口はあるのか」と聞かれたら、アダプタの境界と、列・状態の準備が済んでいることまでを答える。Webhook の受け口と stripe_events 表は未実装なので、「差し替えだけで済む」とは言わないほうがよいと思う。実装フェーズ計画 3 章は、スタブと Stripe テストモードの実装が同じアダプタ IF を満たすので差し替えで済む、と書いている。だが上の表のとおり、Webhook 方式では authorize の形が変わる。
