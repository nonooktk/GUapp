4. 横断的な仕組み

建物に例えると、商品閲覧やカートといった機能は個別の部屋で、この章で扱う仕組みは玄関の鍵、非常口、防犯カメラ、消火設備にあたります。どの部屋にも共通してかかっているため、部屋の中身（各機能のコード）を読んでも見えてきません。

正確には、認証、入力検査、エラー形式、ログ、二重注文の防止、在庫の整合など、複数の機能をまたいで守る規則を実装している箇所です。各節は「何を防ぐか」「どこに実装したか」「どう動くか」「どのテストが守っているか」の順に書きます。レビューで画面に出すときは、各節の参照リンクからコードを開いてください。

秘密をブラウザに出さない：名前の検査、server-only、CI の 2 重チェック

防ぎたいのは、INTERNAL_TOKEN などサーバーだけが知るべき値が、ブラウザに配る JavaScript に混ざることです。Next.js は名前が NEXT_PUBLIC_ で始まる環境変数をビルド時にブラウザ向けの JavaScript へ埋め込みます。付いていない変数はサーバー側でしか読めません。このため、名前の付け間違いと、クライアント側のコードからサーバー専用モジュールを import してしまう間違いの 2 つを、別々の仕組みで止めています。

名前を検査する

NEXT_PUBLIC_ で始まり、名前に TOKEN・SECRET・PASSWORD・DATABASE_URL・API_KEY のいずれかを含む変数があれば拒否する。

環境変数を読む入口を 1 つにする

getEnv() が初回に validateEnv(process.env) を通し、結果をキャッシュする。必須の 3 つ（API_BASE_URL・INTERNAL_TOKEN・IMAGE_BASE_URL）が欠けると例外。

秘密を触るモジュールに server-only を付ける

lib/server/ 配下の 8 ファイルの先頭に import "server-only" がある。クライアントコンポーネントから import するとビルドが失敗する。

CI で、防御が効いていることを毎回確かめる

わざと違反するファイルを作ってビルドを走らせ、失敗しなければ CI を赤にする。続けて、ビルド成果物 .next/static にダミーのトークン値が含まれないことを全文検索する。

実装の見どころは、判定を純粋関数に分けている点です。validateEnv は process.env を直接読まず、引数で受け取ります。server-only も付いていないため、Vitest から直接呼べます。一方、実際に process.env を渡す getEnv は server-only を付けた側に置いています。検証はプロセスの起動時ではなく getEnv の初回呼び出し時に走ります（ファイル内のコメントは「起動時拒否」と書くが、実装は遅延実行）。

CI 側の 2 つの検査は server-only ガードと .next/static の全文検索です。ガードは app/ci-server-only-check/page.tsx を一時的に作り、"use client" のままサーバー専用の @/lib/server/env を import させます。ビルドが成功したら「ガードが壊れている」として失敗させ、失敗しても原因が server-only でなければやはり失敗させます。フォルダ名を _ で始めるとNext.js がルートから除外して検査にならないため、先頭に _ を付けない名前にしてある、とコメントに理由があります。

対応テストは UT-WEB-05（tests/ut-web-05.env-validation.test.ts。NEXT_PUBLIC_INTERNAL_TOKEN を含む環境が EnvValidationError で拒否される）です。UT-WEB-06（server-only）は、テスト設計書で CI へ移管されており、上の CI ステップが担当します。.next/static の検索はテスト設計書の ST-SEC-09 を先に自動化したものです。

内部トークン：BFF 以外からは FastAPI に入れない

FastAPI の URL を知った人が BFF を飛ばして直接叩けば、CSRF 検証や Basic 認証を迂回できてしまいます。FastAPI は X-Internal-Token ヘッダの値が環境変数 INTERNAL_TOKEN と一致するリクエストだけを受け付けます。

実装は verify_internal_token です。期待値が空、またはヘッダが無いときは 401 unauthorized を返します。設定を忘れたときに素通しにならず、全拒否に倒れる作りです。値の比較には hmac.compare_digest を使い、比較にかかる時間から値を推測されないようにしています。

この検証を /api/v1 配下の全ルーターに掛けているのは build_protected_router の 1 行（main.py の L50-66）です。個別のルートに書くのではなくルーター単位で付けるので、新しいルートを足しても付け忘れが起きません。死活監視の /api/v1/health だけは、保護ルーターの外に health.router をそのまま登録して対象外にしています。Web 側では apiFetch が全リクエストにこのヘッダを付けます。

security.py には INTERNAL_TOKEN_EXEMPT_PATHS（対象外パスの集合）が定義されていますが、コード中から参照されていません。対象外になっているのは、health.router を保護ルーターとは別に登録しているためです。定数は説明用に残っている状態です。

確かめているテストは UT-SEC-02（トークンの欠落・不一致で 401、INTERNAL_TOKEN 未設定なら全拒否、health は対象外）と、実 DB を使う IT-060-01 です。公開環境の確認記録（docs/05_検収/公開環境_確認記録_20260925.md）にも、トークン無しで /api/v1/products を直接叩くと 401 になった記録があります。

CORS と Swagger 非表示：本番で API の仕様を見せない

対象は 2 つあります。他サイト上のスクリプトがブラウザ経由で FastAPI を呼ぶことと、本番で API の仕様書（/docs・/redoc・/openapi.json）が誰にでも見えることです。

install_cors は環境変数 CORS_ALLOW_ORIGIN の 1 オリジンだけを許可します。未設定または * のときはミドルウェアを付けません。つまり、設定を誤るとどこからも許可されない側に倒れます。許可するヘッダは Content-Type と X-Internal-Token、メソッドは GET・POST・PATCH・DELETE・OPTIONS です。

Swagger の非表示は create_app の L22-27にあります。APP_ENV=production のときだけ、docs_url・redoc_url・openapi_url を None にして FastAPI を作ります。ルートが無くなるので、3 つのパスは 404 {"code":"not_found"} を返します。この形はエラー応答の共通ハンドラで揃えています（エラー応答の形）。

BFF から FastAPI への呼び出しはサーバー同士の通信で、ブラウザの CORS は関係しません。この設定が実際に効くのは、他サイトのスクリプトが FastAPI を直接呼ぼうとした場合に限られます。内部トークンと合わせた多層防御の 1 枚、という位置づけだと思います。

検証は tests/unit/test_ut_cors.py（許可外オリジンにはヘッダが付かない、ワイルドカードと空なら CORS 無効）、IT-CORS-01（プリフライト）、test_ut_app_production_docs_disabled（本番モードで 3 パスが 404）、テスト設計書の ST-SEC-02 です。公開環境では、許可外オリジンの OPTIONS が許可ヘッダ無しで拒否されたこと、3 パスが 404 になったことを 2026-09-25 に確認しています。

CSRF：Double Submit Cookie で、他サイトからの状態変更を止める

狙われるのは、ブラウザが Cookie を自動で付けて送る性質です。この性質を悪用し、他サイトのページからカート変更や注文確定を勝手に送らせる攻撃（CSRF）に対して、ここでは「Double Submit Cookie」方式を使います。同じ値を Cookie とヘッダの両方に載せさせ、一致したときだけ受け付けます。他サイトは Cookie を送らせられても、値を読み取れないため、一致するヘッダを作れません。

ブラウザが Cookie を確認する

document.cookie に csrf_token が無ければ、先に GET /api/cart を呼んで発行させる。

BFF が発行する

Cookie が無い（または形が不正な）ときだけ、32 バイトの乱数を base64url（43 文字）にして Set-Cookie する。

状態変更でヘッダに載せる

POST・PATCH・DELETE では Cookie の値を X-CSRF-Token ヘッダに載せて送る。

各 Route Handler の先頭で検証する

Cookie とヘッダが両方あり、形が正しく、一致するときだけ通す。不一致は 403 {"code":"forbidden"} を返し、FastAPI へは到達させない。

判定の中身は isCsrfValid です。まず isCsrfTokenShape で「英数字と -・_ の 43 文字」を確認し、その後、1 文字ずつ XOR を積み上げる比較で一致を見ます。先頭の不一致で早く返さないので、応答時間から 1 文字ずつ当てられません。

検証を呼んでいるルートは 5 種類で、いずれも関数の先頭で const denied = verifyCsrf(request); if (denied) return denied; の形です。カート追加（POST /api/cart/items）、数量変更・削除（PATCH・DELETE）、金額計算（POST /api/checkout/prepare）、注文確定（POST /api/orders）、注文照会（POST /api/orders/[orderNumber]/lookup）です。GET は検証しません。トークンの発行を担うのは GET /api/cart で、カート取得の応答に Set-Cookie が付く副作用があります。

FastAPI 側には CSRF の検証がありません（apps/api/app 配下に csrf を含むコードは無い）。CSRF はブラウザが相手の攻撃なので、ブラウザと直接話す BFF だけで検証する設計です。FastAPI は内部トークンで守っています。

守っているテストは tests/csrf-validation.test.ts（一致で通過、欠落・不一致・形の不正で拒否）、tests/bff.cart-route.test.ts、IT-BFF-02（tests/it-bff-01-02.orders-route.test.ts。CSRF が無ければ 403 で、FastAPI を呼ばない）です。

Cookie の属性：カートトークンと CSRF トークンで付け方を変える

Cookie で問題になるのは、スクリプトによる盗み読みと、http での平文送信です。Cookie 文字列を組み立てる処理は buildSetCookie の 1 か所に集めています。

Cookie用途HttpOnlySameSiteSecure寿命
cart_token匿名カートの識別付くLax本番のみ90 日
csrf_tokenCSRF の照合用付かないLax本番のみ90 日

カート用は buildCartTokenCookie、CSRF 用は buildCsrfTokenCookie です。CSRF 用だけ HttpOnly を付けないのは、ブラウザの JavaScript が値を読んで X-CSRF-Token に載せる必要があるからです。Secure は APP_ENV=production のときだけ付きます。ローカルの http では Secure 付きの Cookie がブラウザに保存されないためです。値に使える文字は英数字と .・_・- に限り、改行などを含めてヘッダを書き換える注入を防いでいます。

カートのトークン自体は FastAPI が発行し（secrets.token_urlsafe(32)）、BFF が応答を見て Cookie を更新します。Cookie とトークンが異なるときだけ Set-Cookie を付ける実装です。

属性を確かめるのは ST-SEC-07（tests/st-sec-07.cookie.test.ts。development では Secure が付かず、production では付く。値に改行を含むと例外）と tests/csrf-validation.test.ts（csrf_token に HttpOnly が無い）です。公開環境でも、Set-Cookie に cart_token・csrf_token とも Secure が付くことを 2026-09-25 に確認しています。

利用者 IP の扱い：ブラウザが付けた X-Forwarded-For は転送しない

問題になるのは、ヘッダを 1 行付けるだけでレート制限（注文照会の 100 回/時/IP）を回避されること、他人の IP を名指しして 429 を出させることです。ブラウザから来た X-Forwarded-For は利用者が自由に書けます。Azure App Service のフロントエンドはこのヘッダに追記する動作なので、公開環境でも利用者が先頭に偽の IP を置けます。

BFF が IP を 1 つに決める

受信ヘッダと環境変数 TRUSTED_PROXY_HOPS を resolveClientIp に渡す。

信頼できる送信元だけを使う

hops が 1 以上のときだけ、まず X-Client-IP（App Service のフロントエンドが付ける値）、次に X-Forwarded-For を右から hops 番目で採る。どちらも無い、または hops が 0 なら、接続元（既定は 127.0.0.1）。

決めた IP を単一の値として付け直す

利用者が送ってきたヘッダは転送せず、決めた IP だけを X-Forwarded-For に載せて FastAPI を呼ぶ。

FastAPI が受け取って数える

client_ip は X-Forwarded-For の先頭を採る。内部トークン付きの呼び出し（＝BFF）だけが届くので、この値を信用している。

hops の意味は「信頼できるプロキシが何段あるか」です。XFF は左が元の利用者、右へ向かってプロキシが追記した順に並びます。右から hops 番目を採れば、信頼できるプロキシ自身が書いた値だけを使えます。stripPort は IP:ポート 形式のポートを落とし、isIpLike が IP らしくない値（空文字、unknown、巨大な文字列）を弾きます。環境変数の検証では、TRUSTED_PROXY_HOPS は 0 以上の整数だけを許し、未設定は 0 です（env-validation.ts の L71-76）。

設計仕様書 P1 draft-v3 の環境変数の表（8.2 の TRUSTED_PROXY_HOPS の行）は、App Service 配下では 1 にすると定めています。ところが公開用のデプロイスクリプト（02-settings.sh の L88-121）が投入する設定は、api が 7 つ、web が 7 つで、どちらにも TRUSTED_PROXY_HOPS がありません。リポジトリ全体を検索しても、この名前を設定している箇所はコードと .env.example の空欄だけです。コード上は hops=0 となり、公開環境では全利用者が 127.0.0.1 として数えられます。推測ですが、注文照会の 100 回/時の枠を全員で共有している状態です。実際のヘッダの挙動までは本書では確認していません。第 9 章の A1 で扱います。

IP の判定を守るのは tests/st-sec-xff.client-ip.test.ts（hops=0 では偽の XFF・X-Client-IP を無視して 127.0.0.1、hops=1 なら末尾、hops=2 なら右から 2 番目、要素数より大きければフォールバック）と、IT-BFF-01（利用者が付けた x-forwarded-for がそのまま出ないこと）です。

二重注文の防止：4 層で止める

起きてほしくないのは、連打、通信の再送、同じカートを 2 つのタブで確定するといった操作で、注文が 2 件できることです。1 か所だけの対策では、ボタン連打は止められても 2 タブは止められず、DB の一意制約だけでは異なるキーの同時送信を止められません。そこで性質の違う 4 つの防御を重ねています。

層仕組み止めるもの主な実装
1 画面確定操作中はボタンを無効にし、送信も 1 回に絞る連打・二重クリックinflight、submit
2 冪等キー確認画面の表示時に 1 回限りのキーを発行し、注文表のキー列を一意にする同じ操作の再送・同時 20 本new_idempotency_key、insert_pending_order
3 カートの状態カートを active から ordered へ、条件付き UPDATE の 1 文で切り替えるキーが異なる同じカートの確定（2 タブ）mark_cart_ordered
4 一意制約注文番号の列を一意にする。衝突したら 1 回だけ作り直す乱数の衝突による同じ番号の注文Order.order_number、insert_pending_order の再生成

層 1 は使い勝手のための防御で、設計書も「二重送信の防御は冪等キー側で行う」としています。OrderConfirm の inflightは useRef の同期フラグで、state の更新を待たずに立てます。React の state は再描画まで値が変わらないため、連続クリックが両方通ってしまうのを避けるためです。確認ダイアログも処理中は閉じられません。

層 2 の流れは次のとおりです。確認画面へ進むときに prepareCheckout が呼ばれ、サーバーが secrets.token_urlsafe(32)（43 文字）のキーを返します。確定時にそのキーを添えて送ると、insert_pending_order が注文を INSERT します。同じキーの注文が既にあれば一意制約違反となり、DuplicateIdempotencyKey に変換されます。呼び出し側の _create_order（L364-371）は既存の注文を読み直し、_existing_order_result で応答を作ります。既存の注文が別のカートのものなら 404、決済失敗の注文なら 409、それ以外は 200 でその注文を返します。他人のカートに紐づく注文を、キーが同じというだけで返さないための照合です。

層 3 は UPDATE carts SET status='ordered' WHERE id=? AND status='active' の 1 文です。影響行数が 0 なら、他の処理が先にカートを注文済みにしています。その場合は ROLLBACK して 409 already_ordered を返します。影響行数の判定なので、読んでから書くまでの間に割り込まれる隙がありません。

「別タブで開き直す」場合を追うと、層の分担が分かります。確認画面のフォーム値と冪等キーは sessionStorage に入っていて、これはタブごとに別です。新しいタブで注文手続きをやり直すと、確認画面へ進む時点で別のキーが発行されます。両方のタブで確定すると、キーが違うので層 2 の一意制約には当たらず、層 3 で後の側が 409 already_ordered になります。画面は routeOrderError の対応表に従い、既存の注文番号つきで完了画面へ送ります。なお、タブを複製した場合は sessionStorage が複製されると思うので、同じキーとなり層 2 で 200 が返る、という別の経路になります（この点はコードでは確認していない）。

もう 1 つ、同じカートに 2 本が同時に届くと、MySQL がデッドロックを検出して片方を打ち切ることがあります。注文の INSERT がカートの行に共有ロックを取り、続く UPDATE で互いに排他ロックを待ち合うためです。_create_order_with_deadlock_retry が、エラー番号 1213（デッドロック）と 1205（ロック待ちの超過）を 1 回だけやり直します。やり直した側は相手の COMMIT 後の状態を見るので、キーが異なれば 409、同じなら 200 に着地します。

設計仕様書 7.4（DS-DEC-07）の「4 層」は、冪等キーの一意制約、カート状態、Stripe Session 1 つ、Webhook の event_id の 4 つです。後ろの 2 つは Stripe を使う P2 の内容で、P1 のコードにはありません。この節は、実際にコードにある防御（画面、冪等キー、カート状態、注文番号の一意制約）を数えています。設計書と数え方が違う点は、レビューで聞かれたときのために押さえておくとよいと思います。

対応テストは IT-014-02（同じキーで 20 本を同時に送っても注文は 1 件）、IT-014-03（同じカートに 2 つのキーを同時に送ると 201 と 409 が 1 つずつ）、UT-014-01（注文番号の衝突は 1 回だけ再生成し、2 回目は 500）、UT-WEB-03（送信中は両ボタン無効で、連続 2 回クリックしても fetch は 1 回）です。scripts/mutation-check は、層 2（キーの UNIQUE）と層 3（Cart.status == CartStatus.active の条件）を 1 つずつ外して、該当テストが赤くなることを確かめるスクリプトです（第 6 章）。

在庫の確保：条件付き UPDATE の影響行数で判定する

売り越しとは、最後の 1 点を 2 人が同時に買って、在庫がマイナスになることです。「在庫を読む、足りていれば減らす」の 2 手に分けると、2 人が同時に「足りている」と判断してしまいます。そこで判定と減算を SQL の 1 文にまとめています。

実装は reserve_stock です。UPDATE variants SET stock = stock - :q WHERE id = :id AND stock >= :q を発行し、影響行数（0 か 1）を返します。InnoDB は UPDATE の対象行に排他ロックを掛けるため、同じ行への 2 本目はロックの解放を待ってから条件を評価し直します。1 本目で在庫が尽きていれば、2 本目は 0 行になります。

複数明細の注文では _reserve_all が呼び出します。variant_id の昇順に引き当てるのは、複数のカートが同じ商品群を逆の順に取り合うデッドロックを避けるためです。1 つでも 0 行なら、在庫切れの variant_id の一覧を付けて 409 out_of_stock を返し、そこまでの引き当てを含めてトランザクション全体を ROLLBACK します（L358-363）。variants.stock には CHECK (stock >= 0) の制約もあり（Variant）、コードの判定をすり抜けた場合でも DB が負の値を拒否します。

決済が NG だったときは、注文を payment_failed として COMMIT したあと、別のトランザクションで restore_stock と restore_cart_active により在庫とカートを戻します（L248-271）。失敗した注文の記録は残し、戻す処理は別に確定させる作りです。

在庫の確保を守るテストは UT-014-03・UT-014-04（数量が在庫以下なら 1 行、超えれば 0 行で在庫は変わらない。SQLite の in-memory）、IT-014-04（2 つのカートが最後の 1 点を争い、片方だけが成功。有効試行 30 回）、IT-014-06（決済 NG で在庫とカートが戻る）です。scripts/mutation-check は Variant.stock >= quantity の条件を外して、これらが赤くなることも確かめます。

エラー応答の形：1 か所で決め、画面側で文言に変える

漏らしたくないのは、FastAPI の既定エラー本文や例外メッセージ、SQL、接続文字列です。加えて、画面ごとにエラーの形がばらつくのも避けたい点です。設計仕様書 4.5（DS-DEC-32）が形を決めており、判定の順序は 認証・CSRF（401/403）、入力の形（400）、存在と所有（404）、業務規則（422）、DB の状態（409）、回数（429）、その他（500）です。

API 側は AppError を 1 系統だけ使います。ルーターに HTTPException を直接書かず、業務エラーは AppError(409, "out_of_stock", items=[...]) のように投げます。install_error_handlers が 4 つのハンドラを登録して、本文を揃えます。

例外応答実装
AppError指定の status と {code, ...詳細}_app_error_handler
Pydantic の入力検証エラー400 {code:"validation_error", fields:[{name, reason}]}。reason は required・format・too_long・out_of_range の 4 語validation_error_body、map_reason
Starlette の HTTPException（未定義ルートの 404、メソッド違いの 405 など）{code:"not_found"} など。405 は Allow ヘッダを保つ_http_exception_handler
その他の未捕捉例外500 固定文言。詳細はログのみ_unhandled_error_handler

map_reason には 1 つ工夫があります。文字列の最小長違反（string_too_short）で、入力が空または空白のみ（全角スペース含む）なら、利用者から見て「未入力」なので required にします。それ以外の最小長違反は out_of_range のままです。

BFF 側は、FastAPI の本文をそのまま流さず、sanitizeErrorBody を通します。通してよい詳細のキーは 許可リスト（fields・items・amounts・order_number・from・to・field・limit・message）に固定しています。FastAPI に接続できないときは UpstreamUnavailableError を投げ、BFF が 503 upstream_unavailable に変えます。

画面側は、コードを利用者向けの文言と戻し先に対応付けます。注文系は routeOrderError、カート系は cartErrorMessage、注文照会は lookupErrorMessage です。注文照会の 404 は、番号の不存在とメールの不一致を区別しない 1 つの文言にしています。存在する番号を推測させないためです。

エラー応答のテストは UT-SEC-02（500 は固定文言で、ログの接続文字列はマスクされる。reason の 4 語。空文字と空白のみは required）、UT-SEC-03（404・405 も {code} の形。本番の /docs の 404 も同形）、tests/bff.api-error-shape.test.ts、tests/order-errors.test.ts です。

ログとマスク：秘密のパターンを潰し、個人情報は書かない

ログに残したくないのは、接続文字列やトークン、メールアドレスです。ログは障害調査で多くの人が読み、外部に渡ることもあります。対策は 2 つで、書き出す直前に秘密のパターンを伏せ字にするフィルタと、そもそも個人情報をログに渡さない書き方です。

フィルタは SecretMaskFilter です。対象は Stripe 系のキー、scheme://user:pass@host の資格情報部分、Bearer トークン、X-Internal-Token ヘッダの値（パターンは _PATTERNS）、それに INTERNAL_TOKEN の実値です。実値は設定から受け取り、4 文字未満は誤マスクを避けるため対象にしません。setup_logging が全ハンドラ（uvicorn のロガーも含む）にこのフィルタを付け、create_app の L20 が INTERNAL_TOKEN の実値を渡します。

フィルタは record.args の構造を保ったまま中身だけを置換します。uvicorn のアクセスログは 5 要素のタプルを展開して整形するため、引数を 1 つの文字列に潰すとリクエストのたびにログの書き込みエラーになる、と実起動で確認した経緯がコメントに残っています。

個人情報のほうは、ログに書く箇所でメールをマスクします。mask_email は t***@example.com の形にする関数で、注文確定のログ（services/orders.py の L376-399）とメールアダプタが使います。配送先の氏名・住所・電話は、ログに渡していません。Web 側も、注文系の取り次ぎでは接続不可のときにパスだけを出し、本文を出力しない方針です（proxyOrderRequest）。

メールの送信はOutboxMailAdapterのファイル出力で、本番でも同じアダプタが使われます（get_mail_adapter はこれしか返さない）。注文確認メールの本文には配送先が入り、apps/api/.mail-outbox/ にファイルとして書かれます。このディレクトリは gitignore 済みで、デプロイ用 zip からも除外されます。

マスクのテストは UT-SEC-01（Stripe キー、接続文字列、Bearer、内部トークンのマスク。引数の構造の保持。全ハンドラへの取り付け）、test_ut_mail_mask_email、test_ut_mail_outbox_writes_file_and_log_is_masked です。

レート制限：注文照会だけ、プロセス内メモリで数える

狙われやすいのは、注文番号とメールアドレスの組を総当たりで試す注文照会です。注文番号は 8 文字のランダム値ですが、照会が無制限だと当てにいけるため、1 つの IP につき 1 時間 100 回までに絞っています。

数える処理は SlidingWindowRateLimiter の hit です。キー（IP）ごとに直近 3,600 秒の呼び出し時刻を deque に持ち、100 回に達していれば次に空く秒数を返します。lookup_rate_limit がそれを受けて 429 rate_limited と Retry-After ヘッダを返します。制限器はアプリに 1 つで、create_app で app.state に持たせています。注文照会のルートへは dependencies に依存関数として付けます。この制限をかけているのは注文照会だけです。検索 API の制限は ADR-0003（見送り）で、公開時は Basic 認証があることを理由に ADR-0004 でも見送りを維持しています。

カウンタはプロセスのメモリ上にあります。公開環境の api は uvicorn --workers 2（config.sh の L50-51）で起動するため、ワーカー（プロセス）ごとに別々に数えます。計算上は、1 つの IP が 1 時間に最大 200 回まで通りうる構成です（実際のリクエストの振り分けは未確認）。設計仕様書 P1 draft-v3 の申し送りにも「2 ワーカーでは共有ストアに置き換えること」とあり、設計上は既知で、コードは未対応です。第 9 章の B1 で扱います。

レート制限のテストは test_ut_rate_limit_100_ok_101_limited_with_retry_after（100 回目まで OK、101 回目は制限され Retry-After が付く）と、実 DB を使う IT-023-02 です。

設定と DB 接続：環境変数を型に落とし、接続数を絞れるようにする

設定漏れで意図しない動作をすることと、共用の講義サーバーに接続を使いすぎることが、ここでの心配事です。API の設定は Settings の 1 クラスに集め、get_settings がプロセスごとに 1 回だけ読みます（lru_cache）。APP_ENV は 3 つの値しか受け付けず、is_production・is_test の判定に使われます。既定値のない秘密（INTERNAL_TOKEN など）は空文字が既定で、空のままなら内部トークン検証が全拒否になり、CORS は無効になります。

DB エンジンは build_engine で作ります。接続プールは既定で 20 本と余裕 10 本ですが、DB_POOL_SIZE・DB_MAX_OVERFLOW で上書きできます。共用の講義サーバー向けにデプロイスクリプトは 5 と 5 を設定します（config.sh の L44-45）。ワーカーを増やすと、この本数がワーカーの数だけ掛かるためです。get_session は 1 リクエスト 1 セッションを渡す FastAPI の依存で、commit は各サービスが明示的に行います。

Settings には DB_SSL_CA_PATH と IMAGE_BASE_URL の項目がありますが、API のアプリコードのどこからも参照されていません（apps/api/app 配下の検索で確認）。公開環境の SSL は DATABASE_URL の ssl_ca クエリで効いており、デプロイスクリプトが DB_SSL_CA_PATH を設定していても実際の接続には使われません。IMAGE_BASE_URL を使うのは Web 側です。

接続数の設定を守るテストは UT-DBCONF-01（tests/unit/test_ut_dbconf_01_pool_config.py。既定は 20／10、環境変数で上書きできる）です。

画面と API の型：手で合わせていて、自動の検査はない

起きうる事故は、API の応答の形を変えたのに、画面側の型が古いまま気づかれないことです。両者を自動で合わせる仕組みは無く、手で合わせています。画面側の型は lib/types.ts に手で書かれており、FastAPI 側の Pydantic モデル（apps/api/app/schemas/）とは別々に管理されています。同じ形が両側にある例が、カートの明細です（TypeScript の CartItem と Python の CartLineOut。名前も違う）。注文確定の入力は OrderCreateBody と OrderCreateIn、応答は OrderResponse と OrderOut が対応します。

照合の手がかりは apps/api/openapi.json です。FastAPI が出力する API の契約で、コマンドで再出力するとファイルが更新されます（apps/api/README.md に手順）。lib/types.ts の冒頭コメントは「食い違いが見つかったらここを直す」と書きますが、突き合わせは人が行います。テストでもこのファイルは参照されておらず、更新を忘れても CI は落ちません。さらに、BFF は FastAPI の応答を実行時に検証せず as T でキャストするだけです（api.ts の L113）。

API の形を変える PR では、openapi.json の再出力と lib/types.ts の確認を手順に入れると、漏れを防げると思います。OpenAPI から型を生成する選択肢もありますが、依存の追加になるため、現状のコードからは判断できません。

依存と秘密の検査：Dependabot、gitleaks、pre-commit

対象は、脆弱性のある依存を使い続けることと、秘密がリポジトリに入ることの 2 つです。前者は Dependabot と CI の監査、後者は gitleaks（CI）と detect-secrets（コミット前）で、それぞれ二重にしています。

検査実装動く場面失敗したとき
依存の更新dependabot.yml。npm・uv・GitHub Actions を週次で確認し、minor と patch はまとめて 1 本の PR にする週 1 回（GitHub 側）PR が立つ（2026-09-29 時点で #16〜#20 の 5 本が未マージ）
既知の脆弱性の監査ci.yml の deps-audit。pip-audit --strict と pnpm audit --audit-level highPR と main への pushジョブに continue-on-error: true が付き、失敗しても PR は止まらない（非ブロック）
秘密のスキャン（履歴全体）secrets-scan.yml の gitleaks。fetch-depth: 0 で履歴を全部走査PR と main への pushマージ必須のチェックに指定されている（第 6 章）
秘密のスキャン（コミット前）pre-commit の detect-secrets。許容済みは .secrets.baseline手元の git commitコミットが止まる
.env 系のコミット拒否forbid-dotenv（forbid_dotenv.py）。.env.example だけ許可手元の git commitコミットが止まる

ダミー値の許容は、行の末尾に pragma: allowlist secret または gitleaks:allow を書く方式です（.gitleaks.toml）。コード中の ci-only-* のような値がこの印を付けて残されており、印の付いた行を git grep で一覧できます。

pre-commit は、各自が pre-commit install を実行して初めて効きます。サーバー側では強制されないため、実行していない環境からの push は止まりません。サーバー側の最終防御は gitleaks です。

テスト専用フックを本番で読み込まない

紛れ込むと困るのは、同時実行のテストで使う「処理中の数を数える」機構と「意図的な待ち時間」、およびテスト用 URL（/_test/metrics・/_test/reset）です。待ち時間が本番で有効になると、注文確定が意図せず遅くなります。

仕組みは 3 重です。1 つ目は、create_app の if settings.is_test: の中でだけ testing_hooks とテスト用ルーターを import し、登録することです。トップレベルで import しないので、本番では読み込まれません。2 つ目は、testing_hooks.py 自体が APP_ENV=test 以外では全関数が何もしない作りであることです。3 つ目は、使う側（_maybe_test_delay、create_order）も is_test の内側で遅延 import することです。

対応テストは 4 つです。test_ut_hooks_noop_when_not_test（本番モードで何もしない）、test_ut_test_routes_absent_outside_test_env（development と production で /_test/* が 404）、test_ut_hooks_not_imported_by_production_path（別プロセスで app.main を import し、testing_hooks が sys.modules に無いことを確認）、test_ut_test_routes_present_in_test_env（test モードでは動く）。すべて tests/unit/test_ut_app_production_docs_and_hooks.py にあります。
