5. データモデル

お店の帳簿に例えると、商品台帳（何をいくらで売るか）、買い物かごの控え（お客さんが今何を入れているか）、注文伝票の綴り（いつ誰にいくらで売ったか）が別々のノートになっています。注文伝票には、売った時点の商品名と単価をその場で書き写します。あとで台帳の値段を書き換えても、過去の伝票が変わっては困るからです。

正確には、MySQL 8.4 に 13 の表があり、各表を SQLAlchemy 2.0 のモデルクラス（apps/api/app/models/）で定義し、Alembic のマイグレーション 2 本（12 表＋1 表）で作ります。この章では、表の一覧、表どうしのつながり、状態を持つ列の値、マイグレーション、初期データ（seed）の順に説明します。

全表に共通の作り

13 表はどれも同じ土台を使っています。主キーは id BIGINT AUTO_INCREMENT（IdMixin）、created_at と updated_at は UTC の DATETIME で、DB の now() が自動で入ります（TimestampMixin）。MySQL の DATETIME はタイムゾーンを持たないため、コード中は「UTC の naive 日時」として扱い、応答に出すときに UTC を付けます（build_order_response の ordered_at）。画面では JST に変換して表示します。

テーブルオプションは MYSQL_TABLE_ARGS で、文字コードが utf8mb4、照合順序が utf8mb4_0900_ai_ci、エンジンが InnoDB です。制約や索引の名前は NAMING_CONVENTION で規則化してあり、uq_orders_order_number、fk_orders_cart_id_carts のように「種類_表名_列名」で決まります。名前が決まっていると、マイグレーションの自動生成と衝突せず、エラー文から違反した制約を特定できます。

金額は整数の円で持ちます（products.price_incl_tax は税込）。税率だけは "0.10" という文字列で、system_settings と orders.tax_rate_at_order の両方が同じ表現です。API の中で Decimal に変えて計算します（tax_rate_basis_points）。

一意制約・CHECK・索引

二重登録や不正な値を、アプリのコードだけに頼らず DB が最後に止める作りです。とくに次の 6 つは、他の章で説明した防御の土台になっています。

制約対象支えている仕組み
一意orders.idempotency_key同じキーでの二重注文の検出（第 4 章の層 2）
一意orders.order_number注文番号の重複防止。衝突したら 1 回だけ再生成（層 4）
一意carts.anonymous_token同じトークンで active カートが 2 つできるのを防ぐ。注文済みカートはトークンを NULL にして枠を空ける（detach_token）
一意（複合）cart_items (cart_id, variant_id)同じバリエーションの再追加を「数量の加算」にする

その他の一意制約は categories.slug、variants.sku、contents.slug、system_settings.key、orders.stripe_session_id、product_categories (product_id, category_id) です。索引は、外部キーの列、products.published、orders.status、audit_logs.at（90 日で消す処理を P2 で作る予定）に付いています。contents だけ、一覧の絞り込みに使う (kind, publish_from) の複合索引を持ちます（Content）。

contents には「公開かどうか」の列がなく、publish_from と publish_to（どちらも UTC の naive 日時）だけで公開期間を表します。判定は is_within_publish_window にあり、期間外のコンテンツの詳細を開くと、存在しないときと同じ 404 になります。

状態を持つ列：注文とカート

状態の列は、DB の ENUM 型ではなく文字列列に値を保存し（native_enum=False、長さ 20）、Python 側の StrEnum で値を制限します。この選択の理由はコードに書かれていません。値を増やすときに DB の型を変えずに済む利点があると思います（推測）。

orders.status は 8 値（OrderStatus）で、許される遷移は TRANSITIONS に集めてあります。assert_transition が表に無い遷移を 409 invalid_transition にします。

今の状態進める先意味
pending_paymentaccepted、payment_failed決済待ち。決済の結果で分かれる
acceptedpreparing、cancelled受付済み
preparingshipped出荷準備中
shippeddelivered、pickup_expired出荷済み
delivered・pickup_expired・cancelled・payment_failedなし終端。返品受付は P2 以降

P1 のコードで実際に状態を進めているのは、注文確定の中の 2 か所だけです（pending_payment から accepted、または payment_failed。L215-216・L249-250）。preparing 以降へ進める処理（管理画面や配送連携）は P1 にありません。遷移表と assert_transition は用意されていて、単体テスト UT-014-05 が全 8 状態を網羅して検証しています。

carts.status は active（買い物中）、ordered（注文済み）、merged（会員統合。P1 では未使用）の 3 値です。実際に動く遷移は 2 つあり、注文確定の途中で mark_cart_ordered が active → ordered にし、決済が NG だったときだけ restore_cart_active が ordered → active に戻します。注文済みのカートのトークンで再びカートを開くと、旧カートからトークンを外して新しい active カートを作ります（resolve_cart）。これが、注文後の「買い物を続ける」で新しい空のカートに追加できる理由です。

マイグレーション：2 本で 13 表を作る

マイグレーションは Alembic で管理します。env.py は非同期エンジンで動き、接続先は設定の DATABASE_URL から取ります。alembic.ini に URL を書かないのは、秘匿値をファイルに置かないためです。compare_type=True で列の型の差分も検出します。

ファイル何をするか戻し方
0001_p1_initial.pyP1 の 12 表と、UNIQUE・CHECK・索引・外部キーをまとめて作る。リビジョン ID は 6659ce6c5164（先頭のリビジョン）downgrade が依存の逆順で全表を drop（alembic downgrade base）
371a338f4624_p2a_contents.pycontents 表と (kind, publish_from) の複合索引を作る。down_revision は 6659ce6c5164alembic downgrade -1（DROP TABLE contents のみ）

2 本は down_revision でつながっており、ファイル名の 0001_ はリビジョン ID ではありません。0001_p1_initial.py の downgrade は、autogenerate が出す drop_index を手で取り除いてあります。MySQL は外部キーが使っている索引を単独では消せず（error 1553）、drop_table が索引も一緒に落とすためです。

CI の api-test は、テスト前に空の MySQL に対して alembic upgrade head を実行します。テスト設計書の同時実行テストの条件には「create_all は使わない」があり、マイグレーションに一意制約が欠けていればテストで検知できるようにしています。手元の実行手順は第 7 章にあります。

seed：初期データを入れる

初期データの投入は Alembic とは別で、seed.py が担当します（uv run python -m app.seed）。スキーマは先に alembic upgrade head で作っておく前提で、seed は DDL を発行しません。

実行の安全策は 3 つです。1 つ目に、既定では products に 1 行でもあれば何もしません（データ保護側に倒す）。2 つ目に、投入し直す --reset は対象の DB 名を出して確認を求め、--yes で省略できます（_amain）。3 つ目に、SQL に表名を埋め込む箇所は許可リスト方式です。TRUNCATE_ORDER は子から親の順に並べ、assert で P1 の 12 表と一致することをモジュールの読み込み時に確かめます。count_rows は ALL_TABLES に無い名前を ValueError で拒否します。TRUNCATE は truncate_all_tables が FOREIGN_KEY_CHECKS=0 で囲って実行し、finally で必ず 1 に戻します。

投入する中身は seed_data.py に、DB に依存しない定数として置かれています。_insert_all が、カテゴリ（親から子）、商品と画像とカテゴリ割当、バリエーション、設定、コンテンツの順に入れます。

在庫の乱数は種を固定しているため、何度 seed しても同じ値になります（STOCK_RANDOM_SEED）。固定在庫の商品はテストの目印です。バリエーション GU-029-BK-M の在庫は 0（V-STOCK0）、GU-027-NV-M は 1（V-STOCK1。同時注文の競合用）、商品 28（P-ALL0）は 6 バリエーションすべて 0、商品 30（P-UNPUB）は非公開です。乱数は毎回消費してから固定値で上書きするので、固定在庫を足しても他の SKU の在庫は変わりません。商品 31（4,990 円のライトジャケット）は、送料無料の境界（4,990 円で送料 0、4,980 円で 550 円）を単品で作るために後から足しました。

コンテンツの掲載期間は、固定日付ではなく seed の実行時刻からの日数で決めます。たとえばお知らせ news-002 は実行の 7 日前から 30 日後まで、特集 feature-001 は 1 日前から無期限です。固定日付だと、演習を続けるうちに掲載期間外になって画面に出なくなる事故が起きるためです（_insert_all の contents 部分）。裏返すと、時間がたつと news-002 のように期限つきのものは自然に非表示になります。

seed には個人情報を入れていません。特定商取引法と企業情報のページは、架空の事業者名「サンプルアパレル株式会社」、架空の住所・電話番号（03-0000-0000）で書かれ、本文にも「講義演習用のデモ」と明記してあります。会員と注文の seed は P1 にはありません。
