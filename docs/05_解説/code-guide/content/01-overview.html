1. 全体像

店に例えると、お客さんが見る売り場が画面で、売り場の脇にある受付カウンターが BFF です。注文の受付や在庫の出し入れはカウンターの奥のバックヤード（FastAPI）だけが行い、商品と注文の記録は倉庫（MySQL）に置きます。お客さんはバックヤードに入れず、必ず受付を通ります。

正確には、ブラウザが話す相手は Next.js だけです。Next.js は画面の描画（app/ の各ページ）と、ブラウザ向けの窓口（BFF。app/api/ の Route Handler）の両方を持ちます。BFF は Cookie と CSRF トークンを確かめたうえで、内部トークンを付けて FastAPI を呼びます。金額計算・在庫引当・注文確定といった業務ルールは FastAPI に集め、DB へのアクセスは SQLAlchemy（非同期）が担います。

事実: 画面（Server Component）が商品一覧などを読むときは、BFF を通らずに lib/server/catalog.ts などから FastAPI を直接呼びます。BFF を通るのは、ブラウザ側の JavaScript が呼ぶ経路（カート操作・注文・検索サジェスト・「もっと見る」）だけです。設計仕様書 4.3 の表に「Server Component から直接 FastAPI を呼ぶ場合は BFF を経由しなくてよい」と注記があります。

フォルダ地図

API 側は「入口（routers）→ 業務ルール（services）→ DB 操作（repositories）→ 表の定義（models）」の 4 段です。web 側は、ページ、BFF、部品、サーバー専用の関数、ブラウザ専用の関数、どちらでも使える純粋関数に分かれます。

api（apps/api/app）

フォルダ・ファイル役割代表例
routers/ URL と入出力だけを書く。業務判定はしない。ステータスコードの切り替え（201／200）はここ routers/orders.py::create_order
services/ 業務ルール。在庫・上限・金額・注文確定の手順。トランザクションの commit と rollback もここ services/orders.py::_confirm
repositories/ SQL を書く場所。SELECT と条件付き UPDATE を関数にする。業務判断はしない repositories/orders.py::reserve_stock
models/ 表の定義（SQLAlchemy の ORM クラス）。全表に id・created_at・updated_at がある models/order.py::Order
schemas/ リクエストとレスポンスの型（Pydantic）。入力は「形」だけ検証し、業務規則は書かない schemas/order.py::OrderCreateIn
core/ 設定・DB 接続・エラー統一・内部トークンと CORS・ログのマスク・レート制限 core/errors.py::AppError
adapters/ 外部サービスの差し替え口。決済（スタブ）とメール（ファイル出力） adapters/payment.py::StubPaymentAdapter
seed.py・seed_data.py 初期データの投入（商品 31 点・カテゴリ・設定・お知らせ・FAQ）。定義は seed_data.py、投入は seed.py seed.py::seed
main.py アプリの組み立て。ルーターの登録、エラーハンドラ、CORS、本番での Swagger 無効化 main.py::create_app

依存の向きは routers → services → repositories → models で、下の層から上の層は呼びません。決済とメールのアダプタはルーターが Depends で受け取り、引数としてサービスへ渡します。サービスがアダプタを自分で作ることはありません。

事実（import を grep で確認）: routers/ から repositories/ を直接呼ぶ箇所はありません。ただし例外が 2 つあります。①routers/catalog.py が app.models から列挙型 Gender だけを import している。②repositories/orders.py が services/order_number.py の generate_order_number（DB を見ない純粋関数）を import している。どちらも DB 操作や業務判断を上の層へ持ち出してはいません。

フォルダ・ファイル役割代表例
app/（ページ） URL ごとのページ。すべて Server Component で、必要なデータは lib/server から FastAPI を読んで描画する（注文手続きのようにデータを読まないページもある）。操作のある部分は components/ の Client Component に任せる app/products/page.tsx

事実: lib/ 直下の basic-auth.ts・csrf-validation.ts・client-ip.ts・env-validation.ts は、Vitest から直接テストできるように server-only を付けず、秘密を読まない純粋関数にしています。process.env を実際に読むのは proxy.ts、lib/server/env.ts、layout.tsx です。

1 リクエストの一生：「カートに入れる」

商品詳細の「カートに入れる」を押すと、まず画面の関数が CSRF トークンを用意して BFF を呼びます。BFF は CSRF と入力の形を確かめ、Cookie のカートトークンをヘッダに載せ替えて FastAPI へ渡します。FastAPI はトークンを確かめたあと、サービスがカートを特定し、在庫と上限を見て、リポジトリが cart_items に 1 文で追加します。返ってきたカート全体が BFF を通って画面に戻り、ヘッダのバッジとトーストを更新します。

1. 追加ボタンを押す

PurchasePanel の onAdd。選択中の色・サイズから解決した variant_id と数量で addCartItem を呼ぶ

2. CSRF トークンを付けて送る

ensureCsrfToken が Cookie から csrf_token を読む（無ければ先に GET /api/cart で発行させる）。POST /api/cart/items に X-CSRF-Token ヘッダを付ける

3. BFF が CSRF と入力の形を確かめる

verifyCsrf で Cookie とヘッダが一致しなければ 403。variant_id が整数、quantity が正の整数かを見て、外れれば 400 validation_error

4. Cookie をヘッダへ載せ替えて FastAPI を呼ぶ

Cookie cart_token を X-Cart-Token に載せ、apiFetch が X-Internal-Token を付ける。応答のトークンが Cookie と違えば Set-Cookie で更新する

5. FastAPI がトークンを検証してルーターへ

verify_internal_token を通ったあと、ルーターは body（variant_id・quantity）を検証してサービスを呼ぶだけ

6. サービスが順に判定する

カート特定（resolve_cart）→ 商品が公開中で存在するか（無ければ 404）→ 在庫 0 なら 409 → 加算 → 上限超過なら rollback して 422 → commit

7. cart_items に 1 文で追加

INSERT … ON DUPLICATE KEY UPDATE。同じ variant が既にあれば数量を足す。同時に 2 回押されても行は 1 つ

8. 応答で画面を更新

カート全体（明細・金額・点数）が返る。applyCart でヘッダのバッジを更新し、トーストに「カートを見る」を出す

意見: この 1 本を説明できれば、カート変更・注文手続き・注文確定は同じ型（画面 → クライアント関数 → BFF → FastAPI → サービス → リポジトリ）の繰り返しとして話せると思います。違いが出るのは、BFF に載せ替えるヘッダの種類と、サービスの判定の数です。
