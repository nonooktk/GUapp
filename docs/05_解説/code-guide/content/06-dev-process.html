6. 開発の進め方

本の出版に例えると、著者は本番の原稿を直接書き換えず、コピーに書き込みます。校閲の人が読み、機械が誤字を検査し、通ったものだけが本番の原稿に綴じ込まれます。この章は、その「コピーで作業する」「検査を通す」「本番に綴じる」の流れと、検査に使うテストの読み方の説明です。

正確には、Git のブランチで作業し、GitHub の Pull Request（PR）で main に取り込みます。PR ごとに GitHub Actions が自動テストと秘密のスキャンを走らせます。この章では、実際のリポジトリの設定値を確認して書いているため、設計意図と設定が食い違う箇所は「事実」の注記で示します。

ブランチは接頭辞で分け、PR で main に入れる

作業は main から切ったブランチで行い、feat/（機能）、fix/（修正）、docs/（文書）、test/（テスト）、chore/（雑務）の接頭辞で種類を示します。P1 の実装プランには「作業は feat/p1-<wave>-<topic>。1 Wave 1〜3 PR、squash merge」とあり、履歴にはマージコミットがなく、コミット末尾に (#30) のような PR 番号が付いた 1 本線になっています。squash merge で取り込んだ形です。Dependabot が作る PR は dependabot/ で始まります。

2026-09-29 時点で、PR は #1 から #30 の 30 本です。25 本がマージ済みで、5 本（#16〜#20）は Dependabot の更新 PR が未マージのままです。PR の説明は PR テンプレートに沿って書きます。設計 ID・テスト ID、秘匿情報が差分に無いこと、pre-commit run --all-files が通ること、pytest と Vitest が緑であること、実際に動かして確認したことのチェックと、検証の証拠（テスト結果の抜粋）の欄があります。

main の保護：削除と強制 push は禁止、必須チェックは gitleaks だけ

GitHub のルールセット main-protection が main（既定ブランチ）に掛かっています。gh api repos/nonooktk/GUapp/rulesets で読み取って確認した内容は次のとおりです。

ルール設定効果
削除の禁止（deletion）有効main を消せない
強制 push の禁止（non_fast_forward）有効履歴を書き換える push ができない
PR 必須（pull_request）承認する人数は 0直接 push はできず PR が要るが、承認者は不要（推測：1 人で開発しているため）
必須のステータスチェックgitleaks のみ秘密のスキャンが通らない PR はマージできない
迂回できる主体（bypass）なしリポジトリの所有者も迂回できない

これに加えて、AI エージェントが作業するときは .claude/settings.json の deny 設定で、force push、reset --hard、checkout -f、clean、stash、add -A、add .、rebase などのコマンドを実行できなくしています。実装プランには、ルールセットの作成後に main への直接 push が GH013 で拒否された、と実証の記録があります。

必須のステータスチェックに api-test (pytest) と web-test (vitest + build) は入っていません（ルールセットの required_status_checks は gitleaks の 1 件だけ）。このため、テストが赤のままでも、PR は main にマージできます。実装プランの「main は CI 緑のみマージ」とテスト設計書 1.2 の「IT・UT は 1 件でも失敗すれば main へのマージを止める」は、設定ではなく運用の約束として守られている状態です。第 9 章で扱います。

CI：3 つのジョブと gitleaks が PR ごとに走る

CI の定義は ci.yml と secrets-scan.yml の 2 ファイルです。どちらも PR と main への push で動き、同じブランチで新しい実行が始まると古い実行を止めます（concurrency）。

api-test：本物の MySQL 8.4 で pytest

サービスコンテナの MySQL 8.4 を起動し、文字コードとタイムゾーンを揃えてから alembic upgrade head、続けて pytest -q。マイグレーションが実際に通ることも毎回確かめる。

web-test：Vitest

依存を lock 固定でインストールし、pnpm test -- --run で Vitest を実行する。

web-test：server-only ガード

わざと違反するファイルでビルドし、失敗しなければ CI を赤にする（第 4 章）。

web-test：ビルドと秘密の全文検索

next build を実行し、ビルド成果物 .next/static にダミーのトークン値が含まれないことを確認する。

deps-audit：依存の脆弱性を報告

pip-audit と pnpm audit を実行する。ジョブに continue-on-error: true が付いており、失敗しても PR はブロックされない。

gitleaks：履歴全体の秘密スキャン

別ファイルのワークフロー。fetch-depth: 0 で履歴をすべて取得して走査する。これだけが main の必須チェック。

api-test の MySQL のユーザー名とパスワードは CI の中だけで使う値で、実環境の値ではありません（ファイル冒頭のコメント）。テスト用の接続先 guapp_test、APP_ENV=test、ダミーの INTERNAL_TOKEN などは、ジョブの env で与えます。apps/api や apps/web が存在するかを確かめる「存在確認」ステップが各ジョブの先頭にありますが、これはリポジトリの作り始めの並行作業のための暫定措置で、いまは両方が存在するため、スキップされることはありません。

CI の api-test では、結合テスト 100 件が実行されていません。結合テストは環境変数 DATABASE_URL_TEST が無いと全件スキップする作りですが（conftest の判定）、ci.yml の env にこの変数がありません。2026-09-26 の main（2b9c87d）の CI ログには 200 passed, 100 skipped と出ています。MySQL を起動して alembic upgrade head まで通すのに、同時実行のテスト（IT-014-02〜04）を含む結合テストは走っていない状態です。手元で DATABASE_URL_TEST を設定して実行した結果が、検収の「IT 全件緑」の根拠になっています。第 9 章で扱います。

lint は CI でも pre-commit でも回していない

コードの書き方を機械的に検査する lint は、ツール自体は入っています。api は ruff（ruff.toml。行長 100、pyflakes・pycodestyle・isort・bugbear・pyupgrade の規則）、web は eslint（eslint.config.mjs。Next.js の推奨設定）です。package.json には pnpm lint と pnpm typecheck のスクリプトもあります。

ただし ci.yml にも .pre-commit-config.yaml にも、ruff・eslint・tsc を呼ぶ行はありません（リポジトリ内の検索で、スクリプトから ruff を呼んでいるのは、防御外し確認の run.ps1 が復元後に ruff check を実行する 1 か所だけ）。lint は手元で実行する運用で、実行を強制する仕組みは無い状態です。pnpm build（CI で実行）は Next.js の仕様で型検査を含むはずですが、これは推測で、CI ログでは確認していません。

テストの読み方：ファイル名と関数名からテスト ID をたどる

テストは 4 つのレベルに分かれ、設計書の ID と 1 対 1 で結びつけてあります。テスト設計書 0 章の対応表を実装に置き換えると、次のとおりです。

レベルID の形何を確かめるか実行方法置き場所
受け入れテスト（AT）AT-01〜AT-08利用者の目的が達成できるか。ブラウザで操作手動記録は docs/05_検収/
システムテスト（ST）ST-F014-01、ST-SEC-07機能要件・非機能要件。画面と curl で確認主に手動。一部は自動化記録は docs/05_検収/
結合テスト（IT）IT-014-03、IT-BFF-02BFF・FastAPI・DB の経路、同時実行、異常系自動（api は MySQL 必須）apps/api/tests/integration/、apps/web/tests/
単体テスト（UT）UT-014-04、UT-WEB-05関数・コンポーネント自動apps/api/tests/unit/、apps/web/tests/

ファイル名の読み方は、api と web で少し違います。api はファイル名が test_ut_…・test_it_… で始まり、関数名は test_<ID 小文字>_<要点> の形にする取り決めです（実装プランの実装上の取り決め）。web は <ID>.<対象>.test.ts(x) の形です。ID の付かないテストもあり（csrf-validation.test.ts、datetime.test.ts など）、その場合は対象の名前がそのままファイル名になります。

同時実行のテストには偽陽性を避ける工夫があります。実際に同時に走っていなければ、防御が壊れていても緑になるためです。テスト専用の「処理中カウンタ」の最大値が 2 以上だった試行だけを有効とし、そうでない試行は無効として最大 3 回やり直し、3 回とも不成立ならそのテストを赤にします（run_until_concurrent）。この仕組みが本番のコードに入らない理由は第 4 章にあります。さらに scripts/mutation-check は、冪等キーの一意制約、カートの条件付き UPDATE、在庫の stock >= :q の 3 つを 1 つずつ外して、該当のテストが赤くなることを確かめます。結果は同じフォルダの result-20260918.md に残っています。

自動と手動の分担は、機械で何度でも繰り返せるものを自動、見た目や操作の流れなど人が見ないと判断できないものを手動にする考え方です。AT は 375px と PC 幅の両方をブラウザで操作して確認し、ST は画面操作と curl で確認します。ST の記録では、期待結果の文言をそのまま観測できたときだけ「合格」とし、確認できなかった項目は「未実施（理由）」と書くルールです。検収の記録は、正常系（ST-AT実施記録_正常系）、異常・境界（Mac 分と Windows 分）、公開環境（公開環境_確認記録）に分かれています。

コードカバレッジ（テストがコードの何割を通ったか）は計測していません。pyproject.toml と package.json に pytest-cov や Vitest のカバレッジ設定が無く、CI にも計測のステップがありません。テストの網羅は、設計書の ID と対応表（テスト設計書 10 章）で確認する方式です。
