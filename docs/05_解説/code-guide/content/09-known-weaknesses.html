9.6 付録: 決済 NG で在庫が戻らなかった注文を探す SQL

B2 のとおり、決済 NG の経路は 2 段で、在庫を戻す処理とカートを active に戻す処理が同じトランザクションに入っている。そのため、注文の状態が payment_failed なのに、そのカートがまだ ordered のままなら、2 段目が実行されておらず在庫を戻し損ねたと判断できる。次の 1 本で探せる。

SELECT o.order_number, o.created_at, o.total
FROM orders AS o
JOIN carts AS c ON c.id = o.cart_id
WHERE o.status = 'payment_failed'
  AND c.status = 'ordered'
  AND NOT EXISTS (
    SELECT 1 FROM orders AS o2
    WHERE o2.cart_id = o.cart_id AND o2.status <> 'payment_failed'
  )
ORDER BY o.created_at;

表名と列名は Order・Cart の定義に、状態値は OrderStatus・CartStatus に合わせた。決済 NG の 1 段目で payment_failed が COMMIT され、2 段目の restore_cart_active が成功したときだけカートが active に戻る（_confirm）。

この SQL の限界: 次の 3 点に注意する。①実行した瞬間に 2 段の間にいる注文が 1 件出ることがある（数ミリ秒の窓）。出た注文は数分後にもう一度確かめる。②決済 NG が正常に戻ったあと、同じカートで買い直して成功すると、カートは ordered になる。これを戻し損ねと誤検出しないよう NOT EXISTS で除外している。戻し損ねたカートは次の閲覧時に新しいカートへ差し替わる（resolve_cart）ので、買い直しの成功と混ざらず、この除外で見逃すことは無いと読んでいる（コードを読んだ範囲の推論で、実機では試していない）。③在庫の実数は見ていない。手動で戻すときは variants.stock を数量ぶん加算する。決済 NG の注文は order_items を書かない仕様（設計書 4.4）なので、数量は cart_items から追う。

事実（確認方法）: この SQL の構文は、同じ名前の最小の表を作って SQLite で動かし、戻し損ねの 1 件だけが返ることを確かめた。MySQL 8.4 の実機には接続していない。

9.7 褒められそうな点

弱点の一方で、コードを読んだ人に伝えやすい点もある。事実だけを短く並べる。

  • 内部トークンの比較は一定時間で行い、期待値が未設定なら全リクエストを拒否する（verify_internal_token）。
  • 本番で Swagger（/docs など）を出さないこと、テスト専用ルートが本番の読み込み経路で import されないことを、テストで確かめている（docs の無効化、import されないこと）。
  • SQL は ORM のバインド変数で組み、LIKE の % と _ は autoescape に任せている（build_match_condition）。f 文字列で SQL を作る箇所は seed の表名だけで、既知の表名の一覧に照らして弾いている。
  • CI で、クライアントコンポーネントから server-only のモジュールを import すると next build が失敗すること、ビルド成果物の .next/static に内部トークンの値が無いことを検査している（ci.yml L146-211）。
  • 二重注文の防止は、設計では 4 層（7.4）である。P1 で動いているのは、冪等キーの UNIQUE（insert_pending_order）とカートの条件付き UPDATE（mark_cart_ordered）の 2 層で、Stripe を使う残りの 2 層は P2 である。画面側にも、確定ボタンの二重クリックを止める仕組みがある（OrderConfirm L65-66）。
