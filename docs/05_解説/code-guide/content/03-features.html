匿名カートトークン　カートの持ち主は Cookie の cart_token で決まります。トークンを発行するのは FastAPI で、new_cart_token が 32 バイトの乱数を base64url にした 43 文字を作ります。BFF は Cookie の値を X-Cart-Token ヘッダに載せ替えて渡し、応答のトークンが Cookie と違うときだけ Set-Cookie で更新します（buildCartTokenCookie：HttpOnly・SameSite=Lax・90 日）。ヘッダの値は normalize_token が形（英数・-・_ の 64 文字以内）を確かめ、合わなければ「未知」として新しいカートを作ります。

サービス側の resolve_cart は、トークンのカートが active ならそのまま使い、ordered や merged なら旧カートからトークンを外して同じトークンで新しい active カートを作ります。注文後に「買い物を続ける」から別の商品を入れても、注文済みカートに混ざらないのはこのためです。同時に 2 つの GET が来て UNIQUE 違反になったときは、ロック読み（FOR UPDATE）で先に作られた方を取り直します。

追加の判定順　add_item は次の順で判定し、途中で外れると rollback します。①公開中の商品のバリエーションが無ければ 404 not_found、②在庫が 0 以下なら 409 out_of_stock（items に variant_id）、③加算（INSERT … ON DUPLICATE KEY UPDATE の 1 文）、④加算後の数量で上限を見て、1 明細が 10 点を超えるか、カート合計が 50 点を超えると 422 limit_exceeded（field=quantity、limit は 10 か 50）。数量が在庫より多くても追加はできます。在庫の確定は注文時の引当で行うためです。数量変更（update_item）は、自分のカートに無い明細なら 404 で、他人の item_id を指定しても触れません。変更時は在庫の検査をしません。

在庫状態と送料の案内　カート応答の各明細には stock_status が付きます。非公開または在庫 0 なら out_of_stock、在庫が数量より少なければ insufficient、それ以外は ok です（stock_status）。空でなく、全明細が ok のときだけ can_checkout=true になり、そうでなければ CartView が警告を出して「レジへ進む」を無効にします。送料は calc_shipping_fee が小計（値引き前の明細合計）で判定し、閾値（既定 4,990 円）以上なら 0 円、未満なら設定の送料（既定 550 円）です。CartView は閾値を「（4,990 円以上で無料）」と添え、送料 0 のときは「無料」と表示します。閾値と送料は system_settings の値で、画面には API 応答の free_shipping_threshold を使います。

CSRF　追加・変更・削除は状態を変えるので、クライアント（ensureCsrfToken）が Cookie csrf_token を読み、X-CSRF-Token ヘッダに載せます。Cookie が無ければ先に GET /api/cart を呼び、BFF に発行させます（issueCsrfCookieIfMissing）。BFF 側は verifyCsrf が Cookie とヘッダを比べ、外れれば 403 forbidden で FastAPI へ届かせません。

入力の扱い　検索語は normalize_search_term が前後の空白を落とし、NFKC 正規化と空白の整理をしたうえで、空でないか、100 文字以内かを見ます。外れると 400 validation_error（fields は q）です。ルーターの Query にも 1〜100 文字の指定があり、空文字や 101 文字以上はそこで先に 400 になります。SearchPage は URL の q を 100 文字で切り、空白だけなら API を呼ばずに「検索語を入力してください。」を出します。SearchBox は入力から 300ms 待ってサジェストを呼み、Enter か候補の選択で /search?q=… へ移ります（商品詳細へは飛びません）。

一致の判定　build_match_condition が、商品名・説明・カテゴリ名のいずれかへの部分一致（OR）を作ります。カテゴリ名は product_categories を経由するサブクエリです。% と _ は autoescape=True で文字として扱います。全角と半角、ひらがなとカタカナ、清濁音の違いは、DB の照合順序（utf8mb4_0900_ai_ci）が同じ文字として扱います。コード側の正規化は、空白の整理、長さの判定、言い換え辞書の引き当てを揃えるためのものです（DS-DEC-34）。濁点を欠いた「ハンツ」で「パンツ」が見つかることがあり、これは設計上受け入れた制限です（ST-F003-07）。並びは一覧と同じ新着順です。

0 件のとき　0 件のときだけ 2 つを添えます。1 つは類似キーワードで、SEARCH_SYNONYMS の辞書（例：「デニム」→「ジーンズ」）から候補を引き、実際に 1 件以上ヒットする語だけを最大 5 件残します。もう 1 つはおすすめカテゴリで、子カテゴリを商品数の降順（同数は sort_order、id の順）に並べ、0 件のカテゴリを除いた上位 3 件です。サジェストは商品名の前方一致を優先し、5 件に満たなければ部分一致で補い、同じ商品は重ねません。

事実: 検索 API にレート制限はありません。ADR-0003 で見送り、公開時も ADR-0004 の判断で実装していません（Basic 認証を知らない人は /api/* に届かない前提。公開追補 7.1）。

DS-DEC-48DS-DEC-49DS-DEC-50　レビュー用に公開するサイト全体を Basic 認証で守り、全ページの上部に「期間限定で公開している」という帯を出します。

Basic 認証　proxy.ts の matcher は、_next/static・_next/image・favicon.ico・sitemap.xml・robots.txt を除く全リクエストです。BFF の /api/* も含みます。環境変数はモジュールの読み込み時に parseBasicAuthConfig で 1 回だけ評価し、結果は 3 通りです。両方未設定なら認証なし（ローカル開発を妨げない）、両方設定なら認証あり、片方だけなら BasicAuthConfigError を投げます。設定漏れのまま無防備に公開する事故を、全リクエストが失敗する形で気づけるようにするためです。認証ありのとき、Authorization ヘッダが正しければ通し、そうでなければ本文なしの 401 と WWW-Authenticate: Basic realm="GUapp demo" を返します。

ヘッダの検証（verifyBasicAuthHeader）は例外を投げません。Basic の書式でない、base64 が壊れている、コロンがない、といった場合はすべて「認証失敗」の false です。ID とパスワードは、それぞれ SHA-256 で固定長にしてから timingSafeEqual で比べます。入力の長さの違いで比較が早く終わらないようにするためで、両方を比べ終えてから結果を合わせます。この認証は Next.js の入口だけを守ります。FastAPI は別に、内部トークンで BFF 以外からの呼び出しを拒否します。

公開期間の帯　RootLayout が実行時の process.env.DEMO_PUBLIC_UNTIL（YYYY-MM-DD）を読み、parseDemoPublicUntil で検証して YYYY/MM/DD の文字列にします。未設定または空は帯なし（警告も出しません）。形式が違う日付や、実在しない日付（2026-13-01 など）は、帯なしにして警告を出します。例外は投げず、環境変数 1 件の誤りでサイト全体が落ちないようにしています。NEXT_PUBLIC_ を付けていないので、ビルドし直さずに値を変えて終了日を延ばせます。DemoPeriodBanner は Server Component で、文字列が null のときは何も描画しません。帯は role="status" で、文言そのものに「期間限定」「デモ」と書いています（色だけで意味を伝えない）。
