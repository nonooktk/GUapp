12. 用語集

レビューで出そうな用語を 34 語、話題ごとに並べた。各項目は、その語が指す仕組みを先に書き、このコードのどこに出てくるかを参照で添えた。参照のない語は、このリポジトリでは概念としてだけ使っている。

12.1 構成と画面

BFF（Backend For Frontend）
ブラウザ専用の窓口になるサーバー層。このアプリでは Next.js の Route Handler（/api/*）が担い、FastAPI の URL と内部トークンをブラウザに出さずに取り次ぐ。呼び出しの共通部分は apiFetch、注文確定の入口は POST /api/orders。
Route Handler
Next.js の App Router で app/api/**/route.ts に書く、GET・POST などの HTTP メソッド名の関数。BFF の実体である。例: カート取得の GET。
Server Component / Client Component
Server Component はサーバーだけで実行され、FastAPI を直接呼んで画面の初回表示を作る。Client Component はファイル先頭の "use client" で示し、ブラウザで動いて状態やクリックを扱う。例: ProductsPage（サーバー）と ProductsGrid（クライアント）。
server-only
「このモジュールはサーバー専用」と宣言するための import。クライアントコンポーネントから import するとビルドが失敗する。環境変数のローダー（getEnv）など、秘密を触るモジュールの先頭に置いてある。CI には、違反ファイルでビルドが失敗することを確かめる工程がある（ci.yml）。
sessionStorage
ブラウザがタブごとに持つ保存領域で、タブを閉じると消える。注文手続きの入力値と冪等キーを、入力画面から確認画面へ渡すために使っている（saveCheckoutSession）。個人情報を長く残さないため、localStorage は使わない。
proxy.ts と HTTP Basic 認証
Next.js 16 で middleware.ts の後継になったファイルで、リクエストが画面や API に届く前に呼ばれる。ここでは、レビュー用の公開環境にサイト全体の HTTP Basic 認証をかけるために使っている（proxy、照合は verifyBasicAuthHeader）。

12.2 セキュリティ

内部トークン
BFF から FastAPI への呼び出しに付ける共有の秘密で、ヘッダ X-Internal-Token で送る。FastAPI は一定時間で比較し、期待値が未設定なら全リクエストを拒否する（verify_internal_token）。
CSRF と Double Submit Cookie
CSRF は、利用者のブラウザに別サイトから状態を変えるリクエストを送らせる攻撃である。Double Submit Cookie は、同じトークンを Cookie とリクエストヘッダの両方で送らせ、一致を確かめる対策で、BFF で検証している（verifyCsrf、判定規則は isCsrfValid）。
HttpOnly・SameSite・Secure
Cookie の属性。HttpOnly は JavaScript から読めなくし、SameSite=Lax は別サイトからの送信を制限し、Secure は HTTPS でだけ送る。カートのトークンは HttpOnly、CSRF トークンは JS が読むため HttpOnly なし、Secure は production だけに付ける（buildSetCookie）。
CORS
ブラウザが別のオリジン（ホストとポートの組）の API を呼んでよいかを、サーバー側が許可する仕組み。FastAPI は BFF の 1 オリジンだけを許可し、未設定や * なら CORS を付けない（install_cors）。
X-Forwarded-For
プロキシが付ける、元の送信元 IP を並べたヘッダ。利用者が自分で付けて偽装できるため、信頼できる位置の値だけを使う（resolveClientIp）。設定の漏れが第 9 章の A1 である。
レート制限
一定時間内の呼び出し回数に上限を設けて、総当たりを止める仕組み。ゲスト注文照会に 100 回/時/IP を設け、超えると 429 と Retry-After を返す（SlidingWindowRateLimiter）。
IDOR
他人の注文番号やカートの ID を指定して、他人のデータを見たり操作したりできてしまう脆弱性。他人のものは存在しないのと同じ 404 で返して対策している（_existing_order_result）。
秘密のマスク
ログに書く前に、Stripe のキー・接続文字列・Bearer トークン・内部トークンの値を *** に置き換える処理（SecretMaskFilter）。
gitleaks と detect-secrets
リポジトリに秘密（鍵やトークン）が混ざっていないかを調べるツール。detect-secrets は commit の前に（pre-commit）、gitleaks は CI で履歴全体を走査する（secrets-scan.yml）。
Dependabot
依存ライブラリの更新 PR を自動で出す GitHub の機能。npm・uv・GitHub Actions を週次で見ている（dependabot.yml）。

12.3 データと注文

冪等キー
同じ操作を 2 回送っても、1 回分の結果になるように、操作に付ける固有の値。確認画面の準備で FastAPI が発行し（new_idempotency_key）、注文の INSERT では orders.idempotency_key の UNIQUE 制約で重複を止める（insert_pending_order）。
条件付き UPDATE
更新の条件を UPDATE 文の WHERE に入れ、影響した行数で成否を判断する書き方。在庫引当では stock >= :q を条件にし、0 行なら在庫不足とする（reserve_stock）。
トランザクションと ROLLBACK
複数の DB 更新を、全部成功させるか全部取り消すかにまとめる単位。COMMIT で確定し、ROLLBACK で取り消す。注文確定の境界は _confirm に集めてある。
デッドロック
2 つの処理が互いの持つロックを待ち合って進まなくなる状態。InnoDB は一方を失敗させる。同じカートの同時確定で起き、ROLLBACK して 1 回だけやり直す（_create_order_with_deadlock_retry）。
ORM とバインド変数
ORM は、SQL をプログラムのコードから組み立てる仕組み（ここでは SQLAlchemy）。バインド変数は値を SQL 文と別に渡す方式で、値が SQL として解釈されない。SQL インジェクションを防ぐ土台である。例: build_match_condition。
Pydantic
入力の型と形を宣言して検証する Python のライブラリ。FastAPI の入力検証に使い、違反は 400 validation_error に変換する。例: OrderCreateIn。
Alembic
テーブル定義の変更履歴（マイグレーション）を管理するツール。最初の版は 0001_p1_initial.py、コンテンツ表の追加が 371a338f4624_p2a_contents.py。
監査ログ
誰がいつ何をしたかを DB に残す記録で、audit_logs 表に書く。注文確定は order.confirm、決済 NG は order.payment_failed（AuditLog）。

12.4 外部連携・運用・テスト

スタブとアダプタ
スタブは、本物の代わりに決まった値を返す偽物。アダプタは、呼び出し側と外部サービスの間に置く、差し替え可能な窓口である。決済とメールは、Protocol で型を決めたアダプタの後ろにスタブを置いている（PaymentAdapter、StubPaymentAdapter）。
Webhook
外部サービス（Stripe）が、支払いの完了などの出来事の後に、こちらの URL へ送ってくる通知。P2 の Stripe 接続で使う予定で、まだ実装していない。設計は設計書 3.3.2。
App Service
Azure のアプリ実行サービス。web と api を 1 つのプランに別々に載せ、Always On と HTTPS Only を設定している（01-create.sh）。
ワーカー
1 つのアプリを並列に処理するプロセス。api は uvicorn --workers 2 で動かす（config.sh L51）。メモリはワーカー間で共有されないため、プロセス内メモリのレート制限はワーカーごとの集計になる。
UT・IT・ST・AT
V 字モデルの右側にあたる 4 段階のテスト。単体（UT）、結合（IT）、システム（ST）、受け入れ（AT）で、ID はテスト設計書で決めている。要件からの対応は設計書 10 章のトレーサビリティ表にある。
pytest と Vitest
pytest は Python（api）、Vitest は TypeScript（web）のテストランナー。api は 300 件（unit 200・integration 100）、web は 228 件で、合計 528 件。api の結合テスト 100 件は、いまは CI でスキップされている（第 9 章 D3）。設定は pyproject.toml と vitest.config.mts。

12.5 文書の用語

ADR（Architecture Decision Record）
工程の分け方や環境の調達のような計画レベルの判断を、背景・代替案・理由つきで残す文書。設計レベルの判断は DS-DEC が受け持つ（役割分担は ADR の README）。
DS-DEC
設計仕様書 9.1 にある、設計判断の番号つきの一覧。決めた内容、理由、次善策が 1 行に入っている（設計書 9.1）。
DS-API・DS-TBL・DS-PRC・DS-SCR
設計仕様書の設計 ID の接頭辞で、API・テーブル・処理・画面を指す。コードのコメントにこの ID が付いていて、設計書へたどれる。定義は設計書 0 章。
REQ・F・SCR
REQ は要求仕様書の要求 ID（REQ-FR-501 など）、F は要件定義書の機能 ID（F-013 など）、SCR は画面 ID。追跡は REQ から F、設計 ID、テスト ID の順につなぐ（対応表は実装フェーズ計画 4 章）。
