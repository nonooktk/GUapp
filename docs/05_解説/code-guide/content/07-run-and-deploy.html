7. 動かし方と公開環境

店に例えると、自宅の作業台で試作品を作る段階と、貸し店舗に並べてレビュワーに見てもらう段階があります。作業台には自前の道具（Docker の MySQL）を置き、貸し店舗では共用の倉庫（講義の MySQL）に間借りして、入口に合言葉（Basic 認証）を掛けます。

正確には、ローカルでは Docker の MySQL に Next.js（127.0.0.1:3000）と FastAPI（127.0.0.1:8000）を繋ぎます。公開環境では Azure App Service の 2 つのアプリ（web と api）が、講義共用の Azure Database for MySQL に繋がります。この章は、動かすコマンド、公開環境の構成、デプロイスクリプト、講義 DB への接続方法、環境変数の名前と役割の順に説明します。

ローカルでの動かし方：MySQL、API、web の順に起動する

手順は README.md と scripts/mysql-docker/README.md にあります。次のコマンドは Mac（Docker Desktop）向けに、両方から抜き出してまとめたものです。Windows は scripts/mysql-local/ の PowerShell を使います。

# 0. 初回のみ: 事故防止の仕組み（秘匿ファイルや巨大ファイルを commit 時点で止める）を有効にする
cd ~/GUapp
pre-commit install

# 1. MySQL 8.4 を起動する（Docker Desktop が起動していること）
#    .env は MYSQL_PASSWORD だけを書く。コミット禁止（gitignore 済み）
echo "MYSQL_PASSWORD=<任意のローカル専用パスワード>" > .env
docker compose up -d
docker compose ps        # guapp-mysql が healthy になるまで待つ

# 2. API（apps/api/.env に環境変数を書いておく。名前は本章の表を参照）
cd ~/GUapp/apps/api
uv sync
uv run alembic upgrade head          # 13 表を作る
uv run python -m app.seed            # 初期データ。商品があれば何もしない
uv run uvicorn app.main:app --reload --port 8000
curl http://127.0.0.1:8000/api/v1/health   # {"status":"ok","db":"ok"} なら成功

# 3. web（別のターミナル。apps/web/.env.local に環境変数を書いておく）
cd ~/GUapp/apps/web
pnpm install
pnpm dev                             # http://127.0.0.1:3000 で開く

API のホストは uvicorn の既定の 127.0.0.1 です。web は package.json の dev スクリプトが next dev -H 127.0.0.1 なので、同じく自分の PC からしか届きません（デモの個人情報対策として PR #25 で限定）。apps/api/.env の DATABASE_URL は、Docker の場合 mysql+asyncmy://guapp:<MYSQL_PASSWORD>@127.0.0.1:3306/guapp の形です。INTERNAL_TOKEN は api と web で同じ任意の値にします。商品画像は apps/web/public/products/ のプレースホルダーを使います。

テストの実行は次のとおりです。結合テストは DATABASE_URL_TEST を渡したときだけ走ります。この DB 名は _test で終わる必要があり、そうでなければテストが中止されます（開発 DB を壊さないための安全装置）。

# web（228 件）
cd ~/GUapp/apps/web && pnpm test

# api の単体テスト（DB 不要。結合テストはスキップされる）
cd ~/GUapp/apps/api && uv run pytest -q

# api の結合テストも含める（guapp_test は docker compose の初回起動時に作られる）
DATABASE_URL_TEST="mysql+asyncmy://guapp:<MYSQL_PASSWORD>@127.0.0.1:3306/guapp_test" uv run pytest -q

# 後片付け
cd ~/GUapp && docker compose stop          # データは残す
cd ~/GUapp && docker compose down -v       # データごと消して作り直す

Docker が使えない PC では、Windows 用の scripts/mysql-local/（zip 版 MySQL を管理者権限なしで置く PowerShell 一式）が同じ設定値で動きます。docker-compose.yml の 7 行目には「作成者の PC に Docker が無いため実行確認をしていない（2026-09-18）」とありますが、その後、Mac の Docker MySQL で検収の記録が取られており（docs/05_検収/）、注記は古くなっています。

公開環境の構成：App Service 2 つと講義の MySQL

公開の目的は、講義のレビュー期間中だけ、限られたレビュワーに実際に触ってもらうことです（ADR-0004）。Azure のリソースグループ rg-001-gen12（受講生で共用）の東日本（japaneast）に、Linux の App Service プラン（B1）を 1 つ作り、web と api の 2 つのアプリを同居させます。DB は新しく作らず、講義共用の Azure Database for MySQL（gen12-mysql-pos）に、自分専用のスキーマ guapp_nonooktk を作って使います（ADR-0002）。

レビュワーのブラウザ

URL と Basic 認証の ID・パスワードは、統括が個別に伝える

App Service プラン（B1・Linux）

入口の保護は 3 段です。1 段目は HTTPS Only（http で来ると https へ転送）、2 段目は Next.js の proxy.ts による Basic 認証、3 段目は api の内部トークン（第 4 章）です。Basic 認証の判定は verifyBasicAuthHeader にあり、環境変数の読み取りは parseBasicAuthConfig が担います。次の動作になります。

環境変数の状態動作理由
BASIC_AUTH_USER と BASIC_AUTH_PASSWORD が両方未設定認証なし（ローカル開発向け）手元の開発を妨げない
片方だけ設定例外で失敗（BasicAuthConfigError）設定漏れのまま無防備に公開するのを防ぐ
両方設定正しい Authorization がなければ 401 を返す本番

対象外にしているのは、_next/static、_next/image、favicon.ico、sitemap.xml、robots.txt です（config の matcher）。ファイル名にハッシュが付いていて、認証済みの画面を経由しないと URL が分からず、中身もビルド成果物で個人情報を含まないため、と設計書にあります。/api/* は /api/health も含めて保護の対象です。

公開期間は 2026-10-09 までです。全ページの上部に「講義レビュー用のデモとして、YYYY/MM/DD まで期間限定で公開しています」の帯が出ます。終了日は環境変数 DEMO_PUBLIC_UNTIL で、再デプロイなしに延長できます（parseDemoPublicUntil。NEXT_PUBLIC_ を付けるとビルド時に値が埋まって延長できなくなるため付けていません）。期限が来ても自動では止まらず、停止は手動の 90-stop.sh です（ADR-0004）。注文手続きのフォームには、ダミーの初期値と注意書きが常時出ます（DEMO_CHECKOUT_FORM）。講義サーバーの管理者はスキーマの中身も読めるため、本物の個人情報を入れさせないための仕組みです。

公開後の確認は 2026-09-25 に行い、記録は docs/05_検収/公開環境_確認記録_20260925.md にあります。api のヘルスチェック、Basic 認証（認証なし・誤り・正しい資格情報で 401・401・200）、期間限定の帯、商品閲覧・検索・お知らせ、注文確定 1 件（ダミー値）、Cookie の Secure、api の /docs の 404、CORS、http から https への転送が合格と記録されています。ただし確認画面（/checkout/confirm）は、ルートの疎通までしか確認しておらず、ブラウザでの目視は未実施です。

デプロイスクリプト：01 から 06 が順番、90 と 99 は後片付け

scripts/azure-deploy/ のスクリプトは Azure CLI（az）で操作する手動デプロイです（GitHub Actions による自動デプロイは、この時点では作っていません）。作成・変更するスクリプトは、実行前に az account show を表示して確認を求め、既存のリソースがあれば作成をスキップします。番号順に実行します。

ファイルやること気をつける点
config.sh他のスクリプトが読む共通設定。リソース名、SKU（B1）、ランタイム（Node 24・Python 3.13）、起動コマンド、DB プールの推奨値、公開期限単体では何もしない。名前が衝突したら GUAPP_NAME_SUFFIX="-1" のように設定して再実行する
01-create.shApp Service プランと web・api の 2 アプリを作り、Always On、HTTPS Only、最小 TLS 1.2、起動コマンド、ポート関連の設定を入れるリソースグループは共用のため作らず、存在確認だけ行う。api に SCM_DO_BUILD_DURING_DEPLOYMENT=true を入れるのは、zip デプロイが既定では pip install を走らせないため
02-settings.shweb・api の環境変数（アプリ設定）を投入する。INTERNAL_TOKEN と Basic 認証の ID・パスワードをその場で乱数生成する秘密は画面に出さず、権限 600 の一時ファイルで az に渡す。再実行するたびに秘密が新しい値に替わる（漏えい時の再生成を兼ねる）。ID・パスワードは apps/web/.env.basic-auth に書かれる
03-db-firewall.shapi の送信 IP（possibleOutboundIpAddresses）を、講義 MySQL のファイアウォールに guapp-appsvc-<連番> の名前で 1 件ずつ追加する「Azure サービスからのアクセスをすべて許可」は共用設定全体を変えるため使わない。他の受講生の規則は触らず、古い規則の自動削除もしない。公開時は 31 件を追加
04-deploy-api.shCA 証明書を apps/api/certs/ にコピーし、uv export で requirements.txt を作り、不要ファイルを除いた zip を az webapp deploy で配置するrequirements.txt はコミットせず毎回作る（uv.lock との二重管理を避ける）。zip から .venv、tests、.env*、.mail-outbox を除く
05-deploy-web.shpnpm build（standalone 出力）のあと、シンボリックリンクを実体化して zip にし、配置する次の段落を参照。ビルド時の環境変数はダミー値でよい（実行時に本物を読むため）
06-migrate-seed.sh講義 MySQL に対して alembic upgrade head を実行する。--seed を付け、確認に答えたときだけ seed も実行するseed は --reset --yes で既存データを消すため、統括の指示があるときだけ。資格情報の扱いは with-azure-db.sh に任せる
90-stop.sh公開期間の終了後に、web・api を停止する（削除はしない）停止中もプランの基本料金は続く
99-delete.shApp Service、プラン、講義 MySQL の guapp-appsvc-* 規則を削除するdelete と入力する確認は、GUAPP_ASSUME_YES=1 でも省略できない。講義 MySQL 本体・スキーマ・共用のリソースグループは消さない
README.md実行順序、動作確認の curl、期限の延長、停止・削除、費用の目安、つまずきやすい点実行前に統括の承認を得る、という注意書きが冒頭にある

05-deploy-web.sh がシンボリックリンクを実体化するのは、pnpm の node_modules が大量のシンボリックリンクでできていて、zip にして Azure 側で展開すると壊れたためです。スクリプト冒頭のコメントと公開環境の確認記録によると、経緯は次のとおりです。まず zip をそのまま使うと、リンク先の実体（@swc/helpers など）が欠けて起動に失敗しました。次に zip -y でリンクのまま格納すると、Mac で作ったリンクを Azure 側が「リンク先の文字列を中身とする通常のファイル」として展開し、SyntaxError で起動に失敗しました（コメントは、展開時の解釈の違いと推定している）。そこで rsync -a --copy-links でリンクを実体に置き換えた一時フォルダを作ってから zip にしました。

実体化だけでは、今度は next が必要とする兄弟パッケージを見つけられなくなりました。Node はリンク越しに読んだファイルの実体パスを基準にモジュールを探すため、コピーで独立した実体にすると探索が効かなくなるからです。このため、pnpm が標準で作る共有フォルダ node_modules/.pnpm/node_modules/ の中身を、トップレベルの node_modules/ に重ねてコピーして解決しています。あわせて、リポジトリが iCloud 同期の Desktop 配下にあり、node_modules 3 のような複製フォルダが混ざるため、それを除外し、コピー後にリンクの数と複製名の数を数えて 0 でなければ中止します。この対応を入れた 4 回目のデプロイで、web が起動しました。

api の起動コマンドが gunicorn ではなく uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 2 なのは、gunicorn が依存に入っておらず、依存の追加に承認が必要なためです（設計仕様書 公開追補の DS-DEC-54）。--workers 2 のためレート制限がワーカーごとに数えられる点は第 4 章にあります。az webapp deploy は「Site failed to start within 10 mins」でタイムアウト表示になることがありますが、api と web の両方で、Azure 側ではその後も起動処理が続き、数分後に正常起動したと記録されています。

講義の DB への接続：接続先を検査してからコマンドを実行する

手元から講義の MySQL に対して、マイグレーションや seed を実行するための仕組みが with-azure-db.sh です。with-azure-db.sh <コマンド...> の形で、そのコマンドに接続用の環境変数を付けて実行します。資格情報の扱いが最重要で、値を画面にもログにも出さないように作られています。

CA 証明書を用意する（初回のみ）

fetch-ca.sh が公開されている 3 つの証明書を束ね、リポジトリの外の ~/.config/guapp/azure-mysql-ca.pem に保存する。

資格情報を読む

apps/api/.env.azure（DB_USER・DB_PASSWORD の 2 行、権限 600）だけを読み、値は表示しない。

接続 URL を組み立てて検査する

パスワードを URL エンコードして URL を作り、ホストとスキーマ名が固定値（gen12-mysql-pos…・guapp_nonooktk）と一致しなければ中止する。検査は環境変数経由の Python で行い、コマンドライン引数に載せない。

環境変数を付けて実行する

DATABASE_URL、DB_POOL_SIZE=5、DB_MAX_OVERFLOW=5 を付けて、渡されたコマンドを exec で実行する。

ホスト名とスキーマ名を環境変数で上書きできない固定値にしているのは、上書き用の変数を用意すると検査もその変数を参照することになり、検査の意味がなくなるためです（スクリプト内のコメント）。check_connection.py は SELECT 1 と SSL の暗号方式を読むだけの疎通確認で、例外メッセージに接続文字列が混ざる場合に備えてパスワード部分を伏せてから表示します。

講義サーバーの結合テストは実行しない決まりです（共用サーバーへの負荷とデータの汚染を避けるため。DS-DEC-44）。with-azure-db.sh 経由で動かしてよいのは、マイグレーション、seed、疎通確認、単体テストです。本物の氏名・住所・電話・メールも入れません。

DB への SSL 接続は、DATABASE_URL に ssl_ca=<CA 証明書のパス> のクエリを付ける形で行います（scripts/azure-deploy/02-settings.sh の DATABASE_URL の組み立てと、with-azure-db.sh の L82）。公開環境の証明書は、04-deploy-api.sh が zip に同梱し、App Service 上の /home/site/wwwroot/certs/azure-mysql-ca.pem を指します。

環境変数の一覧：名前と役割（値は書かない）

api の設定は Settings、web の設定は validateEnv が受け取るものが正本です。ローカルでは api が apps/api/.env、web が apps/web/.env.local に書き、公開環境では 02-settings.sh が App Service のアプリ設定に入れます。どちらの .env もコミットできません（.gitignore と pre-commit の二重）。
