    4. X-Forwarded-For: 203.0.113.7, 10.0.0.1 を付けると、別の IP として数えられ 200 に戻る。

事実: このテストは、FastAPI に直接 X-Forwarded-For を付けて送ります。BFF 経由のとき利用者の送った値が使われないことは、別のテスト（it-bff-01-02 と st-sec-xff.client-ip）が確かめます。

予備: test_ut_rate_limit_100_ok_101_limited_with_retry_after ✅ 通過（ローカル・CI とも） — テスト設計書に対応する UT の ID なし

SlidingWindowRateLimiter を、時計を差し替えて単体で確かめる。同じキーで 100 回は通り、101 回目は 1〜3,600 の Retry-After が返る。別のキーは別カウントで、窓の 3,600 秒が過ぎるとまた通るようになり、reset() で全部消える。IT-023-02 と同じ境界を DB なしで確かめるテストなので、CI でも動く。

詰まりそうな質問

1〜2分他人の注文番号を総当たりで試されたら、どうなりますか

当てるには、注文番号とメールアドレスの両方が必要です。注文番号の後ろの 8 文字は 32 種類から選ぶので、約 1.1 兆通り（32 の 8 乗）あります。番号が無い場合もメールが違う場合も、同じ 404 を返すので、注文があるかどうかも分かりません。1 つの IP からの照会は、1 時間に 100 回までです（404 になった呼び出しも数えます）。

追撃: その制限は、公開環境でも掛かっていますか

掛かり方に穴が 2 つあります。1 つ目は、公開環境では IP の設定漏れで、利用者全員が 1 つの枠を共有する見込みであることです（コード解説書 9 章 A1。直す予定ですが、まだ直していません）。2 つ目は、ワーカーごとに数えるので、最大 200 回まで通ることです（同 B1。設計書 9.4 に既知として書いてあり、P2 で対応します）。

1〜2分レート制限の IP は、どう決めていますか

IP を決めるのは BFF の resolveClientIp で、FastAPI にはその値を X-Forwarded-For に載せて渡します。利用者が付けたヘッダーは使いません。信頼するプロキシの段数（TRUSTED_PROXY_HOPS）が 0 のときは接続元だけを使い、1 以上のときは App Service が付ける X-Client-IP を使います。それが無ければ、X-Forwarded-For を右から数えた位置の値です。FastAPI は、受け取った値の先頭を IP として数えます。

ST 実施記録の 2026-09-24 の指摘で、問題が見つかりました。利用者の X-Forwarded-For をそのまま転送していたため、ヘッダーを付けるだけで制限を逃れられたのです。これは PR #27 で今の形に直しました。公開環境で段数の設定が抜けている点は、上の A1 のとおりです。

0〜1分完了画面をリロードしたり、別のタブで開いたりしたらどうなりますか

同じタブでリロードしたときは、sessionStorage の guapp.lastOrder が残っているので、同じ注文がまた表示されます。タブを閉じたあとや、別のタブで URL を開いたときは、保存した注文が無いので、照会フォームが出ます（注文番号は URL から入り、メールアドレスは自分で入力します）。URL の注文番号が保存済みの注文の番号と違うときも、保存済みの注文は見せず、照会フォームを出します。別タブから照会する流れは、手動テストの ST-F025-01 で確認しました（2026-09-18）。
