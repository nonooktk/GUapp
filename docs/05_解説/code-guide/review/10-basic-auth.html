10. Basic 認証と公開期間の帯

指定のされ方と 30 秒版

「サイトへのアクセスをどう制限していますか」「認証の仕組み」「公開環境の守り方」「ヘッダーの上の『期間限定で公開』の帯」

30 秒版

レビュー用に公開しているサイトは、Next.js の proxy.ts で、全ページと BFF の /api/* に Basic 認証をかけています。ID とパスワードは環境変数で管理していて、照合は、かかる時間が一定になる比較で行っています。この認証は Next.js の中だけで完結していて、FastAPI までは届きません。全ページの上に出る「期間限定で公開しています」の帯は、環境変数の終了日を layout.tsx が読んで表示しています。

この章で扱うのは、個別の機能というより、全ページにかかる仕組みです。ID とパスワードの値そのものは、この手引きにもコードにも書いていません（環境変数にだけあります）。

② 画面からバックエンドへ（proxy で判定されるまで）

Next.js 16 で、従来の middleware.ts が proxy.ts に名前を変えました。ページの表示も /api/* も、ルートの処理に入る前に、まずここを通ります。

  1. config.matcher。_next/static・_next/image・favicon.ico・sitemap.xml・robots.txt を除く全リクエストが対象。/api/* も含む。

    静的ファイルを除いた、全ページと BFF が対象です。静的ファイルは、ファイル名にハッシュが付いていて、中身もビルドの成果物なので、対象から外しました（公開追補 7.1）。

    次へ: 同じファイルの basicAuthConfig へ

  2. モジュールの読み込み時に 1 回だけ、環境変数から設定を作る。

    環境変数を読むのは、起動後にこのファイルを最初に読み込むときの 1 回だけです。リクエストのたびには読みません。

    次へ: parseBasicAuthConfig にカーソルを置いて F12

  3. 両方未設定なら null（認証なし）。片方だけなら BasicAuthConfigError を投げる。

    両方とも空なら、ローカル開発用に認証なしで通します。片方だけ入っているのは設定ミスなので、例外を投げます。無防備なまま公開してしまう事故が、全リクエストの失敗という形で表に出るようにしています。

    次へ: ⌘P で apps/web/proxy.ts に戻り、proxy 関数へ（⌃- で戻る）

  4. proxy。Authorization ヘッダを取り、verifyBasicAuthHeader に ID・パスワードの期待値と一緒に渡す。

    リクエストのヘッダを、期待する ID・パスワードと照らし合わせます。

    次へ: verifyBasicAuthHeader にカーソルを置いて F12

  5. 書式の確認、base64 の復号、最初のコロンで ID とパスワードに分ける。例外は投げず、書式が違えば false。

    書式が違う場合も、base64 が壊れている場合も、コロンが無い場合も、どれも「認証失敗」として扱います。例外は投げません。

    次へ: 下の timingSafeEqualString(user, expectedUser) の関数名にカーソルを置いて F12

  6. SHA-256 で固定長にしてから timingSafeEqual で比べる。

    入力の長さが違うせいで比較が早く終わることのないよう、先に固定長のダイジェストにしてから比べます。ID とパスワードは別々に比べて、両方とも比べ終えてから結果を合わせます。

③ バックエンドの処理

FastAPI には届きません。proxy は Next.js の中の処理で、認証に失敗したリクエストは、ここで 401 を返して終わります。認証に通ると NextResponse.next() で通常のページや BFF の処理に進みます。その先は他の章で扱う経路です。

  1. 認証に失敗したときの応答。本文なしの 401 に WWW-Authenticate: Basic realm="GUapp demo" を付ける。

    失敗したら、本文なしの 401 を返して終わります。ブラウザはこのヘッダを手がかりに、ID とパスワードの入力欄を出します。

    次へ: 同じ関数の先頭へスクロール

  2. 設定が両方未設定（null）のときは認証せずに通す分岐。

    環境変数が無いローカル開発では、認証なしで通します。公開環境では、アプリ設定に両方とも入れています。

④ 応答から表示まで（帯の表示）

ここからは、認証に通ったあと全ページの上に出る「期間限定で公開しています」の帯の話です。終了日は環境変数 DEMO_PUBLIC_UNTIL（YYYY-MM-DD）で指定します。NEXT_PUBLIC_ を付けていないので、ビルドし直さなくても、値を変えて延長できます（公開追補 6.1、DS-DEC-50）。

  1. RootLayout。実行時の環境変数を読み、parseDemoPublicUntil で検証して YYYY/MM/DD にする。

    全ページ共通のレイアウトが、環境変数の終了日を読みます。

    次へ: parseDemoPublicUntil にカーソルを置いて F12

  2. 未設定・空は null（警告なし）。形式が違う日付と、実在しない日付は警告を出して null。

    形式を間違えていても、例外にはしません。帯を出さずに警告だけ残して、環境変数 1 件の誤りでサイト全体が止まらないようにしています。

    次へ: ⌘P で apps/web/components/DemoPeriodBanner.tsx を開く

  3. 文字列が null なら何も描画しない。あれば role="status" の帯に終了日を入れる。

    帯の文言に「期間限定」「デモ」と書いてあるので、色が見えなくても意味が伝わります。本番でも常に表示します。

帯の文言は の行、配置は の行です（ヘッダーより前）。

⑤ テスト 1 本の説明

推しは、環境変数が片方だけのときに、起動時（モジュールの読み込み時）に失敗することを確かめる UT-WEB-09 の 1 本です。設計判断（DS-DEC-49）の「設定ミスのまま無防備に公開しない」に対応します。 ✅ 通過（ローカル） web のテストなので CI でも実行されます。

  • テスト: ut-web-09.proxy-basic-auth.test.ts の「片方だけ設定されていると import 時（起動時相当）に BasicAuthConfigError で失敗する」（テスト設計書 公開追補 3.1。ST-SEC-16b に当たる UT レベルのテスト）
  • 前提: テストごとに環境変数を作り直し、vi.resetModules() を呼ぶ。proxy.ts は読み込み時に環境変数を 1 回だけ評価する設計のため、読み込み直すたびに結果が変わる。
  • 操作: BASIC_AUTH_USER だけを設定し、proxy を動的 import で読み込む。
  • 確認: で、読み込みが BasicAuthConfigError で失敗する。instanceof でなく name で比べているのは、vi.resetModules() のあとはクラスが別のモジュールインスタンスになりうるため（コメントに記載）。

実装側は、parseBasicAuthConfig の BasicAuthConfigError と、basicAuthConfig の読み込みです。同じ describe には、次の 5 本があります。両方未設定なら 401 にしないこと、Authorization ヘッダが無ければ 401 と WWW-Authenticate を返すこと、誤った認証は 401 になること、正しい認証は 401 にならないこと、config.matcher の中身です。ID・パスワードの正誤とヘッダの書式は、ut-web-09.basic-auth.test.ts の 15 本で確かめています。

詰まりそうな質問

1〜2分ID とパスワードはどこで管理していますか

環境変数 BASIC_AUTH_USER と BASIC_AUTH_PASSWORD です。NEXT_PUBLIC_ を付けていないので、ブラウザには出ません。リポジトリにも入れていません。公開環境では、デプロイ用のスクリプト（ の近く）が値をその場で作り、Azure のアプリ設定に入れます。ターミナルには表示しません。レビュワーに伝えるため、ID とパスワードだけは、git の管理対象外にした権限 600 のファイルに残します。

弱点: このスクリプトは、再実行するたびに内部トークンと Basic 認証の値を作り直します（解説書 第 9 章 A1 の補足）。すでに伝えた資格情報が変わってしまうので、反映の方法はその都度選びます。

追撃: Basic 認証だけで十分ですか

意見: レビュー期間に限って、不特定多数には見せない、という目的には足りると考えています。ただ、FastAPI の App Service にはアクセス制限が掛かっていません（設計の方針とは違います。解説書 第 9 章 D4）。FastAPI は内部トークンで守っていて、閉域化は後の対応になります。

1〜2分静的ファイルを認証の対象から外して問題ありませんか

設計の段階で、外すと決めたものです（公開追補 7.1、DS-DEC-48）。_next/static と _next/image はビルド時にハッシュ付きのファイル名になり、そのファイル名は認証済みの HTML からしか分かりません。中身もアプリのコードと画像で、個人情報や非公開の業務データは含みません。

弱点: 除外されていること自体を確かめるテストはありません。自動テストが見ているのは matcher の文字列が仕様どおりかどうかまでで、Next.js がその正規表現でどのパスを除外するかは検証していません。
