    明細は、その時点の単価と商品名をコピーして保存します。商品マスタを後から変えても、過去の注文は変わりません。

    決済が ng のときは、注文を決済失敗の状態で残し、そのあとで在庫とカートを元に戻して、409 を返します。

詰まりそうな質問

1〜2分二重注文や在庫の取り合いは、どう防いでいますか

防ぎ方は 4 段あります。1 段目は画面で、inflight フラグで連打を止めます。ただ、これは使い勝手のための対策で、防御の本体ではありません。2 段目は、同じ冪等キーの 2 本目を orders.idempotency_key の UNIQUE で DB が断り、既存の注文を 200 で返します（IT-014-02: 20 同時でも注文は 1 件）。3 段目は、別の冪等キーで同じカートを 2 回確定しようとした場合です。カートの active → ordered の条件付き UPDATE が 1 回しか通らず、もう一方は 409 already_ordered になります（IT-014-03）。4 段目は在庫で、WHERE stock >= :q の UPDATE 1 文が、足りなければ 0 行になります。CHECK (stock >= 0) もあります（IT-014-04: 在庫 1 に 2 件を同時に送って、成功は 1 件だけ。これを 30 回繰り返す）。

追撃: その結合テストは、CI で動いていますか

動いていません。結合テスト 100 件は CI ではスキップされています（コード解説書 9 章 D3）。ローカルでは通っています。また、防御を外して赤くなることの確認は、2026-09-18 に 3 つとも実施して、総合 PASS でした（scripts/mutation-check/result-20260918.md、テスト設計書 1.4 の #8）。

1〜2分決済に失敗したとき、在庫が戻らなくなることはありませんか

あります。決済 NG の経路は、payment_failed を commit してから、別のトランザクションで在庫とカートを戻す 2 段です。間でプロセスが落ちると、在庫が引かれたまま残ります。設計仕様書 9.4 に、P1 では受け入れる穴として書いてあります。決済スタブは同期で結果を返すので、実害はほぼ無いと見ています。P2 の期限切れ処理で回収する予定です。

そうなった注文を見つける SQL は、コード解説書 9 章の付録 9.6 にあります（payment_failed の注文のカートが ordered のまま残っているものを探す）。2 段目の前で落ちる場合を再現するテストは、今はありません。

0〜1分画面の金額を書き換えられたら、どうなりますか

画面の金額は表示用で、サーバーが確定時の単価と設定から計算し直した値と照合します。1 円でも違えば 409 price_changed で、注文は作られません（IT-014-05、手動の ST-SEC-04 は 2026-09-24 に合格）。確認画面を出したあとに価格が変わった場合も同じ扱いです。画面は注文手続きに戻り、次に確認画面を開くときに金額を取り直します。
