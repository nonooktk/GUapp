1. 商品一覧を表示する

「トップページで商品を表示する」「商品一覧ページ（/products）を表示する」「カテゴリで絞り込んで表示する」「『もっと見る』を押したときの動き」

30 秒版

商品一覧は、初回の表示と「もっと見る」で通る道が違います。初回は、Next.js のサーバー側のページが BFF を通らず、FastAPI の GET /api/v1/products を直接呼びます。「もっと見る」だけは、ブラウザから BFF の /api/products を呼び、BFF が同じ FastAPI に取り次ぎます。FastAPI は内部トークンを確かめたあと、ルーター、サービス、リポジトリの順に処理を進め、公開中の商品を新着順に 24 件、MySQL から読みます。応答には items・total・has_more が入っていて、ProductsGrid が商品カードを並べます。「もっと見る」は、has_more が true の間だけ出します。

② 画面からバックエンドへ

経路は 2 本あり、どちらも着く先は FastAPI の同じエンドポイント（GET /api/v1/products）です。

経路呼ぶ側途中で通る場所使われる場面
A. 初回表示サーバー側のページ（Server Component）lib/server/catalog.ts → apiFetch → FastAPI。BFF は通らないトップのおすすめ 8 件、/products の 24 件、カテゴリ切り替え（URL が変わってページが描き直される）
B. もっと見るブラウザ（ProductsGrid）/api/products（BFF の Route Handler）→ apiFetch → FastAPI2 ページ目以降の追加取得

③ バックエンドの処理

  1. /api/v1 配下のルーターすべてに verify_internal_token が付く。catalog.router の登録もここ。health だけ別で、検証の対象外。

    /api/v1 の下は、この 1 か所で内部トークンの検証が必須になっています。商品一覧のルーターもここに登録されています。

    次へ: verify_internal_token にカーソルを置いて F12

  2. ヘッダー X-Internal-Token が無い、または一致しないと 401 unauthorized。期待値が未設定のときも全拒否。比較は hmac.compare_digest。

    BFF からの呼び出しだけを通す仕組みです。トークンが違えば、中身を見る前に 401 で返します。

    次へ: ⌘P で apps/api/app/routers/catalog.py を開き、⌘⇧O で list_products へ

  3. クエリの検証。page は 1 以上、per_page は 1〜48（PER_PAGE_MAX）、category は 100 文字以内、gender は Gender の列挙。外れると 400 validation_error（FastAPI 既定の 422 をハンドラで変換）。

    入力の形はここで確かめます。たとえば page が 0 だと、400 の validation_error で返ります。

    次へ: catalog_service.list_products にカーソルを置いて F12

  4. リポジトリで一覧と総件数を取り、続けて色をまとめて取る。has_more は page * per_page < total。

    サービスは、一覧と総件数を取り、色の一覧を足して、次のページがあるかどうかを計算します。

    次へ: list_published にカーソルを置いて F12

  5. 件数用の count と本体の SELECT の 2 本。性別・カテゴリの絞り込みは _category_scope（サブクエリ）。ページ送りは offset と limit。

    ここで SQL を組み立てます。先に件数、次に該当ページの分を取ります。

    次へ: summary_select にカーソルを置いて F12

  6. 公開条件 published_filter()、新着順（created_at 降順、同時刻は id 降順）、先頭画像（サブクエリ）はここで決まる。sold_out は、在庫合計（variants を GROUP BY で 1 回集計）から作る。

    非公開の商品は、ここで除かれます。公開の条件は published_filter の 1 か所で、一覧も詳細もカート追加もここを通ります。

    次へ: ⌘⇧O で colors_by_product へ

  7. ページ分の商品 ID をまとめて渡し、1 クエリで色を取る。商品ごとに問い合わせる形（N+1）にはしていない。

    24 件分の色は、1 回の問い合わせでまとめて取っています。

    次へ: ⌘P で apps/api/app/models/catalog.py を開き、⌘⇧O で Product へ

  8. products テーブル（公開フラグ published、税込価格 price_incl_tax）。ほかに画像は product_images、色と在庫は variants、絞り込みは product_categories と categories。

    読むテーブルの中心は products です。画像、色と在庫、カテゴリの対応表をつないで一覧を作ります。

④ 応答から表示まで

  1. 応答は items・page・per_page・total・has_more。items の 1 件は ProductListItemOut（id・name・price_incl_tax・image_path・colors・sold_out）。

    FastAPI が返す形は、この Pydantic のクラスで決まっています。大事なのは、商品の配列、総件数、次のページがあるかどうかの 3 点です。

    次へ: ⌘P で apps/web/lib/server/api.ts を開き、⌘⇧O で apiFetch へ

  2. 2xx なら本文の JSON をそのまま data に入れて返す（整形はしない）。非 2xx は sanitizeErrorBody で {code, …} だけに絞る。

    FastAPI の応答は、成功ならそのまま data に入って返ります。初回表示の経路では、BFF による整形はありません。

    次へ: ⌘P で apps/web/lib/server/catalog.ts を開き、⌘⇧O で loadOrNull へ

  3. 失敗（非 2xx・接続不可）は null を返し、ログだけ残す。成功なら data。

    失敗したときは null を返す取り決めになっていて、ページ側は null なら「読み込めませんでした」を出します。FastAPI が止まっていても、画面は崩れません。

    次へ: ⌘P で apps/web/app/products/page.tsx を開く

  4. list === null なら LoadError。そうでなければ ProductsGrid に initialItems・initialPage・hasMore・total を渡す。見出し横の件数は list.total。

    取得に失敗していれば LoadError を出し、成功なら、取れた商品と総件数を ProductsGrid に渡します。

    次へ: ProductsGrid にカーソルを置いて F12

  5. 渡された 24 件が state の初期値。0 件なら「該当する商品がありません」。1 件以上は ProductCard を並べ、「{表示数} / {total} 件を表示」を出す。「もっと見る」は more（has_more）が true の間だけ。

    最初の 24 件は、サーバーから渡されたものをそのまま state の初期値にしています。次のページがある間だけ、「もっと見る」を出します。

    次へ: ProductCard にカーソルを置いて F12

    商品カードが 1 件分の表示です。全バリエーションの在庫が 0 の商品は、価格の代わりに「在庫切れ」と出します。

  1. 成功は FastAPI の本文をそのまま 200 で返す（Cache-Control: no-store）。失敗は result.error を元のステータスで返す。接続不可は 503 upstream_unavailable、想定外は 500 internal_error。

    BFF は、成功なら FastAPI の応答をそのまま返し、失敗ならエラーの code だけを返します。

    次へ: ⌘P で apps/web/lib/client/cart-api.ts を開き、⌘⇧O で requestJson へ

  2. 2xx 以外は CartApiError（status と body）を投げる。2xx は JSON を返す（本文が空なら bad_response）。fetchProductsPage の戻り値は ProductListResponse。

    ブラウザ側の fetch は、失敗なら例外、成功なら JSON を返します。

    次へ: ⌘P で apps/web/components/ProductsGrid.tsx を開き、loadMore の続きを見る

  3. 返った items から、すでに表示している id を除いて末尾に足す。page と more は応答の page・has_more で更新する。

    返ってきた商品のうち、すでに画面にあるものは除いて、末尾に足します。表示中に新着が増えて 1 ページの境目がずれても、同じ商品は 2 回出ません。

    次へ: 同じ関数の下の catch を見る

  4. どんな失敗でも同じ文言。role="alert" で表示し、finally で処理中を解除するので押し直せる。ステータスごとの出し分けはしない。

詰まりそうな質問

0〜1分なぜ初回表示は BFF を通らないのですか

設計仕様書 4.3 に、サーバー間通信なら BFF を通さなくてよいと決めてあります。サーバー側のページは Next.js のサーバーの中で動くので、FastAPI の URL も内部トークンもブラウザには出ません。BFF が必要なのは、ブラウザの JavaScript から呼ぶ経路（「もっと見る」・カート操作・注文）だけです。

追撃: BFF を通さないと CSRF の検証は抜けませんか

一覧は読み取りだけなので、CSRF の検証が要る操作ではありません。状態を変える操作（カートへの追加など）は、すべて BFF を通り、CSRF を確かめています。

1〜2分非公開の商品が一覧に出ないことは、どう保証していますか

公開の条件は published_filter の 1 か所で、一覧・詳細・関連商品・カート追加がすべてこれを通ります。確かめているのは、IT-002-01（一覧に非公開商品の名前が無い）、IT-003-02（詳細は 404）、手動の ST-F001-02 です。ただし結合テストは CI でスキップされるため、自動で守られているのは手元で実行したときだけです。

1〜2分「もっと見る」で同じ商品が重複したり、取りこぼしたりしませんか

重複は ProductsGrid が id で除いています。取りこぼしの対策は入れていません。並びは created_at 降順なので、閲覧中に新商品が登録されると、ページの境目で 1 件ずれる可能性があります。P1 は seed の固定データで、閲覧中に商品が増えることは想定していません（これは私の見立てで、コードにこの前提を書いた記述はありません）。
