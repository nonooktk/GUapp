2. 商品詳細を表示し、色・サイズを選ぶ

「商品詳細ページを表示する」「色・サイズを選ぶと在庫の表示が変わる」「在庫切れの商品を選んだときの表示」「商品カードを押して詳細へ行く」

30 秒版

商品詳細は、一覧の初回表示と同じ経路です。Next.js のサーバー側のページが、BFF を通らずに FastAPI の GET /api/v1/products/{id} を直接呼びます。FastAPI は公開中の商品だけを引いて、色・サイズごとの在庫の有無、画像、関連商品 4 件を付けて返します。在庫は、あるかないかだけを返します。残りの数は返しません。色とサイズを選んだときの判定は、ブラウザ側の PurchasePanel が、受け取った variants の一覧を見て、画面の中だけで行います。選んだ組み合わせが無いか、在庫が無いときは「在庫切れ」を出して、追加ボタンを無効にします。この選択では API を呼びません。

② 画面からバックエンドへ

事実: 詳細の表示は、一覧の初回表示（経路 A）と同じで、BFF を通りません。app/products/[id]/page.tsx の Server Component が、lib/server/catalog.ts の getProduct を経由して FastAPI を直接呼びます。この画面には、ブラウザから API を呼ぶ経路がありません。色・サイズを選ぶ操作でも API は呼びません（④ で説明します）。

  1. 一覧・トップ・関連商品のカードは、/products/{id} へのリンク。ふつうの Link で、ここでは API を呼ばない。

    商品カードは、/products/商品 ID へのリンクです。API を呼ぶのは、リンク先のページが開くときで、サーバー側から商品の情報を取りに行きます。

    次へ: ⌘P で apps/web/app/products/[id]/page.tsx を開く

  2. id は 1〜18 桁の数字だけ通す。外れたら notFound()（）を呼び、API は呼ばない。通れば getProduct(id) を呼ぶ。Next.js 16 では params が Promise なので await する。

    詳細のページも、サーバー側で動く Server Component です。getProduct を呼んで商品を取ります。id が数字でなければ、API は呼ばずに 404 の画面にします。

    次へ: getProduct にカーソルを置いて F12

  3. /products/{id} を組み立て、apiFetch（一覧と同じ関数で、X-Internal-Token を付ける）から FastAPI を呼ぶ。BFF の Route Handler は通らない。

    一覧と同じ仕組みです。BFF は通らずに、サーバーから FastAPI を直接呼びます。内部トークンは、apiFetch が付けています。

    次へ: URL の文字列なので F12 では飛べない。⌘⇧F で /products/{product_id} を検索し、apps/api/app/routers/catalog.py を開く

  4. @router.get("/products/{product_id}")。ここがリクエスト先のバックエンド。product_id を受け取って、サービスを呼ぶだけの関数。

    リクエスト先は、FastAPI の GET /api/v1/products/商品 ID です。コードでは、routers/catalog.py の get_product にあたります。

事実（設計書との差）: 設計仕様書 4.3 の BFF 表には /api/products/[id] がありますが、実装にはありません。Server Component が直接呼ぶからです。同じ表の注記「BFF を経由しなくてよい」とは矛盾しません。

③ バックエンドの処理

  1. /api/v1 配下のルーターすべてに、verify_internal_token が付く。catalog.router もここで登録している。

    /api/v1 の下は、この 1 か所の指定で、すべて内部トークンの検証が必須になります。

    次へ: verify_internal_token にカーソルを置いて F12

  2. X-Internal-Token が無いか、一致しないと 401 unauthorized。

    BFF 以外からの呼び出しは、ここで 401 になります。

    次へ: ⌘P で apps/api/app/routers/catalog.py を開き、⌘⇧O で get_product へ

  3. パスの product_id を整数として検証する。整数でなければ 400 validation_error。業務上の判定はしない。

    ルーターがやるのは、商品 ID が整数かどうかの確認だけです。あとはサービスに渡します。

    次へ: catalog_service.get_product_detail にカーソルを置いて F12

  4. 公開商品が無ければ 404 not_found（非公開と存在しないは区別しない）。あれば variants・画像・関連商品を順に取る。in_stock は stock > 0 で決め、色とサイズは出てきた順のまま重複を除く。

    サービスは、まず公開中の商品かどうかを見ます。非公開の商品と存在しない商品は、どちらも同じ 404 です。そのうえで、色・サイズごとの在庫の有無を、在庫が 0 より大きいかどうかで決めます。

    次へ: products_repo.get_published にカーソルを置いて F12

  5. published_products()（公開条件つきの SELECT）に、ID の条件を足す。

    公開の条件は、一覧と同じ published_filter です。

    次へ: ⌘⇧O で list_variants へ

  6. その商品の variants（色・サイズ・在庫）を id 順に取る。

    色とサイズの組み合わせごとの行を、ここで全部取ってきます。

    次へ: ⌘⇧O で list_related へ

  7. 同じカテゴリの公開商品から、自分を除いて新着順に RELATED_LIMIT（4）件。

    関連商品は、同じカテゴリの公開商品のうち、新着順に 4 件です。商品自身は除きます。

    次へ: ⌘P で apps/api/app/models/catalog.py を開き、⌘⇧O で Variant へ

  8. variants テーブル（color・size・sku・stock）。stock は 0 以上の CHECK 付き。画像は product_images。

    在庫の数は、variants の stock 列にあります。API が画面に返すのは、その数ではなく、0 より大きいかどうかだけです。

④ 応答から表示まで

  1. 応答は id・name・description・material・price_incl_tax・images・colors・sizes・variants・related。VariantOut は variant_id・color・size・in_stock（真偽）で、残りの数は含まない。

    FastAPI が返す形は、この Pydantic のクラスで決まります。在庫は、あるかないかの真偽値だけです。

    次へ: ⌘P で apps/web/app/products/[id]/page.tsx を開く

  2. 404 は notFound()（404 の画面）。それ以外の非 2xx は、ステータスと code をログに出して、「商品情報を読み込めませんでした」の LoadError にする。接続できないとき（UpstreamUnavailableError）も同じ LoadError。

    取得できなかったときは、404 なら 404 の画面を出します。それ以外は「読み込めませんでした」の表示です。

    次へ: 同じ関数の下へ進み、PurchasePanel を呼ぶ行を見る

  3. 画像（複数枚は横スクロール）、名称、税込価格（Price に「（税込）」）を表示し、PurchasePanel に colors・sizes・variants を渡す。そのあとに、説明・素材・サイズの一覧と、関連商品（ProductCard を最大 4 件）が続く。

    取れた商品の情報を、画面に並べます。色・サイズ・バリエーションの一覧は、購入操作を受け持つ PurchasePanel に渡します。

    次へ: PurchasePanel にカーソルを置いて F12

  1. 色とサイズの選択は useState で持つ。1 種類しかない商品は、最初から選択済み。数量は 1〜10 のセレクト（MAX_QUANTITY_PER_ITEM）。

    選んだ色とサイズは、ブラウザの中の state に持っています。色やサイズが 1 種類しかなければ、最初から選ばれた状態です。

    次へ: ⌘⇧O で resolveVariant へ

  2. 純粋関数。色とサイズが両方選ばれ、その組み合わせが variants にあれば variant、無ければ null。

    色とサイズの組み合わせから、バリエーションを 1 つ決める関数です。受け取った variants の中から探すだけなので、API は呼びません。

    次へ: ⌘⇧O で PurchasePanel に戻り、outOfStock の行へ

  3. 在庫切れになるのは、「両方選択済み」で、組み合わせが無いか in_stock が false のとき。canAdd は、在庫ありで、処理中でないとき。

    色とサイズを両方選んだあとで、その組み合わせが無いか、在庫が無ければ、在庫切れとして扱います。

    次へ: 下の stockLabel の行へ

  4. 表示は 3 通り。「色とサイズを選択してください」「在庫切れ」「在庫あり」。aria-live="polite"。追加ボタンは disabled={!canAdd} で、在庫切れならラベルも「在庫切れ」。

    表示は、未選択、在庫切れ、在庫ありの 3 通りです。在庫切れのときは、追加ボタンを無効にして、ボタンの文言も「在庫切れ」に変えます。

    次へ: 下のチップの行 isCombinationOut(c, size) へ

  5. 相手側（サイズ）が選択済みなら、その組み合わせが在庫切れになる色チップに、取り消し線を引き、「（在庫切れ）」を付けた aria-label を出す。サイズ側も同じ。

    両方を選び終える前でも、在庫の無い組み合わせは、チップの取り消し線で分かるようにしてあります。

    次へ: 同じ関数の最後、data-testid="sticky-bar" の固定バーへ

  6. 375px 幅の下部固定バー。選択内容（色 / サイズ / 数量）と、価格 × 数量、追加ボタン。sm 以上では出ない。

    スマホの幅では、画面の下にバーを固定で出します。スクロール中でも、カートに入れられます。

詰まりそうな質問

0〜1分在庫の残り数は画面に出さないのですか

出していません。API の VariantOut にあるのは in_stock（在庫が 0 より大きいかどうか）だけで、残数は応答に含めない作りです。設計仕様書 6.5 も、求めているのは在庫の有無までです。残数が足りるかどうかは、カートに入れたあとで、カート画面の stock_status（insufficient）に出ます。

1〜2分表示したときは在庫ありだったのに、押したら売り切れていたらどうなりますか

ページは force-dynamic で、毎回 API から取り直します。ただ、表示してから押すまでの間に在庫が変わることはあります。その場合は、追加の API が在庫をもう一度判定して、409 out_of_stock を返すので、「在庫切れのため追加できません」というトーストが出ます（3 章の順路）。

0〜1分非公開の商品の URL を直接開くとどうなりますか

404 の画面になります。FastAPI が、非公開の商品と存在しない商品を区別せず、どちらにも同じ 404 not_found を返すからです。確認は、IT-003-02 と、手動の ST-F001-02 です。
