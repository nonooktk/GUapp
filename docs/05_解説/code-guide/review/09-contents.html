9. FAQ・お知らせ・静的ページ

指定のされ方と 30 秒版

「FAQ を表示する機能」「お知らせを表示する機能」「トップのお知らせ欄」「利用規約などのページを表示する機能」

30 秒版

お知らせ・特集の一覧と、FAQ や利用規約などのページは、Next.js のサーバー側から FastAPI のコンテンツ API を直接呼んで表示します。ブラウザ向けの BFF は作っていません。FastAPI が返すのは掲載期間内の行だけで、お知らせは新しい順です。FAQ などは slug で 1 件取ります。存在しない場合も、掲載期間外の場合も、対象外の種別の場合も、区別せず 404 にします。本文はプレーンテキストで、React 標準のエスケープだけで描画します。

② 画面からバックエンドへ

この機能に BFF（/api/*）はありません。画面は Server Component で、lib/server/contents.ts から FastAPI を直接呼びます（設計仕様書 P2 追補a 1 章）。最初はお知らせ・特集の一覧です。トップのお知らせ欄（、3 件）も、同じ関数を使っています。

  1. ContentsPage。お知らせは常に取得し、特集は ?kind=news でないときだけ取得する。上限は 20 件。

    お知らせと特集を、サーバー側でまとめて取りに行きます。?kind=news を付けると、お知らせだけになります。

    次へ: getContents にカーソルを置いて F12

  2. getContents。kind と limit のクエリを付けて /contents を呼ぶ。

    種類は feature と news の 2 つだけで、型もその 2 つに絞っています。

    次へ: apiFetch にカーソルを置いて F12

  3. apiFetch。内部トークンを付けて FastAPI を呼ぶ共通の関数（検索と同じもの）。

    FastAPI を呼ぶ共通の関数です。接続できなければ例外を投げます。ページ側はそれを受けて、「読み込めませんでした」と表示します。

    次へ: ⌘⇧F で "/contents" を検索（routers/content.py を開く）

  4. ルーター list_contents（GET /api/v1/contents、DS-API-005）。kind は Literal、limit は 1〜20。

    ここが呼び出し先です。種類と件数の範囲の検査も、ここで行います。

    次へ: list_contents にカーソルを置いて F12

続いて、FAQ・利用規約などの静的ページです。フッターの 5 つのリンクと、メニューの FAQ・INFO は、どれもここに来ます。

  1. フッターのリンク定義。faq に terms・privacy・tokushoho・company を加えた 5 つ。

    フッターの「FAQ」は /contents/faq へのリンクです。規約などの 4 つも、同じ形のリンクです。

    次へ: ⌘P で apps/web/app/contents/[slug]/page.tsx を開く

  2. ContentDetailPage。URL の slug で 1 件取る。接続できないときは UpstreamUnavailableError を受けて、「ページを読み込めませんでした」と表示する。

    どの slug も同じ画面で表示します。取得は Next.js のサーバー側で行います。

    次へ: getContent にカーソルを置いて F12

  3. getContent。slug を URL エンコードして /contents/{slug} を呼ぶ。

    slug をパスに入れて呼びます。

    次へ: ⌘⇧F で "/contents/{slug}" を検索

  4. ルーター get_content（GET /api/v1/contents/{slug}、DS-API-006）。slug は Path(pattern=…) で検査する。

    ここが呼び出し先です。slug は、^[a-z0-9-]{1,100}$ の形だけを受け付けます。

    次へ: get_content_detail にカーソルを置いて F12

③ バックエンドの処理

  1. サービス list_contents。現在時刻（UTC）を作り、リポジトリに渡す。

    時刻の比較は UTC で行います。日本時間にするのは、画面に出すときだけです（DS-DEC-40）。

    次へ: list_by_kind にカーソルを置いて F12

  2. kind と掲載期間で絞る SQL。お知らせは publish_from の新しい順、特集は sort_order の昇順。

    一覧は、掲載期間内の行だけを SQL の条件で絞り込んで取ります。

    次へ: _published_at にカーソルを置いて F12

  3. 「publish_from <= now かつ（publish_to が空、または publish_to >= now）」の条件。

    終了日が空なら無期限です。境界ちょうどの日時も、掲載中として扱います。

    次へ: ⌘⇧O で services/content.py の get_content_detail へ（詳細の経路）

  4. 詳細は、種別（faq・static）と slug で 1 行取ってから、サービスで掲載期間を判定する。

    詳細は一覧と違い、先に行を取ってから、関数で期間を判定します。行がない場合も期間外の場合も、同じ 404 にします。

    次へ: is_within_publish_window にカーソルを置いて F12

  5. DB を使わない純粋関数。now < publish_from だけが「まだ」、now > publish_to だけが「終了」で、等号は掲載中。

    DB に触らない関数なので、単体テストで境界を確かめています。

状況どこで判定するか応答画面側の扱い
kind が feature・news 以外（例: faq）、limit が 0 や 21 以上ルーターの Literal・Query(ge, le)400 validation_error画面は feature・news しか指定しないので起きない
slug が ^[a-z0-9-]{1,100}$ に合わない（例: 大文字）ルーターの Path(pattern=…)400 validation_error画面は slug の形を事前に確かめない。notFound() にはならず、「ページを読み込めませんでした」と表示される
slug が無い、種別が feature・news、掲載期間外get_by_slug が空、または is_within_publish_window が偽404 not_found（3 つを区別しない）notFound() でサイト共通の 404 画面
FastAPI に接続できないapiFetch が UpstreamUnavailableError を投げる（BFF が無いので応答は無い）お知らせ欄・特集欄・各ページで、それぞれ「読み込めませんでした」と表示する
一覧が 0 件エラーではない200、items は空配列「お知らせはまだありません」「特集はまだありません」

④ 応答から表示まで

  1. 応答が失敗だったときの分岐。404 なら notFound()。それ以外はログに残して、「読み込めませんでした」と表示する。

    404 のときは、存在しないページと同じ画面を出します。期間外かどうかは、利用者には分かりません。

    次へ: 同じ関数の下へスクロールして本文の描画を見る

  2. 本文の描画。特商法（tokushoho）だけ定義リスト、ほかは whitespace-pre-line の段落。

    本文はプレーンテキストです。dangerouslySetInnerHTML は使わず、React 標準のエスケープだけで描画します。改行は whitespace-pre-line で保ちます（DS-DEC-38）。

    次へ: ⌘P で apps/web/app/contents/page.tsx を開く（お知らせ一覧）

  3. お知らせ一覧の日付。応答の publish_from（UTC）を日本時間の日付にして出す。

    お知らせに出るのは日付とタイトルだけで、個別ページへのリンクはありません。お知らせと特集には、個別の URL を作らない設計です。

    次へ: formatJstDate にカーソルを置いて F12

  4. formatJstDate。Asia/Tokyo で YYYY-MM-DD にする。

    掲載の判定は UTC のまま、表示だけ日本時間にします。

⑤ テスト 1 本の説明

推しは、掲載期間の境界を確かめる UT-CONTENT-02 です。 ✅ 通過（ローカル） unit なので、CI でも実行されます。

  • テスト: test_ut_content_02_boundary_equal_now_is_published（テスト設計書 P2 追補a 5.1）
  • 前提: 現在時刻を固定値（NOW）にする。DB は使わない。
  • 操作: publish_from も publish_to も NOW と同じ値にして、 を実行する。
  • 確認: ちょうど今は「掲載中」になる。判定が <・> ではなく、等号を含むことを確かめる。実装は is_within_publish_window の 2 つの比較にあたる。

同じファイルの test_ut_content_02b_… は公開開始の 1 秒前、test_ut_content_02c_… は公開終了の 1 秒後の時刻で判定し、どちらも「掲載外」になることを確かめます。この 3 本で、境界の両側がそろいます。

期間外のものが API の応答に出ないことは、IT-005-02（一覧）と IT-006-04（詳細は 404）が MySQL で確かめています。✅ 通過（ローカル） ⏭ CI ではスキップ

詰まりそうな質問

1〜2分お知らせや特集に、個別のページが無いのはなぜですか

設計で、個別の URL は用意していません（設計仕様書 P2 追補a 4.3）。理由は、特集とお知らせは一覧からの導線だけで足りること、FAQ や規約などはフッターから直接リンクする固定ページであることです。API も、詳細（/contents/{slug}）が返すのは faq と static だけです。

追撃: お知らせのタイトルをクリックできないのは不便では

意見: 本文を読ませたいなら、種別の制限を外して個別ページを作ることになります。P2-a の要件にはなかったので、作っていないと答えます。

1〜2分本文にスクリプトを入れられたらどうなりますか

本文はプレーンテキストとして扱い、描画は React 標準のエスケープだけで行います。HTML や Markdown としては解釈せず、dangerouslySetInnerHTML も使っていません。入れられても、画面には文字のまま出ます（DS-DEC-38、ST-SEC-13）。

弱点: これを確かめる自動テストはありません。検索結果の画面には、同じ趣旨のテスト（検索語に HTML を含めても文字として表示される）があります。コンテンツの画面にも同種のテストを足すなら、ContentDetailPage を対象にするのが近道だと思います。
