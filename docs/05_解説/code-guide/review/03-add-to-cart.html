3. カートに入れる

「カートに入れるボタンを押す」「カートに商品が入るまでの流れ」「ヘッダーのカートの数字（バッジ）が増える仕組み」「カートの持ち主を見分ける仕組み（匿名カートのトークン）」「在庫切れの商品をカートに入れようとしたとき」

30 秒版

「カートに入れる」を押すと、PurchasePanel の onAdd が addCartItem を呼び、ブラウザから BFF の POST /api/cart/items に variant_id と quantity を送ります。このとき Cookie の csrf_token と同じ値を X-CSRF-Token ヘッダーに載せます。BFF は CSRF と入力の形を確かめます。そのあと、HttpOnly の cart_token Cookie を X-Cart-Token ヘッダーに載せ替え、内部トークンを付けて FastAPI の POST /api/v1/cart/items を呼びます。FastAPI は商品が公開中か、在庫があるか、上限を超えないかを確かめ、cart_items に 1 文で追加して、カート全体を返します。画面はその item_count でヘッダーのバッジを更新し、トーストを出します。カートのトークンは、最初の呼び出しで FastAPI が発行し、BFF が Cookie に載せます。

② 画面からバックエンドへ

事実: 3 章の操作は状態を変えるので、すべてブラウザ → BFF → FastAPI の経路です（初回表示のように Server Component から直接呼ぶ操作はありません）。BFF の役割は、CSRF の検証と、cart_token Cookie の値を X-Cart-Token ヘッダーに載せ替えることです。Cookie は 2 つあります。cart_token は HttpOnly（JavaScript から読めない）、csrf_token は JavaScript が読んでヘッダーに載せるので HttpOnly なしです。

  1. onAdd。在庫ありの組み合わせ（canAdd）のときだけ動く。busy を立ててボタンを無効にし、選択から決めた variant_id と数量で addCartItem を呼ぶ。

    ボタンを押すと onAdd が動きます。選んだ色とサイズから決めた variant_id と数量を渡して、addCartItem を呼びます。

    次へ: addCartItem にカーソルを置いて F12

  2. 送り先は /api/cart/items（BFF）、本文は {variant_id, quantity}。戻り値は Cart（カート全体）。

    送り先は同じ Next.js の /api/cart/items です。FastAPI の URL は、ブラウザには出ません。

    次へ: mutate にカーソルを置いて F12

  3. 状態を変える操作（POST・PATCH・DELETE）の共通処理。ensureCsrfToken で Cookie の csrf_token を読み、X-CSRF-Token ヘッダーに載せる。Cookie が未発行なら先に GET /api/cart で発行させる（順路 B）。

    カートを変える操作は、共通の mutate を通ります。Cookie の csrf_token と同じ値をヘッダーに載せて送ります。

    次へ: URL の文字列なので F12 では飛べない。⌘P で apps/web/app/api/cart/items/route.ts を開く

  4. BFF の POST。順に、① CSRF の検証 ② 本文の形（variant_id が整数、quantity が正の整数） ③ proxyCartRequest で FastAPI へ。①で外れると 403 forbidden、②で外れると 400 validation_error。どちらも FastAPI は呼ばない。

    BFF はまず CSRF を確かめ、次に送られた値の形を確かめます。ここで外れたものは、FastAPI まで届きません。

    次へ: verifyCsrf にカーソルを置いて F12

  5. Cookie csrf_token とヘッダー X-CSRF-Token を取り出して比べる。どちらかが無い、形が違う（43 文字の base64url）、一致しない、のいずれも 403。比較は定数時間の isCsrfValid。

    CSRF は、Cookie の値とヘッダーの値が一致するかで見ます。別のサイトから送られたリクエストは、ヘッダーに載せる値を知らないので通りません。

    次へ: ⌘P で apps/web/app/api/cart/items/route.ts に戻り、末尾の proxyCartRequest にカーソルを置いて F12

  6. Cookie の cart_token を readCookie で取り出し、X-Cart-Token ヘッダーに載せ替える。apiFetch で FastAPI の /cart/items へ POST。トークンは URL にもクエリにも載らない。

    ブラウザの Cookie にあるカートのトークンを、BFF が FastAPI へのヘッダーに載せ替えます。

    次へ: apiFetch にカーソルを置いて F12

  7. X-Internal-Token を付け、API_BASE_URL + /api/v1/cart/items へ POST（本文は JSON）。X-Cart-Token は呼び出し元が headers で渡したもの。

    FastAPI の URL に、内部トークンのヘッダーを付けて呼びます。

    次へ: ⌘P で apps/api/app/routers/cart.py を開き、⌘⇧O で add_item へ

  8. @router.post("/items")。成功は 201。ヘッダー X-Cart-Token を Header で受け、本文は CartItemIn で受ける。これがバックエンド側の着地点。

    ここに届くのが FastAPI の POST /api/v1/cart/items で、routers/cart.py の add_item です。トークンはヘッダーで受けます。

初めてカートに入れるときは、まだ Cookie がありません。そこで mutate の前に、カートのトークンと CSRF 用の Cookie を発行する呼び出しが 1 回入ります。この呼び出しの流れが、次の順路 B「匿名カートトークンの発行」です。

  1. Cookie に csrf_token が無ければ fetchCart（GET /api/cart）を呼び、そのあと Cookie を読み直す。まだ無ければ 403 forbidden を投げる。

    初めてのときは Cookie が無いので、先にカートを取る GET を 1 回呼んで、BFF に Cookie を発行してもらいます。

    次へ: ⌘P で apps/web/app/api/cart/route.ts を開く

  2. GET は CSRF の検証なし。cart_token が Cookie に無ければ、X-Cart-Token なしで FastAPI の /cart を呼ぶ。

    トークンが無い呼び出しも、そのまま FastAPI に渡します。

    次へ: ⌘P で apps/api/app/routers/cart.py を開き、⌘⇧O で get_cart へ

  3. @router.get("")（GET /api/v1/cart）。X-Cart-Token は任意（None 可）。

    ここもトークンが無くて構わない作りです。

    次へ: cart_service.get_cart を F12 で開き、中の resolve_cart へ

  4. ヘッダーが無い・形が違う・未知のとき、新しいトークンで active のカートを作る。注文済みのカートのトークンなら、旧カートから外して同じトークンで新しいカートを作る。

    トークンが無ければ、新しいカートを作って、新しいトークンを発行します。発行するのは FastAPI で、BFF ではありません。

    次へ: new_cart_token にカーソルを置いて F12

  5. 32 バイトの乱数を base64url にした 43 文字。形の検査は normalize_token（英数・-・_ の 64 文字以内）。

    推測できない 43 文字の乱数です。この文字列を知っている人が、そのカートの持ち主として扱われます。

    次へ: ⌘P で apps/web/lib/server/cart-proxy.ts を開き、⌘⇧O で proxyCartRequest へ

  6. 応答の cart_token が Cookie と違う（または Cookie 無し）なら Set-Cookie で更新する。csrf_token が未発行なら issueCsrfCookieIfMissing で、こちらも発行する。

    応答に入っているトークンを、BFF が Cookie にして返します。CSRF 用の Cookie も、ここで一緒に発行します。

    次へ: buildCartTokenCookie にカーソルを置いて F12

  7. cart_token は HttpOnly・SameSite=Lax・90 日。Secure は APP_ENV=production のときだけ付く。

    カートのトークンの Cookie は、JavaScript から読めない設定で、期限は 90 日です。

    次へ: ⌘⇧O で buildCsrfTokenCookie へ

  8. csrf_token は httpOnly: false。JavaScript が document.cookie から読んでヘッダーに載せるため。

    CSRF 用の Cookie だけは、ヘッダーに載せるために、JavaScript から読めるようにしてあります。

③ バックエンドの処理

  1. /api/v1 配下のルーターすべてに verify_internal_token が付く。cart.router もここで登録される。

    /api/v1 配下は、この 1 か所で内部トークンの検証を必須にしています。カートのルーターもここで登録しています。

    次へ: verify_internal_token にカーソルを置いて F12

  2. X-Internal-Token が無い・一致しないと 401 unauthorized。

    BFF 以外からの呼び出しは、ここで 401 になります。

    次へ: ⌘P で apps/api/app/routers/cart.py を開き、⌘⇧O で add_item へ

  3. 本文を CartItemIn で受ける。形が外れると、サービスに入る前に 400 validation_error。

    ルーターは、本文の形を Pydantic に確かめさせて、サービスに渡すだけです。

    次へ: CartItemIn にカーソルを置いて F12

  4. variant_id は整数、quantity は 0 より大きい整数。上限（10・50）はここに書かない。書くと 422 が 400 に変わってしまうため（クラスの docstring に理由がある）。

    ここでは形だけを確かめます。点数の上限は業務のルールなので、ここではなくサービスで判定します。

    次へ: ⌘P で apps/api/app/services/cart.py を開き、⌘⇧O で add_item へ

  5. 判定の順は、① resolve_cart でカートを特定 ② 公開商品の variant が無ければ rollback して 404 ③ stock <= 0 なら rollback して 409 out_of_stock（items に variant_id） ④ 加算 ⑤ 加算後の数量で上限を検査し、超えたら rollback して 422 ⑥ commit して build_cart_response。

    サービスは、商品があるか、在庫があるか、加算して上限を超えないか、の順に確かめます。途中で外れたら加算を取り消して、エラーを返します。

    次へ: get_variant_of_published_product にカーソルを置いて F12

  6. variants と products を結合し、公開条件（published_filter）を付けて 1 件取る。無ければ None。非公開の商品と存在しない variant は、ここで区別されず 404 になる。

    非公開の商品の variant は、ここで「無いもの」として扱われます。

    次へ: ⌘⇧O で upsert_item_add へ

  7. INSERT … ON DUPLICATE KEY UPDATE の 1 文（MySQL の方言）。同じ variant が既にあれば数量を足す。同時に 2 回押しても、行は 1 つになる。

    同じ商品をもう一度入れると、行を増やさず、数量を足します。1 文で行うので、同時に 2 回押されても行は重複しません。

    次へ: ⌘P で apps/api/app/services/cart_rules.py を開き、⌘⇧O で check_limits へ

  8. 加算後の数量で検査する。1 明細が 10 点を超えたら 422 limit_exceeded（limit は 10）、カート合計が 50 点を超えたら 422（limit は 50）。両方超えたときは 10 を先に返す。

    上限は、1 つの商品で 10 点、カート全体で 50 点です。足したあとの数で判定し、超えていたら足す前に戻します。

    次へ: ⌘⇧O で stock_status を見るか、⌘P で services/cart.py に戻り build_cart_response へ

  9. 明細・小計・送料・合計を組み立てる。item_count は数量の合計。can_checkout は、明細が 1 件以上で、全明細の在庫状態が ok のときだけ true。

    追加したあとのカート全体を作り直して返します。画面はこの応答だけで、明細も合計もバッジも更新できます。

    次へ: ⌘P で apps/api/app/models/cart.py を開き、⌘⇧O で CartItem へ

  10. cart_items テーブル。(cart_id, variant_id) が UNIQUE、quantity > 0 の CHECK。カート本体は carts（anonymous_token が UNIQUE、status は active／ordered／merged）。

    同じカートに同じバリエーションは 1 行だけ、という制約が DB にあります。同時に 2 回押されたとき、行の重複を最後に止めるのは、この制約です。

詰まりそうな質問

1〜2分CSRF はどう防いでいますか

Double Submit Cookie という方式です。csrf_token の Cookie と、X-CSRF-Token ヘッダーの値が一致するときだけ、BFF が通します。他のサイトから送られたリクエストは、Cookie は付いても、ヘッダーに同じ値を載せられません。判定は isCsrfValid（定数時間の比較）で、テストは csrf-validation.test.ts と bff.cart-route.test.ts です。

追撃: cart_token は HttpOnly なのに、csrf_token は JavaScript で読めるのはなぜですか

csrf_token は、JavaScript が読んでヘッダーに載せる必要があるためです。cart_token は、BFF が Cookie からヘッダーに載せ替えるので、JavaScript に読ませる必要がありません。

1〜2分同じ商品を同時に 2 回押したらどうなりますか

追加は INSERT … ON DUPLICATE KEY UPDATE の 1 文で、(cart_id, variant_id) の UNIQUE 制約もあるので、行は 1 つで数量が 2 になります。確認は IT-011-01（asyncio.gather で同時に 2 回送る）です。画面側も、処理中はボタンを無効にします。ただし IT-011-01 は CI ではスキップされます。

1〜2分在庫が 1 しかないのに、2 点をカートに入れられるのはなぜですか

設計仕様書 DS-PRC-011 で、数量が在庫を超えていても追加は許すと決めています。在庫の確定は、注文確定時の引当で行うためです。カートの応答は明細ごとに stock_statusを返します。1 つでも insufficient があると「レジへ進む」を無効にします。確認は IT-011-02 の別関数 test_it_011_02_quantity_over_stock_is_allowed_with_insufficient です。
