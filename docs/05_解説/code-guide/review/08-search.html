8. 商品検索とサジェスト

指定のされ方と 30 秒版

「商品を検索する機能」「検索ボックスに入力して候補を出す機能」「検索結果を表示する機能」「該当商品が 0 件のときの表示」

30 秒版

ヘッダーの検索欄に入力すると、300 ミリ秒待ってから候補を取りに行き、Enter で検索結果ページに移ります。候補も検索結果も、Next.js から FastAPI の検索 API を呼んでいます。商品名・説明・カテゴリ名の部分一致で探して、公開商品だけを新着順に返します。0 件のときは、言い換え辞書の候補とおすすめカテゴリを添えます。全角半角やひらがなカタカナの違いは、データベースの照合順序に任せています。

検索 API にレート制限はありません。ADR-0003 で見送り、公開環境でも ADR-0004 の判断で実装していません。Basic 認証を知らない人は /api/* に届かない、という前提に立っています。

② 画面からバックエンドへ

経路は 2 本あります。入力中の候補は、BFF を経由します。結果ページの初回表示は、Server Component が BFF を通さず FastAPI を直接呼びます。まず候補の経路から見ます。

  1. 入力欄の onChange。文字が変わるたびに scheduleSuggest を呼ぶ。

    検索欄に文字を打つたびに、候補を取りに行く予約を入れ直します。

    次へ: scheduleSuggest にカーソルを置いて F12

  2. setTimeout の中。前の予約と前の通信を止め、300 ミリ秒（DEBOUNCE_MS）たってから fetchSuggestions を呼ぶ。

    入力が 300 ミリ秒止まったときだけ呼びます。打っている途中の通信は中止します。候補が取れなくても、検索自体は Enter で続けられるので、エラーは無視しています。

    次へ: fetchSuggestions にカーソルを置いて F12

  3. ブラウザから GET /api/search/suggest?q=… を呼ぶ行。

    ブラウザが話すのは Next.js だけです。FastAPI は直接呼びません。読み取りだけなので CSRF トークンは付けていません。

    次へ: ⌘P で apps/web/app/api/search/suggest/route.ts を開く（URL 文字列なので F12 では飛べない）

  4. BFF の GET。q だけを FastAPI の /search/suggest に渡す。

    Next.js が取り次ぎます。受け取るクエリは q だけです。

    次へ: apiFetch にカーソルを置いて F12

  5. apiFetch。内部トークンのヘッダを付けて FastAPI の /api/v1 配下を呼ぶ。接続できなければ 5 秒で UpstreamUnavailableError。

    FastAPI を呼ぶときは、BFF が内部トークンを付けます。ブラウザには見えません。

    次へ: ⌘⇧F で /search/suggest を検索（コード側のパスには /api/v1 が付いていない）

  6. FastAPI のルーター suggest（GET /api/v1/search/suggest、DS-API-004a）。サービスを呼ぶ行。

    ここからがバックエンドで、リクエストの届く先です。ルーターは受け取って返すだけで、判断はサービスに任せています。

    次へ: suggest_products にカーソルを置いて F12

次は、Enter か候補の選択で結果ページへ移る経路です。結果ページの初回表示では、ブラウザではなく Next.js のサーバー側が FastAPI を直接呼びます（設計仕様書 P2 追補a 1 章）。

  1. goToSearch。空白を落とした検索語で /search?q=… へ移る。

    Enter でも候補の選択でも、商品詳細ではなく検索結果ページに移ります。

    次へ: ⌘P で apps/web/app/search/page.tsx を開く

  2. Server Component の SearchPage。q は 100 文字で切り、空白だけなら API を呼ばない。

    結果ページは Next.js のサーバー側で FastAPI を呼びます。BFF を挟まないので、通信が 1 段少なくなります。

    次へ: getSearch にカーソルを置いて F12

  3. getSearch。q・page・per_page のクエリ文字列を作って apiFetch を呼ぶ。

    候補のときと同じ apiFetch を使います。

    次へ: ⌘⇧F で "/search" を検索（routers/search.py を開く）

  4. ルーター search（GET /api/v1/search、DS-API-004）。

    ここが検索 API の入口です。検索語の長さの制約もここで掛けています。

    次へ: search_products にカーソルを置いて F12

「もっと見る」だけは BFF を通ります。 から へ進み、ページ番号だけを差し替えて同じ /search を呼びます。

③ バックエンドの処理

  1. サービス search_products の先頭。検索語を検査して整える。

    最初に検索語を整えます。空なら 400 を返して、ここで終わります。

    次へ: _validate_query から normalize_search_term へ F12 を 2 回

  2. 前後の空白を落とし、NFKC 正規化、連続空白の整理、空チェック、100 文字の判定。

    この正規化は、一致判定のためのものではありません。目的は、空白の整理と長さの判定、それから言い換え辞書を引くときの表記そろえです。一致の判定はデータベースの照合順序に任せています（DS-DEC-34）。

    次へ: ⌘⇧O で repositories/search.py の build_match_condition へ（別ファイル）

  3. 商品名・説明・カテゴリ名の部分一致を OR でつなぐ条件。カテゴリ名は product_categories 経由のサブクエリ。

    % と _ は SQLAlchemy の autoescape に任せ、自前のエスケープは書いていません。SQL は文字列連結で作っていません。

    次へ: ⇧F12 で呼び出し元（search_published）を見る

  4. 件数を数える SQL と、新着順で 1 ページ分を取る SQL。どちらも公開商品だけ（published_filter）。

    公開商品に絞ったうえで、新着順に 24 件ずつ取ります。総件数は別の SQL で数えます。

    次へ: ⌘⇧O で search_products に戻り total == 0 の分岐へ

  5. 0 件のときだけ、類似キーワードとおすすめカテゴリを作る分岐。

    0 件のときだけ 2 つを添えます。言い換え辞書の候補は、実際に 1 件以上ヒットするものだけを残します。おすすめカテゴリは、商品数の多い子カテゴリの上位 3 件です。

サジェストは から へ進みます。同じ検査を通したあと、商品名の前方一致を id 順に最大 5 件取り、足りなければ部分一致で補います（）。

④ 応答から表示まで

  1. 候補の応答を受けたところ。items を state に入れ、1 件以上なら一覧を開く。

    BFF から戻った候補を state に入れます。0 件なら一覧は開きません。

    次へ: 同じファイルの下の role="listbox" へスクロール

  2. 候補一覧（role="listbox"）の描画。各候補は role="option"。

    候補は最大 5 件です。クリックすると、入力欄の blur より先に選択を確定させて、結果ページへ移ります。

    次へ: ⌘P で apps/web/app/search/page.tsx を開く

  3. 結果ページで、見出し・件数のあとに SearchResults へ応答を渡す。

    FastAPI の応答をそのまま、結果の一覧を描く部品に渡します。見出しには正規化後の検索語と件数を出します。

    次へ: SearchResults にカーソルを置いて F12

  4. 0 件の分岐。「もしかして」（類似キーワード）と「おすすめのカテゴリ」。0 件でなければ下のグリッドと「もっと見る」。

    0 件のときは、ほかの探し方を案内します。類似キーワードが空なら「もしかして」の見出し自体を出しません。検索語に HTML が入っていても、React の標準のエスケープで文字として表示されます。

詰まりそうな質問

1〜2分「ハンツ」で「パンツ」が出るのは不具合ではないですか

不具合ではなく、設計で受け入れた制限です（DS-DEC-34、案 A）。MySQL 8.4 の照合順序 utf8mb4_0900_ai_ci が、全角半角・ひらがなカタカナ・清音濁音・半濁音を同じ文字として扱います。ローカルの MySQL 8.4 で実際に比較して確認しています（設計仕様書 P2 追補a 4.4）。

アプリ側で二重に正規化すると、DB 任せの利点が消えます。そのため DB の挙動をそのまま仕様にしました。ST-F003-07 と IT-004-08 で確認しています。

追撃: 区別したい場合はどうしますか

意見: 照合順序を変えるか、検索の列だけ別の照合順序にする方法が考えられます。他の画面の検索結果にも影響するので、変える前に影響範囲を見る必要があると思います。

1〜2分検索 API にレート制限が無いのはなぜですか

ADR-0003 で見送りました。理由は、公開商品を読むだけで個人情報を含まないこと、当時は Azure に公開しておらず実害が出る状況ではなかったこと、置き場所の設計がスコープを圧迫することです。

公開するにあたり ADR-0004（2026-09-25）で再判断し、見送りを維持しました。サイト全体に Basic 認証をかけていて、知らない人は /api/* に届かないためです。この判断は Basic 認証がかかっている間に限ります。認証を外す一般公開に切り替えるなら、ADR-0003 をもう一度見直します。

追撃: 入れるなら、どこにどう入れますか

意見: 既存の SlidingWindowRateLimiter は注文照会用で、プロセス内のメモリで数えます。API は --workers 2 で動くので、そのまま流用するとワーカーごとに別々に数えることになります。共有ストアに置くか、App Service 側の制限に任せる案を比べることになると思います。
