5. 注文手続き（入力 → 確認画面へ）

「注文手続きの画面を説明してください」「『確認画面へ』を押すと何が起きますか」「prepare とは何ですか」「入力したお届け先はどこに置いていますか」「フォームの初期値がダミーなのはなぜですか」

30 秒版

お届け先を入力して「確認画面へ」を押すと、ブラウザ側で入力を検査し、通れば POST /api/checkout/prepare を送ります。Next.js の BFF はこれを FastAPI の /api/v1/checkout/prepare に取り次ぎ、FastAPI がカートの中身から金額を計算して、冪等キーと一緒に返します。画面は応答と入力値を sessionStorage に保存して、確認画面へ移ります。お届け先はサーバーには保存しません。

未実装（画面には出ているが選べない）: 会員としての購入（P2）、店舗受け取り（P2）、クーポン（P3）。決済はスタブで、カード番号の入力欄はありません。未実装

② 画面からバックエンドへ

リクエストは 2 区間あります。ブラウザから BFF までが 1 本、BFF から FastAPI までがもう 1 本です。

区間メソッドとパス主なヘッダー本文

  1. パンくずと CheckoutForm を並べるだけの Server Component。入力の処理はここには無い。

    注文手続きのページです。パンくずとフォームを置くだけで、入力の処理はクライアントコンポーネントの CheckoutForm が受け持っています。

    次へ: 同じファイルの CheckoutFormInner（⌘⇧O で関数名を入力）

  3. 入力値の初期化。{ ...DEMO_CHECKOUT_FORM, ...(session?.form ?? {}) } の順なので、保存済みの入力があればダミー値より優先される。

    入力欄の初期値は、保存された入力があればそれ、無ければデモ用のダミー値です。講義用のサイトなので、本物の個人情報は入れさせたくありません。

    次へ: DEMO_CHECKOUT_FORM にカーソルを置いて F12

    ダミー値はすべて架空です。メールアドレスは example.com で、注意書きも環境を問わず常に画面に出しています。

    次へ: ⌘⇧F で validateCheckoutForm(values) を検索し、CheckoutForm.tsx の結果を開く

    「確認画面へ」を押すと、まず入力を検査します。エラーがあれば赤字を出して、最初のエラー欄にフォーカスし、ここで止めます。

    次へ: validateCheckoutForm にカーソルを置いて F12

  6. 氏名 50 文字以内、郵便番号 7 桁、電話 10〜11 桁、メールの形式、住所は結合後 200 文字以内。ハイフンと空白は digitsOnly が落としてから数える。FastAPI の OrderCreateIn と同じ規則。

    検査の規則は、サーバー側の Pydantic と同じにしてあります。画面で先に赤字を出し、サーバーでも同じ規則でもう一度検査します。

    次へ: ⌘P で CheckoutForm.tsx に戻り、onSubmit の prepareCheckout を探す（⌘⇧F で await prepareCheckout() でも可）

  7. 検査を通ったときだけ prepareCheckout() を呼ぶ。成功すると応答と入力値を保存して /checkout/confirm へ移る（④ で見る）。

    検査を通ったら prepareCheckout を呼びます。確認画面に出す金額と、注文確定用の冪等キーを取りに行く呼び出しです。

    次へ: prepareCheckout にカーソルを置いて F12

    ブラウザが呼ぶのは、同じサイトの /api/checkout/prepare だけです。FastAPI のアドレスはブラウザには見えません。

    次へ: post にカーソルを置いて F12

  9. ensureCsrfToken() で Cookie csrf_token を読み（無ければ GET /api/cart で発行させる）、ヘッダー X-CSRF-Token に載せる。credentials: "same-origin"。失敗は OrderApiError（status と本文）で投げる。

    POST なので CSRF トークンをヘッダーに載せます。トークンの検証は、このあと BFF で行います。

    次へ: URL は文字列なので F12 では飛べません。⌘P で api/checkout/prepare/route と入力して開く

  10. BFF の Route Handler。最初に CSRF を検証し、通らなければ 403 forbidden を返して FastAPI へは進まない。通れば proxyOrderRequest にパス /checkout/prepare を渡す。

    BFF の Route Handler です。最初に CSRF を検証して、通らなければ 403 で止めます。通ったら、取り次ぎ関数に FastAPI 側のパス /checkout/prepare を渡します。

    次へ: 検証の中身は verifyCsrf にカーソルを置いて F12

  11. Cookie の値とヘッダーの値を isCsrfValid で比べる（Double Submit Cookie。両方あり、43 文字の形で、一致するときだけ通す）。不一致は 403 {"code":"forbidden"}。

    Cookie とヘッダーの値が一致したときだけ通します。別のサイトからの送信では、この 2 つを揃えられません。

    次へ: ⌘P で prepare/route.ts に戻り、proxyOrderRequest にカーソルを置いて F12

  12. Cookie cart_token を X-Cart-Token に載せ、X-Forwarded-For に clientIp が決めた利用者 IP を載せる（利用者が送ってきた値は転送しない）。メソッドは POST、本文は {}、待ち時間は 15 秒。

    カートのトークンと利用者の IP をヘッダーに載せて、FastAPI を呼びます。利用者が付けた X-Forwarded-For は信用せず、BFF が決めた値だけを送ります。

    次へ: apiFetch にカーソルを置いて F12

  13. URL は API_BASE_URL ＋ /api/v1 ＋ パスで、結果は POST /api/v1/checkout/prepare。ここで X-Internal-Token を付ける。接続できない・時間切れは UpstreamUnavailableError になり、BFF は 503 upstream_unavailable を返す。

    ここで内部トークンを付けて、FastAPI の POST /api/v1/checkout/prepare を呼びます。ここから先がバックエンドです。

    次へ（③）: パスは文字列なので F12 では飛べません。⌘⇧F で verify_internal_token を検索し、main.py の結果を開く

③ バックエンドの処理

prepare は読み取りだけで、DB には何も書きません。カートの状態を確かめ、金額を計算し、冪等キーを作って返します。

  1. /api/v1 配下の全ルーターに verify_internal_token が掛かる。続けて checkout.router・orders.router を登録している。health だけは外（create_app 側）。

    FastAPI は、/api/v1 配下のすべてのルーターに内部トークンの検証を付けています。BFF 以外からは入れません。

    次へ: verify_internal_token にカーソルを置いて F12

  2. 期待値が未設定、ヘッダーが無い、または不一致なら 401 unauthorized。比較は hmac.compare_digest。設定漏れのときは全リクエストを拒否する側に倒している。

    内部トークンが無い、または違うときは 401 です。環境変数を設定し忘れたときも、すべて拒否します。

    次へ: ⌘P で routers/checkout.py を開く

  3. prefix="/checkout" と "/prepare" で POST /api/v1/checkout/prepare。ヘッダー X-Cart-Token を受けてサービスに渡すだけ。response_model=PrepareOut。

    ルーターは薄く作ってあり、カートのトークンを受け取ってサービスに渡すだけです。

    次へ: checkout_service.prepare の prepare にカーソルを置いて F12

  4. prepare の順番。(1) カートを特定（404）(2) active でなければ 409 already_ordered（注文番号付き）(3) 設定を読む (4) 明細を取得、空なら 409 empty_cart (5) 在庫状態が ok でない明細があれば 409 out_of_stock (6) 金額計算 (7) 冪等キー発行。

    prepare は、まずカートを特定します。注文済みのカート、空のカート、在庫のない明細は 409 で弾きます。そのあとで金額を計算し、冪等キーを付けて返します。

    次へ: 1 つ目の resolve_existing_cart にカーソルを置いて F12

  5. 既存のカートだけを返す。トークンが無い・形が合わない・DB に無いなら 404 not_found。ここでは新しいカートは作らない（作るのは GET /cart）。

    カートが見つからないときは 404 です。確認画面の段階で、新しいカートを勝手に作ることはしません。

    次へ: services/checkout.py の prepare に戻り、carts_repo.fetch_lines の fetch_lines にカーソルを置いて F12

  6. カート明細・バリエーション・商品を結合した 1 本の SELECT。単価は products.price_incl_tax（現在の値）、在庫は variants.stock、公開フラグ、最初の画像のパス。

    明細は 1 回の SELECT でまとめて読みます。単価は、その時点の商品マスタの値を使います。

    次へ: services/checkout.py に戻り、calc_totals にカーソルを置いて F12

  7. 明細 0 件は 409 empty_cart。小計 → 送料（小計が閾値以上なら 0、未満なら設定値）→ 合計 → 内税（合計 × 10 ÷ 110 の円未満切り捨て）。税率・送料・閾値は system_settings の値。

    金額は、小計、送料、合計、内税の順にサーバーで計算します。送料の閾値と税率は、設定テーブルの値です。画面側では計算しません。

    次へ: services/checkout.py に戻り、new_idempotency_key にカーソルを置いて F12

  8. 32 バイトの乱数を base64url にした 43 文字。prepare の時点では DB に保存しない。最初に保存されるのは、注文確定の INSERT orders（6 章）。

    冪等キーは、ここで 43 文字の乱数として作るだけで、DB には保存しません。注文を確定するときに、初めて orders テーブルに入ります。

    次へ: ⌘P で models/cart.py を開く（読むテーブルの確認）

  9. prepare が読むのは carts（status は active か ordered）・cart_items・variants・products・product_images・system_settings。書き込みはしない。

    prepare はこれらのテーブルを読むだけで、何も書き込みません。

    次へ（④）: ⌘P で schemas/order.py を開く

詰まりそうな質問

0〜1分なぜ prepare を別の API にしているのですか

確認画面に出す金額を、画面ではなくサーバーで計算するためです。prepare が金額と冪等キーを返し、注文確定のときに、画面に出した金額をサーバーが再計算した値と照合します（6 章）。冪等キーは prepare のたびに新しく作るので、金額が変わった場合や決済に失敗した場合は、prepare を呼び直して新しいキーで注文し直せます。

追撃: 冪等キーはいつ DB に入りますか

prepare の時点では入りません。注文確定の最初の INSERT（orders.idempotency_key、UNIQUE）で初めて保存されます。

1〜2分お届け先をサーバーに保存せず sessionStorage に置くのはなぜですか

注文を確定するまでは、注文の実体が無いためです。確認画面に渡すだけなので、タブを閉じれば消える sessionStorage にだけ置いていて、localStorage にもサーバーにも保存していません。サーバーに入るのは、注文確定で orders にコピーされるときです。

意見: sessionStorage は同じオリジンの JavaScript から読めます。XSS があれば読まれうる点は、この方式の弱みだと思います。氏名にスクリプトタグを入れても実行されないことは、手動の ST-SEC-05（2026-09-24 合格）で確認しています。コード全体を調べて XSS の経路が無いと確かめたわけではありません。

0〜1分フォームのテストが少ないようですが

CheckoutForm の自動テストは、ダミー初期値の 4 本と、検査関数の 14 本です。フォームを送信して prepare を呼び、確認画面へ移るところまでの自動テストは無く、手動の ST-F013-01・02 と AT-01 で確認しています（コード解説書 9 章 C2）。部品テストを足すのは P2 の中で行う予定です。
